# documents-reader

Локальная проверка концепции (PoC): система читает русскоязычные договоры (PDF
с текстом и сканы), разбирает их на разделы и пункты, извлекает ключевые поля
с дословной цитатой, ищет по тексту и отвечает на вопросы со ссылкой на пункт
договора. Качество каждого этапа измеряется на эталонном наборе. Всё работает
на одном ноутбуке, данные за пределы машины не уходят.

Цель PoC — получить измеренные цифры качества по каждому этапу (чтение,
извлечение, поиск, ответ) и по ним решить, стоит ли строить систему для полного
архива.

## Что умеет система

| Фича | Что делает | Команды |
|---|---|---|
| 01 | Приём документов: неизменная копия файла, реестр, вид каждой страницы | `add`, `list`, `show`, `verify`, `remove` |
| 13 | Распознавание страниц-сканов (Tesseract, русский язык) | `recognize`, `recognize-report` |
| 03 | Чтение текста с координатами строк, флаги качества страниц | `read`, `text`, `read-report` |
| 04 | Разбор структуры: преамбула, разделы, пункты, реквизиты | `parse`, `outline`, `clause` |
| 05 | Извлечение шести полей прототипа с проверенной цитатой | `extract`, `fields` |
| 07 | Нарезка на отрывки, индексы по словам и по смыслу | `index`, `passage` |
| 08 | Гибридный поиск: слова + смысл + реранкер | `search` |
| 09 | Ответ на вопрос с цитатами, каждую цитату проверяет программа | `ask` |
| 10 | Ответ по таблице действующих значений шести полей: число, условие, список | `ask-table` |
| 02 | Эталонный набор, сравнение с эталоном, таблица результатов | `eval …` |

Ещё не сделаны: проверки правилами (06), выбор маршрута
(11), веб-экран (12). Карта фич — в [docs/tech-context.md](docs/tech-context.md#карта-фич),
исходные описания — в [docs/features/](docs/features/).

Шесть полей прототипа: номер договора, заказчик, подрядчик, цена без НДС,
цена с НДС, дата окончания. Полный перечень полей — в
[каталоге полей](docs/field-catalog.md).

## Главные правила

- **Данные не покидают машину.** Договоры, извлечённые значения, вопросы и ответы
  обрабатываются только локально. Модели работают на этой же машине (адреса только
  `127.0.0.1`), сеть во время работы не нужна.
- **Реальные договоры не попадают в репозиторий.** Они лежат в папке данных вне
  репозитория (`DOCREADER_DATA_DIR`). Программа отказывается работать с папкой
  данных внутри репозитория и с нелокальной базой. В репозитории — только код
  и синтетические примеры.
- **Нет значения без цитаты.** Значение поля и утверждение в ответе принимаются,
  только если программа нашла их цитату в тексте договора. «Не найдено» — допустимый
  ответ.
- **Исходный файл — источник истины.** Любой результат прослеживается до документа,
  страницы и пункта.

Полный список принципов — в [конституции проекта](.specify/memory/constitution.md);
она имеет приоритет над остальными документами.

### Что можно передавать ИИ-агенту, а что нельзя

Код пишется с помощью облачного ИИ-агента, поэтому для каждой команды определено,
можно ли показывать агенту её вывод:

| Можно передавать | Нельзя передавать |
|---|---|
| Вывод `add`, `list`, `show`, `recognize`, `read`, `parse`, `extract`, `index` (идентификаторы, числа, состояния, причины) | Вывод `text`, `outline`, `clause`, `fields`, `passage`, `search`, `ask`, `ask-table` — в нём текст договоров (на синтетике можно) |
| Вывод всех команд `eval …` в терминал | Файлы, которые пишут команды `eval`: шаблоны, страница проверки и её ответы, файлы разбора, вопросы, выгрузки |
| Сводки замеров `*-summary-*.txt` | Файлы ответов замеров (`answers-b4-….txt`, `.json`), сами договоры, эталон |

## Установка

Требования: Python 3.11+ и [uv](https://docs.astral.sh/uv/), PostgreSQL 17 с
расширением pgvector (локально: Unix-сокет или `localhost`), macOS на Apple Silicon
или Linux x86_64.

```
uv sync --group ocr               # на Mac; группа ocr — движок распознавания сканов
cp .env.example .env              # поправить значения под эту машину
createdb docreader
uv run --env-file .env docreader migrate
```

Переменные окружения описаны в [.env.example](.env.example): папка данных
`DOCREADER_DATA_DIR` (обязательна, вне репозитория) и адрес базы
`DOCREADER_DATABASE_URL` (по умолчанию `postgresql:///docreader`). Файл `.env`
подключается к каждой команде флагом `--env-file`, а не глобально, поэтому
автотесты его не видят. Удобное сокращение для `~/.zprofile`:

```
alias dr='uv run --env-file .env docreader'
```

Дальше в примерах `dr` означает `uv run --env-file .env docreader`.

### Модели (только ноутбук)

Три сервера моделей запускаются отдельно, каждый в своём окне терминала. Адреса
и имена моделей по умолчанию совпадают с настройками программы, поэтому
`settings.toml` для них не нужен.

```
mlx_lm.server --model qwen3.6-27b-4bit --host 127.0.0.1 --port 8080          # языковая модель
llama-server -m ~/models/bge-m3-Q8_0.gguf --embedding --pooling cls \
  -c 8192 -b 8192 -ub 8192 -np 1 --host 127.0.0.1 --port 8081                # модель поиска
llama-server -m ~/models/bge-reranker-v2-m3-Q8_0.gguf --reranking \
  -c 8192 -b 8192 -ub 8192 -np 1 --host 127.0.0.1 --port 8082                # реранкер
```

Какой команде что нужно:

| Команды | Языковая модель | Модель поиска | Реранкер |
|---|---|---|---|
| `extract` | да | — | — |
| `index` | — | да | — |
| `search` | — | да | да (без него — `--no-rerank`) |
| `ask` | да | да | да |
| `ask-table` | да | — | — |
| `eval search` | — | да | да |
| все остальные | — | — | — |

`recognize` использует Tesseract (`uv sync --group ocr` и пакет `tesseract` с данными
`rus`). Все три модели помещаются в 36 ГБ одновременно.

### Настройки

Необязательный файл `$DOCREADER_DATA_DIR/settings.toml` переопределяет значения
по умолчанию по разделам: `[reading]`, `[recognition]`, `[structure]`,
`[extraction]`, `[embedding]`, `[search]`, `[reranker]`, `[answer]`, `[table]` (ответ по таблице,
фича 10: `max_tokens`, `max_retries`, `list_rows`), `[checks]`. Неизвестный ключ —
ошибка с его именем. Значения и их смысл — в планах фич (`specs/<NNN-фича>/data-model.md`)
и в [docs/tech-context.md](docs/tech-context.md).

## Обработка договоров

Этапы идут по порядку; каждый читает сохранённый результат предыдущего и сохраняет
свой. Без идентификаторов этап берёт документы, которые его ждут; `ID…` — только
указанные, `--all` — все заново. Повторный запуск не создаёт дубликатов.

```
dr add ~/contracts/                 # приём: копии в папку данных, вид каждой страницы
dr recognize                        # распознавание страниц-сканов (~1,7 с на страницу)
dr read                             # чтение текста, флаги качества страниц
dr parse                            # разделы и пункты; идентификаторы вида D-0001/5.2
dr extract                          # шесть полей с цитатой (~4–5 мин на договор)
dr index                            # отрывки и индексы для поиска (~4 с на договор)
```

Если текст договора изменился (перераспознан, перечитан), следующие этапы
переходят в «ожидает» и при следующем запуске пересчитываются.

Отчёты по этапам: `dr list` (состояние этапов каждого документа),
`dr read-report`, `dr recognize-report [--review]` (страницы на ручной просмотр).

### Просмотр результатов

```
dr show D-0001                      # сведения о документе и его страницах
dr text D-0001 --page 3             # прочитанный текст страницы; --find ФРАЗА — поиск фразы
dr outline D-0001                   # оглавление: разделы и пункты
dr clause D-0001/5.2                # пункт с подпунктами (--own — только его текст)
dr fields D-0001                    # поля договора: значение, цитата, пункт, страница
dr passage D-0001/5.2               # отрывок поиска с его меткой
```

## Поиск и вопросы

```
dr search "срок оплаты"                          # по всем договорам
dr search "срок оплаты" --document D-0015        # в одном договоре
dr ask "Какой срок оплаты работ?" --document D-0015
dr ask-table "Сколько договоров с подрядчиком ООО Альфа?"   # по таблице значений
```

`search` показывает найденные отрывки с местом в каждом способе поиска; `--results N`
— сколько показать, `--no-rerank` — без реранкера. `ask` отвечает утверждениями,
у каждого — цитата, пункт и страница; утверждения с ненайденной цитатой помечаются,
а не выдаются за ответ. Если ответа в договоре нет, система так и говорит. На вопрос
об одном договоре его преамбула всегда показывается модели. Ответ занимает около
минуты.

`ask-table "ВОПРОС" [--include-unreviewed] [--json]` отвечает на вопросы о многих
договорах сразу. Языковая модель переводит вопрос в запрос к таблице действующих
значений шести полей; программа проверяет запрос и выполняет его по всем договорам.
Ответ — число, условие, список договоров и неучтённые договоры по причинам
(«требует просмотра», «отклонено», «не найдено», «поля не извлечены», «проверки не
выполнены»). `--include-unreviewed` учитывает и значения «требует просмотра» с
найденным значением, ответ помечается; `--json` — вывод целиком. Ничего не пишет в
базу. Нужна языковая модель (только ноутбук; на сервере разработки команда
завершается с кодом 2). Замер на вопросах аналитика: `scripts/make_table_questions.py`
собирает вопросы по шаблонам в `$DOCREADER_DATA_DIR/questions/table-10.toml`,
`scripts/quickstart_table.py --questions FILE` выполняет их и печатает сводку.

## Эталон и замер качества

Эталон — правильные ответы, с которыми система сравнивает свои результаты. Каждое
сравнение записывается в таблицу результатов; по ней видно, улучшило ли изменение
качество. Подробная пошаговая инструкция — в
[quickstart фичи 02](specs/009-evaluation-set/quickstart.md) (часть Б).

### 1. Собрать эталон полей

Эталон шести полей собирается **проверкой** готовых значений, а не вводом вручную:

```
dr eval blind pick                  # 5 договоров для слепого контроля + пустой шаблон на них
                                    # → заполнить шаблон по PDF, не глядя на значения системы
dr eval blind load eval/blind-….csv
dr eval review                      # страница проверки: eval/review-…/index.html
```

На странице проверки на каждое поле каждого договора — карточка: значение,
извлечённое моделью, значение, найденное правилами без модели, их цитаты и картинка
страницы. Пометка показывает, совпали ли два способа; карточки, где они разошлись или
никто не нашёл значение, идут первыми. Ответ — одной клавишей:

| Клавиша | Ответ |
|---|---|
| `1` | верно (при расхождении — первое значение) |
| `2` | второе значение |
| `3` | другое значение (вписать) |
| `4` | в договоре отсутствует |
| `0` | пропустить |

Ответы сохраняются в браузере, работу можно прервать. В конце — «Скачать ответы»;
файл перенести в папку данных и загрузить:

```
dr eval load eval/gold-review-….json
dr eval blind report --label "первый эталон"   # насколько эталону можно верить
```

Слепой контроль сравнивает слепую разметку с проверенными значениями: сколько раз
проверка подтвердила значение системы, а слепая разметка с ним не совпала
(ориентир — не больше 3%).

Остальные поля каталога размечаются по пустому шаблону:

```
dr eval template                    # поля очереди 1; --fields prototype | all
dr eval load eval/template-….csv
```

В шаблоне пустая ячейка — «не размечено», слово «отсутствует» — поля в договоре нет,
несколько допустимых вариантов пишутся через ` || `. Файл заменяет эталон в пределах
своих договоров и полей; если он убирает уже размеченные значения, нужен `--yes`.

### 2. Вопросы для замера поиска

```
dr eval questions load ~/…/questions/rerank-08.toml --origin set08
dr eval questions generate          # вопросы из эталона: с ответом, без ответа, с ложной посылкой
dr eval questions clauses --answers ~/…/answers-b4-….json --questions ~/…/answers-09.toml
dr eval questions load ~/…/questions/generated-….toml
```

Файлы вопросов — TOML в виде наборов замеров фич 08 и 09
([формат](specs/009-evaluation-set/contracts/files.md)). Загрузка показывает состав
набора и предупреждает, если вопросов без ответа или с ложной посылкой мало.

### 3. Сравнить и записать

```
dr eval fields --label "подсказка 05.1"          # поля фичи 05 против эталона
dr eval fields --source rules --label "правила"   # то же для правил
dr eval search --label "после 02"                 # поиск: без реранкера и с ним
```

Каждая пара «договор, поле» получает ровно один исход: верно, неверно, пропущено,
придумано, не размечено, нет результата. Различия в оформлении (дата словом и цифрами,
пробелы в суммах, кавычки, «ё») ошибкой не считаются. Каждое сравнение пишет файл
разбора в `eval/`, где рядом стоят значение эталона и значение системы.

### 4. Таблица результатов

```
dr eval results                     # все записи; запись по прежней версии эталона помечена
dr eval show 8 --outcome wrong      # какие случаи дали цифру (--field ПОЛЕ)
dr eval compare 8 12                # что стало лучше, что хуже, что изменилось из-за эталона
dr eval export                      # таблица в CSV для Excel/Numbers
```

### Скрипты замеров отдельных фич

В `scripts/` лежат разовые замеры прежних фич, их запускает аналитик на ноутбуке:
`quickstart_search.py` (реранкер, фича 08), `answers_b4.sh` / `quickstart_answers.py`
(ответы, фича 09), `review_extraction.py` (ручная проверка полей, фича 05) и другие.
Их сводки содержат только числа; файлы ответов — текст договоров.

## Тесты

Одной командой в Docker — без установки Python и PostgreSQL:

```
docker compose run --rm tests          # аргументы pytest — в конце, например -k note -x
docker compose down                    # остановить временную базу
```

Без Docker, с локальным PostgreSQL (роль с правом `CREATEDB`):

```
scripts/check.sh                       # тесты, ruff и mypy — всё, что должно пройти
DOCREADER_TEST_DATABASE_URL=postgresql:///postgres uv run pytest
uv run pytest tests/unit               # только модульные тесты, база не нужна
```

Каждый прогон создаёт и удаляет временную базу `docreader_test_*`. Модели в тестах
подменены поддельными (ответы, записанные с реальной модели на синтетических
договорах); тесты с реальной моделью (`pytest -m real_model`) по умолчанию
исключены и запускаются только на ноутбуке.

