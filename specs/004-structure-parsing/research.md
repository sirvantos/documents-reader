# Research: Разбор структуры (фича 04, минимальная версия)

Решения плана. Основа — `spec.md` (уточнения 2026-11-22), часть B
`docs/features/04-structure-parsing.md`, `docs/tech-context.md` и обзор реальных
договоров `scripts/survey_structure.py` версии 3 (56 договоров, 2026-11-22; только
числа, вывод прислан аналитиком). Где часть B расходится со спецификацией, верна
спецификация.

## R-1. Вход разбора: строки очищенного текста

**Decision.** Разбор работает по `document_text.text` и `text_span`. Строка — это
диапазон `text_span`, который начинается с начала текста или сразу после `"\n"`.
Диапазон, приклеенный к предыдущему без `"\n"` (склейка переноса, фича 03, R-6),
началом строки не считается. Для каждой строки известны страница и номер строки
на странице (`text_span`), а через `page_text.lines[line_index].table` — признак
строки таблицы. Флаги страниц берутся из `page_flag`, источник строк страницы —
из `page_text.source`.

**Rationale.** Смещения пунктов должны быть смещениями в `document_text.text`:
на них ссылаются фичи 05, 07 и 09, а `source_text_sha256` защищает от устаревших
смещений (tech-context). Строки `page_text` до склейки переносов дали бы другие
смещения.

**Alternatives.** Разбор по `page_text.lines` — отклонён: смещения пришлось бы
переводить в очищенный текст, и склеенные переносы рвали бы пункты.

**Risk.** Склейка «код или имя через дефис» (фича 03, `_code_break`) приклеивает
строку, начинающуюся с цифры, к предыдущей, если та кончается словом вроде «ОС-».
Если так приклеится начало пункта, пункт не начнётся. Обзор этого не видел (он
работал по строкам `page_text`); проверяется в quickstart Б2 по оглавлению.

## R-2. Кандидат в начало пункта

**Decision.** Кандидат — строка, которая начинается с номера:

- одно или несколько чисел через точку: `5.`, `5.2`, `5.2.`, `5.2.1`, `5.2.1.1.`;
  за номером — пробел, конец строки или сразу буква (`5.2Оплата`, обзор: 44 договора);
- в каждом числе 1–3 цифры, без ведущего нуля: `01.03.2025` — не кандидат;
- номер из одного числа — только с точкой (`5.` — раздел); `5` без точки и `5)` —
  не кандидаты (`5)` — перечень, в наборе их нет);
- сразу после номера не идёт единица суммы или меры (`млн`, `млрд`, `тыс`, `руб`,
  `коп`, `%` и подобные — список в коде): `5.3 млн` внутри пункта 5.2 — не пункт;
- строка таблицы (`table` не пуст) — не кандидат.

Номер «в напечатанном виде» — найденный токен как есть (`5.2.`, `5.2`); номер
числами — кортеж (`(5, 2)`); глубина — длина кортежа.

**Rationale.** Правило продолжения (R-3) само отсекает почти все ложные начала.
Два исключения закрываются здесь: сумма `5.3 млн` внутри пункта 5.2 (иначе R-3
приняла бы её как пункт 5.3) и дата с ведущим нулём. Шаблон даты сам по себе
кандидатов не отбрасывает: обзор — 694 из 697 строк «как дата» оказались подпунктами
вида `5.2.15`. Дата без ведущего нуля (`15.3.2025` внутри раздела 15) отсекается R-3:
после `15.3` должна идти единица, а не `2025`.

**Alternatives.** «Дата важнее номера» (как в обзоре версии 1) — отклонено: потеряло
бы 694 подпункта.

## R-3. Правило продолжения нумерации

**Decision.** Разбор помнит текущий номер `p` — последний принятый (в начале — `(0,)`).
Кандидат `c` длины `k` принимается, если он имеет один из видов:

1. **Шаг на уровне `j`** (`1 ≤ j ≤ len(p)`): `c[:j-1] == p[:j-1]`, `c[j-1] = p[j-1] + d`,
   все числа после `j`-го равны 1 (`k ≥ j`). `d = 1` — следующий номер; `2 ≤ d ≤
   max_gap + 1` — пропуск, записывается в находки. Примеры: `5.2.1 → 5.2.2`,
   `5.2.3 → 5.3`, `5.3 → 6.`, `6.3 → 7.1` (заголовок раздела 7 не распознан),
   `5.1 → 5.3` (пропуск).
2. **Спуск**: `c[:len(p)] == p`, `k > len(p)`, `1 ≤ c[len(p)] ≤ 1 + max_gap`, все
   числа после него равны 1; `c[len(p)] > 1` — пропуск. `5. → 5.1`, `5.2 → 5.2.1`,
   `5. → 5.1.1` (пункт 5.1 не распознан), `5.2 → 5.2.2` (пропуск 5.2.1).

Принятый кандидат становится текущим номером. Промежуточные уровни, которых нет
в тексте (`7` при `6.3 → 7.1`), записей не получают; вышестоящая запись пункта —
ближайший существующий предок, а при его отсутствии — нет.

**Повтор**: кандидат, равный текущему номеру или одному из его вышестоящих (второй
`5.2` при текущем `5.2` или `5.2.1`, второй `5.` внутри раздела 5), не принимается
и записывается в находки. Кандидат, равный другому уже принятому номеру (`1.2`
внутри раздела 5, `5.1` при текущем `5.3`), — ссылка: не принимается, в находки
не попадает (решение аналитика, clarify 2026-11-22, находка F1 анализа: ссылка
в начале строки есть почти в каждом договоре). Остальные непринятые кандидаты
делятся на три вида (решение аналитика после анализа 2026-11-22):

- **номер вне порядка** — кандидат больше текущего номера в порядке «по числам слева
  направо» (`5.9` при текущем `5.1`, `8.1` при текущем `5.3`): не принимается,
  записывается в находки;
- **заголовок раздела после его пункта** — кандидат `N.` при текущем разделе `N`,
  у которого нет записи раздела (раздел начат строкой `N.1` без заголовка):
  не принимается, записывается в находки;
- **номер назад** — всё остальное (ссылка, число; обзор: около одного на договор):
  не принимается и в находки не попадает.

Во всех трёх случаях строка остаётся в тексте пункта, ничего не теряется.

**Перенесённая ссылка**: кандидат сразу после строки, которая кончается запятой,
сокращением `п.`, `пп.`, `ст.`, `ч.` или словом «пункт», «подпункт», «статья»,
«раздел», «глава», «часть» в косвенном падеже (строчными, то есть внутри фразы), —
продолжение ссылки: не принимается и в находки не попадает, даже если продолжает
нумерацию. После «и», «или», «либо» кандидат принимается как обычно, но непринятый
в находки не попадает. Именительный падеж («Первая часть», «1.1. Пункт») — конец
заголовка, не ссылка. Основание — разбор пяти договоров исключения 4.3.0
(2026-11-22): все массовые находки полного набора — такие ссылки.

**Раздел без заголовка**: если пункт раздела `N` принят, а строки `N.` в разделе
нет ни до, ни после него (`6.3 → 7.1`), это находка «нет заголовка раздела 7»
(решение аналитика, clarify 2026-11-22, U1). Если заголовок встретился после пункта,
находка одна — «заголовок раздела после его пункта».

**Следствие.** Принятые номера строго растут в порядке «по числам слева направо»,
поэтому номера в документе не повторяются по построению (R-5).

**Rationale.** Обзор версии 3: 99% шагов `N.M` — следующий номер, пропусков —
2 в одном договоре, повторов разделов — 9 договоров по одному. Правило с одним
текущим номером — то, что посчитал обзор.

**Alternatives.** Отдельные счётчики по уровням — отклонено: тот же результат при
большей сложности. Принятие повторов с меткой `(2)` — отклонено аналитиком.

## R-4. Граница хвоста

**Decision.** Хвост начинается со строки-кандидата глубины 1 (`N.`), номер которой
больше номера текущего раздела, а текст после номера совпадает с шаблоном
`requisites_pattern` (настройка, R-10). Шаблон по умолчанию — как `REQUISITES`
в `scripts/survey_structure.py`: `реквизит|подписи\s+сторон|адреса\s+сторон|юридические\s+адреса`,
без учёта регистра. Ищется только после первого принятого кандидата. Предел пропуска
`max_gap` к заголовку реквизитов не применяется: хвост начинается при любом номере
больше текущего раздела (решение аналитика, clarify 2026-11-22, U2). Пропуск номера
перед заголовком реквизитов записывается в находки, как в R-3. Не найден — хвоста
нет, текст после последнего пункта остаётся в нём, находка «раздел реквизитов
не найден».

**Проверка границы.** Хвост не разбирается, но первый кандидат глубины 1 после его
начала проверяется: если его номер продолжает нумерацию от номера заголовка
реквизитов (следующий или пропуск в пределах `max_gap`), это находка «после начала
хвоста идёт раздел N» — хвост мог начаться на обычном разделе со словом «реквизиты»
в заголовке. Хвост при этом не меняется. В настоящем хвосте первый такой кандидат —
нумерация приложения с `1.`, и находки нет.

**Rationale.** Обзор: нумерованный заголовок реквизитов во всех 56 договорах,
приложения всегда после него, ни одной строки «Приложение» вверху страницы до него.

**Alternatives.** Граница по строке «Приложение» вверху страницы — следующая
итерация (выделение приложений); в минимальной версии не нужна.

## R-5. Идентификаторы

**Decision.** Идентификатор записи — `<документ>/<ключ>`:

| Запись | Ключ | Пример |
|---|---|---|
| преамбула | `преамбула` | `D-0001/преамбула` |
| раздел | номер числами | `D-0001/5` |
| пункт, подпункт | номер числами через точку | `D-0001/5.2`, `D-0001/5.2.1` |
| хвост | `реквизиты` | `D-0001/реквизиты` |

Ключ строится из номера числами, а не из напечатанного вида: `5.2.` и `5.2`
дают `5.2`. Хвост минимальной версии начинается с раздела реквизитов и называется
`реквизиты`; следующая итерация выделит из него приложения (`D-0001/П1/…`),
не меняя адреса `D-0001/реквизиты`. Идентификатор не зависит от текста пункта:
повторный разбор того же текста даёт те же идентификаторы (SC-004).

**Rationale.** Формат tech-context (`D-0001/5.2`, `D-0001/преамбула`). Уникальность —
по R-3.

**Alternatives.** `D-0001/хвост` — отклонено: при выделении приложений адрес раздела
реквизитов пришлось бы менять.

## R-6. Что хранится

**Decision.** Таблица `clause` хранит для записи диапазон собственного текста
(`start`, `end` в `document_text.text`), а не копию текста; текст берётся срезом.
Заголовок раздела хранится у записи раздела (`title`) и копируется
в `section_title` всех его пунктов. Первая и последняя страница — по `text_span`
для `start` и `end - 1`. `source_text_sha256` — отпечаток текста разбора.

**Rationale.** Копия текста удвоила бы хранилище и могла бы разойтись
с `document_text`; отпечаток всё равно сверяется при каждом чтении.

**Alternatives.** Хранить `text` — отклонено (дублирование). Список всех страниц —
отклонено: страницы между первой и последней известны, пропущенные видны по флагам.

## R-7. Находки и состояние этапа

**Decision.** Разбор возвращает список находок; `needs_review`, если есть хотя бы одна:

| Находка | Причина в `stage_status.reason` |
|---|---|
| нумерация не найдена (ни одного принятого кандидата) | `нумерация не найдена` |
| хвост не найден | `раздел реквизитов не найден` |
| после начала хвоста идёт раздел (R-4) | `после начала хвоста идёт раздел 10 (стр. 20)` |
| пропуск | `пропуск: после 5.1 идёт 5.3 (стр. 4)` |
| повтор | `повтор: 6 (стр. 9)` |
| номер вне порядка (R-3) | `номер вне порядка: 5.9 после 5.1 (стр. 4)` |
| заголовок раздела после его пункта (R-3) | `заголовок раздела 7 после пункта 7.1 (стр. 12)` |
| раздел без заголовка (R-3) | `нет заголовка раздела 7 (стр. 12)` |
| непрочитанная страница в преамбуле или основном тексте | `не прочитана страница: стр. 7` |

Находки одного вида объединяются через запятую (`пропуск: после 5.1 идёт 5.3 (стр. 4),
после 8 идёт 10 (стр. 15)`), виды — через `; `, в порядке таблицы. Непрочитанная
страница — флаг `scan_unread`, `scan_no_text` или `unreadable` у страницы, номер
которой меньше страницы начала хвоста (при отсутствии хвоста — любой); страница
в хвосте находки не даёт (clarify 2026-11-22, U3). Номера таких страниц чистая
функция разбора получает на вход, и вся причина строится в одном месте. Страница
с флагом `empty` непрочитанной не считается. Иначе — `done`.
Исключение при разборе документа — `failed` с причиной `ошибка разбора: <тип
исключения>`, остальные документы продолжаются. Текст исключения в причину
не попадает: он может содержать текст договора (принцип I; clarify 2026-11-22, D2).

**Rationale.** Уточнение 2026-11-22 (вариант A). В причине только номера пунктов и
страниц — её можно присылать агенту.

## R-8. Страницы-сканы и таблицы

**Decision.** Распознанная страница (`page_text.source = 'recognized'`) разбирается
как обычная; `outline` помечает записи, в диапазоне страниц которых она есть, а при
флаге `low_recognition_quality` — ещё и пометкой о низком качестве распознавания.
Непрочитанная страница в `outline` — отдельная строка-пометка на своём месте.
Строки таблиц отсекаются по `table`; у распознанных страниц таблицы не размечены
(фича 13), поэтому там защищает только правило продолжения.

**Rationale.** Обзор: 90% страниц основного текста распознаны, низкого качества — 0;
строк таблиц в основном тексте — 0.

## R-9. Какие документы разбираются; повторный разбор; устаревание

**Decision.**

- Доступен документ, у которого этап `reading` в `done` или `needs_review`
  и `document_text.read_pages > 0` (tech-context).
- `parse` без аргументов — доступные документы с этапом `structure` в `pending`
  или `failed`; `parse --all` — все доступные; `parse ID…` — указанные; недоступный
  указанный документ не трогается и попадает в вывод с причиной.
- Документ разбирается в одной транзакции: блокировка строки `stage_status`
  (`stages.lock`), удаление прежних записей `clause` документа, вставка новых,
  `stages.set_state`. Сбрасывать следующие этапы при изменении разбора в минимальной
  версии некому: этапов после `structure` ещё нет (фича 05 решит это у себя
  по отпечатку).
- `outline` и `clause` сверяют `clause.source_text_sha256` с
  `document_text.text_sha256`; при расхождении — ошибка «Разбор устарел: текст
  изменён — выполните docreader parse D-0001».

**Rationale.** Как у чтения (уточнение фичи 03); принцип VI.

## R-10. Настройки

**Decision.** Раздел `[structure]` в `settings.toml`:

| Ключ | По умолчанию | Проверка |
|---|---|---|
| `max_gap` | 5 | целое 0–20 |
| `requisites_pattern` | `реквизит|подписи\s+сторон|адреса\s+сторон|юридические\s+адреса` | непустая строка, компилируется как регулярное выражение |

Значения записываются в `run.settings`.

**Rationale.** Загрузчик настроек принимает только скаляры; одна строка-шаблон
проще, чем добавлять списки.

## R-11. Скорость

**Decision.** Разбор линеен по числу строк; запросов — несколько на документ (строки
и признаки таблиц, флаги, вставка `executemany`). Ожидание — доли секунды на договор;
SC-005 (50 договоров за минуту) замеряется на Mac (quickstart Б1).

## R-12. Тесты

**Decision.**

- Модульные тесты чистой функции разбора на списках строк (`structure.py`): случаи
  из раздела «Тесты» `plan.md`.
- Генератор `make_structured_contract` в `tests/synthetic/make_pdfs.py`: договор-PDF
  с текстовым слоем на кириллическом шрифте из репозитория — четыре уровня, раздел
  без подпунктов, потерянный заголовок, пропуск, повтор, слипшийся номер, `5.2.15`
  и дата в одном пункте, сумма и ссылка в начале строки, таблица с линейками
  внутри пункта, нумерованный раздел реквизитов, приложение с `1.1` заново
  и страница-картинка без текста внутри основного текста (на сервере разработки
  она остаётся непрочитанной: `DOCREADER_FORBID_MODELS=1`).
- Интеграционные тесты через CLI: приём → чтение → `parse` → `outline`/`clause`;
  покрытие текста (SC-003), одинаковые идентификаторы при повторном разборе (SC-004),
  устаревание после смены текста, выбор документов.

Реальные договоры, модели и записи распознавания не нужны.

## R-13. Обзор и разбор

**Decision.** `scripts/survey_structure.py` остаётся инструментом диагностики
и кодом разбора не используется; шаблоны разбора живут в `src/docreader/structure.py`.
Обзор не обязан совпадать с разбором построчно.
