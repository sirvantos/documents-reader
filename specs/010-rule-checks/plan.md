## Summary

Группа подкоманд `docreader check …` (R-1). `check [ID…] [--all] [--again]` читает
`field_value` шести полей прототипа и проверяет их **правилами** — функциями в одном
реестре (`checks.py`, версия набора `CHECKS_VERSION`, R-2): сумма положительна, пропись
в скобках равна рублям (разбор русских числительных — `numwords.py`, R-3), сумма с НДС =
без НДС × (1 + ставка) до копейки (ставка из цитат, иначе `[checks] vat_rate`, R-4), дата
окончания в пределах `[checks]` (R-5), краткие наименования сторон различаются
(`values.same_value`), пять обязательных полей заполнены, значение приводится по виду.
Исход правила — «пройдено», «нарушено», «не применялось» с кодом причины без значений.
Статус поля выводится из исхода извлечения, исходов правил и решения аналитика по одной
таблице (R-6) и хранится с запуском извлечения, по которому вычислен; изменившееся
извлечение делает проверки договора устаревшими (R-7). Результаты — новые таблицы
`field_check`, `field_status`, решения — `field_decision`, отдельно от `field_value`
и от эталона (миграция `0008_checks`, R-8). `check queue` собирает локальную страницу
очереди кодом страницы проверки фичи 02 (`review_page`, `pageimage`), `check load` загружает
скачанные ответы (R-9). `check summary` — счёт статусов по полям; `check report` —
польза правил по эталону фичи 02, запись `eval_result` нового этапа `checks` со случаями
(R-10). Ловлю ошибок мерит синтетика: генератор договоров с внесёнными ошибками
и фиксированные ответы модели — `ScriptedModel` (R-11). Моделей фича не вызывает.

## Technical Context

**Language/Version**: Python 3.12 (tech-context: 3.11 или новее), окружение — `uv`

**Primary Dependencies**: новых библиотек нет: `decimal`, `json`, `re` (стандартная
библиотека), `psycopg[binary]` 3, `pypdfium2` (картинки страниц — `pageimage` фичи 02).
Приведение и сравнение значений — `values.py` (фичи 05 и 02), каталог — `catalog.py`.

**Storage**: PostgreSQL 17; миграция `0008_checks.sql` — `field_check`, `field_status`,
`field_decision`; новый этап `checks` в `eval_result.stage` и четыре исхода отчёта
в `eval_case.outcome` (данные — [data-model.md](data-model.md)). Таблицы фич 01–05 и 02
только читаются, кроме общих `run`, `stage_status`, `eval_result`, `eval_case`. Файлы — в папке
данных: `checks/queue-<сборка>/` (страница, `cards.json`, картинки), скачанные ответы,
разборы отчёта.

**Testing**: `pytest`, уровень 1 tech-context (модели не участвуют). Модульные —
числительные, каждое правило на значениях с дефектом и без, таблица статусов, решения
и «значение системы изменилось», порядок очереди, метрики отчёта, отсутствие значений
в выводе. Интеграционные — CLI на временной базе: синтетические договоры с внесёнными
ошибками → `extract` (`ScriptedModel`) → `check` → `check summary` → `check queue` →
ответы → `check load` → повторный `extract` с другим значением → `check` (пометка
изменения) → `check report` по синтетическому эталону. Уровень 3 не нужен.

**Target Platform**: рабочие прогоны — macOS, Apple M3 Pro, без сети; разработка
и автотесты — Ubuntu 24.04 x86_64 и Docker.

**Project Type**: CLI-приложение, один пакет (как в прежних фичах).

**Performance Goals**: `check --all` по 56 договорам < 60 с (SC-004; ожидаемо доли
секунды: 336 значений, правила — строковые и десятичные операции); страница очереди —
секунды.

**Constraints**: без сети; страница — один локальный HTML без внешних ссылок, как
у фичи 02; вывод в терминал — только числа, идентификаторы, названия полей, правил
и статусов (FR-013); значение системы никогда не перезаписывается решением (FR-008);
решения не пополняют эталон (уточнение 2026-11-27); проверки детерминированы (FR-005).

**Scale/Scope**: 56 договоров × 6 полей; 1 группа подкоманд (5 команд), 3 новых модуля
(`numwords`, `checks`, `check_queue`), 1 миграция, правки `config.py`, `stages.py`
(`RunStage.CHECKS`), `outcomes.py`, `evaluation.py`, `review_page.py`, `render.py`,
`cli.py`, генератор `tests/synthetic/make_pdfs.py`; `scripts/survey_rule_checks.py`
берёт разбор числительных из пакета.

Неясностей (NEEDS CLARIFICATION) нет: вопросы закрыты уточнениями 2026-11-27, решения
плана — в [research.md](research.md). Открыто то, что проверяется на ноутбуке: доля
верных значений в очереди на рабочем наборе (Б2, SC-003), время прохода очереди (Б3,
SC-007).

**Structure Decision**: один пакет `docreader`, как в фичах 01–09; группа `check`
рядом с `eval`. Модуль `rules.py` фичи 02 (извлечение правилами) не трогается: правила
проверок — в `checks.py`, чтобы не смешивать «найти значение» и «проверить значение».

## Модели для задач (CLAUDE.md, «Model routing»)

- **Opus сам**: миграция `0008_checks`; таблица статусов и правило устаревания (R-6, R-7);
  решения аналитика и «значение системы изменилось»; правила согласованности НДС и прописи
  (решающие правила); проверка «без значений в выводе».
- **Sonnet** (тесты пишет Opus заранее): `numwords`, остальные правила, сводка, страница
  очереди и разбор ответов, отчёт и запись `eval_result`, команды CLI с их аргументами
  и выводом (идут одной задачей с командой).
- **Haiku**: настройки `[checks]`, генератор синтетических договоров с ошибками.
