# Feature Specification: Проверки правилами и статусы полей

**Feature Branch**: `010-rule-checks`

**Created**: 2026-11-27

**Status**: Draft

**Input**: User description: "Фича 06 «Проверки правилами и статусы полей»
(docs/features/06-rule-checks-and-statuses.md), минимальная версия: только шесть полей
прототипа, которые сейчас извлекает фича 05 — contract_number, customer_name_short,
contractor_name_short, amount_without_vat, amount_with_vat, contract_end_date. Правила
для остальных полей каталога (ИНН, КПП, ОГРН, валюта, даты подписания и начала,
проценты, неустойки, парные поля) — в «Следующей итерации», вне объёма. В объёме:
проверки, применимые к шести полям (сумма цифрами = сумма прописью, сумма положительна,
сумма с НДС согласуется с суммой без НДС и ставкой, дата окончания в разумных пределах,
наименования сторон различаются, обязательные поля из шести заполнены, общие проверки
по виду значения); статус каждого поля («принято», «требует просмотра», «отклонено»,
«не найдено») с перечнем пройденных, нарушенных и не применявшихся правил; очередь
просмотра и сводка по статусам; решения аналитика (подтвердить, исправить, «в договоре
нет»), которые не теряются при повторном извлечении; отчёт о пользе правил по эталону
фичи 02 (39 договоров, 234 пары). Без моделей: правила — обычный код."

## Суть и назначение

Фича 05 извлекает шесть полей прототипа и подтверждает каждое значение цитатой: такие
слова в договоре есть. Цитата не доказывает, что значение взято из нужного места
и прочитано верно. Эта фича добавляет второй слой — проверки обычным кодом, без модели:
сумма прописью совпадает с суммой цифрами, сумма с НДС согласуется с суммой без НДС
и ставкой, у заказчика и подрядчика разные наименования. По итогам каждое поле каждого договора получает **статус** —
«принято», «требует просмотра», «отклонено» или «не найдено» — с перечнем проверок
и их исходов.

Значения, которым нельзя доверять без человека, собираются в **очередь просмотра**.
Аналитик проходит её, подтверждает значение, исправляет его или отмечает, что в
договоре его нет; решения хранятся рядом со значением системы и переживают повторное
извлечение. **Отчёт о пользе правил** по эталону фичи 02 показывает, сколько раз каждое
правило сработало и сколько из этих значений действительно неверны, — чтобы правила
не превратились в шум.

**Зачем.** Ошибки, которые видны без чтения договора, — неверно распознанная цифра
в сумме, взятая сумма не того вида, номер с подменённым знаком — сейчас находит только
ручная сверка всех значений. Статусы отделяют значения, которым можно доверять
в подсчётах, от тех, что ждут человека, и сокращают проверку 336 значений рабочего
набора (56 договоров × 6 полей) до короткой очереди. Механизм статусов, очереди
и решений нужен и следующим фичам: ответам по таблице (фича 10) и веб-экрану (фича 12).

**Пользователь.** Один аналитик на своём ноутбуке. Проверки он запускает из командной
строки, очередь проходит на локальной странице в браузере, как страницу проверки
эталона фичи 02.

**Что уже есть.** Шесть полей прототипа извлечены для 56 договоров (фича 05):
у каждого значения — состояние извлечения («найдено», «не найдено», «отклонено»
проверкой цитаты, «ошибка»), приведённое значение, цитата, пункт и страница. Эталон
фичи 02 — 39 договоров, 234 пары, извлечение на нём даёт 234 верных из 234 (замер
2026-11-27); правила извлечения фичи 02 (без модели) — 224 из 234.

## Clarifications

### Session 2026-11-27

Опрос `scripts/survey_rule_checks.py` (версия 1, 56 договоров рабочего набора): все шесть
полей найдены в 56 из 56; у всех 112 сумм пропись в скобках равна рублям, копейки прописью
не пишутся; ставка 20% написана в цитатах всех 56, сумма с НДС = без НДС × 1,2 точно до
копейки во всех 56, «не облагается» — 0; даты окончания 2025–2026, все в прошлом; краткие
наименования сторон различаются во всех 56; номер в колонтитулах — 2 из 56, на листе
подписи — 2 из 56.

- Q: Где стоит сумма прописью и как её сравнивать? → A: В скобках сразу после суммы
  цифрами; сравниваются рубли, копейки прописью не читаются; прописи нет — правило «не
  применялось» (решено по опросу и каталогу полей, «Правила проверки»: «только рубли для
  сумм»).
- Q: Какую ставку НДС брать и с каким допуском? → A: Ставку, написанную при суммах
  («НДС (20%)»); не написана — ставка по умолчанию из настроек, 20%. Сумма с НДС должна
  быть равна сумме без НДС × (1 + ставка), округлённой до копейки, без допуска; одна сумма
  из двух или «не облагается» — правило «не применялось» (решено по опросу и каталогу
  полей: «с округлением до копейки»).
- Q: Какие пределы у даты окончания? → A: Абсолютный диапазон в настройках, по умолчанию
  с 2015-01-01 по 2040-12-31; дата в прошлом нарушением не считается — договоры набора
  завершены (решено по опросу: все 56 в 2025–2026 и все в прошлом).
- Q: Как статусы сочетаются с исходами фичи 05? → A: «Отклонено» проверкой цитаты →
  «отклонено», правила не применяются; «ошибка» извлечения → «требует просмотра» с причиной
  извлечения; договор «требует просмотра» на чтении или разборе → пометка у его значений,
  статус по правилам; при нескольких нарушениях перечисляются все (решено по
  docs/features/06-rule-checks-and-statuses.md, «Особые случаи»).
- Q: Что из фичи можно показывать агенту? → A: Только вывод команд: числа, идентификаторы,
  названия полей, правил и статусов; страница очереди, файлы ответов и отчётов со
  значениями — никогда (решено по конституции, принцип I, и правилам фичи 02).
- Q: Какие из шести полей обязательны? → A: Пять: номер договора, оба кратких
  наименования, обе суммы; дата окончания необязательна.
- Q: Оставлять ли правило «номер в заголовке совпадает с колонтитулами и листом подписи»?
  → A: Отложить в «Следующую итерацию»: номер вне заголовка есть только в 2 договорах
  из 56, а номер на листе подписи стоит, по-видимому, строкой ниже слов «Номер договора».
- Q: В каком виде аналитик работает с очередью? → A: Локальная страница, как страница
  проверки эталона фичи 02: карточка с причиной, цитатой и изображением страницы,
  решения клавишами, ответы скачиваются файлом и загружаются командой.
- Q: Становится ли решение по очереди значением эталона фичи 02? → A: Нет: решения
  хранятся отдельно и исправляют данные; эталон не меняют и пополняются как прежде,
  страницей проверки фичи 02 (эталон из очереди, отобранной правилами, мерил бы сами
  правила).
- Q: На чём мерить пользу правил? → A: На обоих: отчёт по эталону фичи 02 на рабочем
  наборе (ложные срабатывания на верных значениях) и синтетические договоры с внесёнными
  ошибками (доля пойманных).
- Q: Что разрешено на карточке очереди без надёжного значения системы (отклонено проверкой
  цитаты, ошибка извлечения, обязательное поле не найдено)? → A: Только «исправить»,
  «в договоре нет» и «пропустить»; «подтвердить» — только у найденного значения, загрузка
  отклоняет его на остальных; отклонённая карточка показывает предложение модели
  с пометкой «цитата не подтверждена» (analyze U1, принцип III).
- Q: Устаревают ли проверки после изменения настроек `[checks]`? → A: Да: у статуса
  хранится отпечаток настроек `[checks]`, его смена — устаревание, как новое извлечение
  или новая версия правил (analyze U2).
- Q: Нужен ли в минимальной версии случай «каталог полей изменён»? → A: Нет, в «Следующую
  итерацию»: шесть полей закреплены в базе (analyze C4).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Проверить значения и присвоить статусы (Priority: P1)

Аналитик запускает проверки по извлечённым договорам. Каждое из шести полей каждого
договора получает ровно один статус и перечень проверок: какие пройдены, какие
нарушены (с названием правила и пояснением), какие не применялись и почему.

**Why this priority**: Без статусов нет ни очереди, ни отчёта; это основа фичи.

**Independent Test**: Запустить проверки на синтетических договорах с заранее
внесёнными дефектами (сумма прописью не равна цифрам, сумма с НДС не согласуется,
одинаковые стороны, дата вне пределов, пустое обязательное поле) и на договоре без
дефектов; сверить статусы и названия нарушенных правил с ожидаемыми.

**Acceptance Scenarios**:

1. **Given** извлечение выполнено, **When** аналитик запускает проверки, **Then**
   каждое из шести полей каждого договора получает ровно один статус и перечень
   проверок с исходом «пройдена», «нарушена» или «не применялась».
2. **Given** сумма цифрами и сумма прописью в том же месте договора расходятся,
   **When** выполняются проверки, **Then** поле суммы получает «требует просмотра»
   с названием правила.
3. **Given** сумма с НДС не равна сумме без НДС, увеличенной на ставку НДС (с
   округлением до копейки), **When** выполняются проверки, **Then** оба поля суммы
   получают «требует просмотра».
4. **Given** сумма не больше нуля, **When** выполняются проверки, **Then** поле
   получает «требует просмотра».
5. **Given** дата окончания вне разумных пределов, **When** выполняются проверки,
   **Then** поле даты получает «требует просмотра».
6. **Given** краткие наименования заказчика и подрядчика совпадают (по правилу
   сравнения наименований фичи 02), **When** выполняются проверки, **Then** оба поля
   получают «требует просмотра».
7. **Given** обязательное поле имеет результат «не найдено», **When** выполняются
   проверки, **Then** статус — «требует просмотра» с причиной «обязательное поле не
   заполнено»; дата окончания (необязательное поле) с результатом «не найдено» получает
   «не найдено».
8. **Given** значение прошло все применимые проверки, **When** выполняются проверки,
   **Then** статус — «принято».
9. **Given** значение отклонено проверкой цитаты фичи 05, **When** выполняются
    проверки, **Then** правила к нему не применяются и статус — «отклонено».
10. **Given** проверки уже выполнены и данные не менялись, **When** аналитик
    запускает их снова, **Then** статусы и перечни проверок те же.

### User Story 2 - Очередь просмотра и сводка (Priority: P1)

После проверок аналитик видит сводку по статусам и собирает очередь — значения со
статусом «требует просмотра» или «отклонено», самые важные первыми, — на локальной
странице, как страница проверки эталона фичи 02.

**Why this priority**: Очередь — то, ради чего аналитик запускает проверки: она
заменяет сверку всех значений.

**Independent Test**: После проверок на синтетических договорах собрать страницу очереди
и сводку; проверить состав и порядок карточек, их содержимое и числа сводки.

**Acceptance Scenarios**:

1. **Given** есть значения со статусом «требует просмотра» или «отклонено», **When**
   аналитик собирает очередь, **Then** страница в папке данных содержит по карточке на
   значение: договор, поле, значение системы, цитата, пункт, изображение страницы
   договора, статус и причины (все нарушенные правила).
2. **Given** очередь, **When** аналитик её читает, **Then** сначала идут обязательные
   поля (номер, наименования, суммы), затем дата окончания; внутри — по договору.
3. **Given** у договора состояние «требует просмотра» на чтении или разборе, **When**
   собирается очередь, **Then** его значения в очереди несут эту пометку.
4. **Given** проверки выполнены, **When** аналитик запрашивает сводку, **Then** он
   видит число значений в каждом статусе по каждому полю и в целом, и вывод команды
   содержит только числа, названия полей и правил и идентификаторы — без значений
   и цитат.

### User Story 3 - Решения аналитика (Priority: P2)

Аналитик на странице очереди принимает решение по каждой карточке — подтвердить,
исправить (вписать верное значение) или отметить, что в договоре значения нет, —
скачивает ответы файлом и загружает их командой. Решения хранятся отдельно от значения
системы и от эталона фичи 02 и сохраняются при повторном извлечении и проверках.

**Why this priority**: Без решений очередь не уменьшается; но статусы и очередь
полезны и без них (замер правил на эталоне).

**Independent Test**: Загрузить файл ответов страницы с решениями трёх видов по синтетическим
договорам, повторить извлечение (с изменённым значением системы для одного поля)
и проверки; убедиться, что решения на месте, а изменение видно.

**Acceptance Scenarios**:

1. **Given** найденное значение в очереди, **When** аналитик подтверждает его, **Then** статус —
   «принято» с отметкой «подтверждено человеком».
2. **Given** значение в очереди, **When** аналитик вписывает исправленное значение,
   **Then** оно приводится по виду поля (как в эталоне фичи 02), статус — «принято»
   с отметкой «исправлено человеком», а значение системы хранится рядом без изменений.
3. **Given** значение в очереди, **When** аналитик отмечает «в договоре нет», **Then**
   статус — «не найдено» с отметкой «подтверждено человеком».
4. **Given** вписанное значение не приводится по виду поля, **When** файл ответов
   загружается, **Then** это решение не принимается, система называет карточку (договор
   и поле, без значения), остальные решения файла принимаются.
5. **Given** решение принято, **When** извлечение и проверки запускаются заново,
   **Then** решение сохраняется; если новое значение системы отличается от того, по
   которому принималось решение, поле помечено «значение системы изменилось» и снова
   стоит в очереди.
6. **Given** решение принято, **When** аналитик смотрит эталон фичи 02, **Then** эталон
   не изменился: решения его не пополняют.

### User Story 4 - Польза правил по эталону (Priority: P2)

Аналитик запрашивает отчёт по правилам на договорах с эталоном фичи 02: сколько раз
каждое правило сработало, сколько из этих значений неверны по эталону, какая доля
неверных значений попала в очередь и какая доля верных попала в неё напрасно. Отчёт
записывается в таблицу результатов фичи 02.

**Why this priority**: Показывает, стоит ли правилам доверять, и подсказывает, какое
правило шумит; без него очередь нельзя оценить.

**Independent Test**: На синтетических договорах с эталоном, где часть значений
системы неверна, получить отчёт и сверить числа с подсчитанными вручную. Отдельно —
синтетические договоры с внесёнными ошибками каждого вида, на которые нацелено правило
(пропись не равна цифрам, суммы не согласуются со ставкой, сумма не больше нуля, дата вне
пределов, одинаковые стороны, пустое обязательное поле): доля пойманных по каждому правилу.

**Acceptance Scenarios**:

1. **Given** проверки выполнены и есть эталон, **When** аналитик запрашивает отчёт,
   **Then** для каждого правила видно число срабатываний и сколько из них пришлось на
   значения, неверные по эталону.
2. **Given** тот же отчёт, **When** аналитик смотрит итог, **Then** он видит долю
   неверных по эталону значений, попавших в очередь, и долю верных, попавших в неё
   напрасно, по каждому полю и в целом.
3. **Given** отчёт снят, **When** аналитик смотрит таблицу результатов фичи 02,
   **Then** там есть запись этого отчёта с версией правил и эталона, и каждую цифру
   можно раскрыть до случаев (договор, поле, правило, исход).
4. **Given** у поля есть решение аналитика, **When** снимается отчёт, **Then**
   сравнивается значение системы, а не решение аналитика.
5. **Given** синтетические договоры с внесёнными ошибками, **When** выполняются проверки,
   **Then** каждое правило ловит все внесённые для него ошибки, и на договоре без
   дефектов не срабатывает ни одно правило.

### Edge Cases

- Значение отклонено проверкой цитаты фичи 05: правила не применяются, статус
  «отклонено» сохраняется.
- Поле в состоянии «ошибка» (извлечение не выполнилось): статус «требует просмотра»
  с причиной из извлечения.
- Правило нельзя применить, потому что нужного значения нет (пропись не написана, одна
  из сумм не найдена): правило отмечается «не применялось» с причиной и на статус не
  влияет.
- Сумма прописью записана с копейками или с сокращениями («руб.», «коп.»): сравниваются
  только рубли (каталог полей; по опросу копейки прописью не пишутся).
- Сумма прописью относится к другой сумме того же пункта (например, к сумме НДС):
  сравнивается пропись, стоящая при сумме поля.
- Договор «НДС не облагается» или указана только одна сумма: правило согласованности
  сумм не применялось.
- Ставка НДС написана в тексте («НДС (20%)»): берётся она; не написана — ставка по
  умолчанию из настроек (20%).
- Дата окончания в прошлом: не нарушение (договоры набора завершены); нарушение — только
  выход за пределы из настроек.
- Нарушено несколько правил: в причине перечислены все.
- Договор получил состояние «требует просмотра» на чтении или разборе: его значения
  в очереди несут эту пометку (сами правила не меняются).
- Извлечение договора повторено после проверок: проверки этого договора устаревают
  и при следующем запуске выполняются заново; решения аналитика остаются.
- Решение относится к полю, которого больше нет в извлечении, или к договору,
  удалённому из реестра: решение не применяется, система называет число таких решений.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001.** Система должна присваивать каждому из шести полей прототипа каждого
  извлечённого договора ровно один статус: «принято», «требует просмотра»,
  «отклонено», «не найдено».
- **FR-002.** Система должна сохранять для каждого значения перечень правил с исходом
  «пройдено», «нарушено» или «не применялось» и коротким пояснением (без значений
  договора в пояснении, кроме страницы очереди).
- **FR-003.** Система должна выполнять правила минимальной версии:
  - сумма положительна (`amount_without_vat`, `amount_with_vat`);
  - сумма цифрами равна сумме прописью при ней, по рублям (обе суммы);
  - сумма с НДС равна сумме без НДС, увеличенной на ставку НДС, с округлением до
    копейки (обе суммы);
  - дата окончания в пределах из настроек, по умолчанию с 2015-01-01 по 2040-12-31
    (`contract_end_date`);
  - краткие наименования сторон различаются (`customer_name_short`,
    `contractor_name_short`);
  - обязательные поля заполнены: номер договора, оба кратких наименования, обе суммы;
  - значение приводится по виду поля (общая проверка вида).
  Пропись — слова в скобках сразу после суммы цифрами, сравниваются рубли; ставка НДС —
  написанная при суммах, иначе из настроек; совпадение сумм — до копейки, без допуска.
- **FR-004.** Значение, отклонённое проверкой цитаты фичи 05, правилами не проверяется
  и получает «отклонено»; поле в состоянии «ошибка» получает «требует просмотра».
- **FR-005.** Проверки не должны обращаться к языковой модели и должны давать
  одинаковый результат на одинаковых данных.
- **FR-006.** Система должна собирать очередь просмотра (значения «требует просмотра»
  и «отклонено») на локальной странице в папке данных, как страница проверки фичи 02:
  карточка с причинами, цитатой, пунктом и изображением страницы; порядок —
  обязательные поля, затем дата окончания; внутри — по договору.
- **FR-007.** Система должна показывать сводку: число значений в каждом статусе по
  каждому полю и в целом.
- **FR-008.** Система должна принимать файл ответов страницы очереди с решениями
  аналитика (подтвердить, исправить, «в договоре нет»), приводить исправленные значения
  по виду поля и хранить решения отдельно от значения системы и от эталона фичи 02
  (решения эталон не пополняют).
- **FR-009.** Система должна сохранять решения при повторном извлечении и проверках
  и помечать поле «значение системы изменилось», если значение системы стало другим,
  возвращая такое поле в очередь.
- **FR-010.** Система должна строить отчёт о пользе правил по эталону фичи 02 и
  записывать его в таблицу результатов фичи 02 с версией правил и эталона; в отчёте
  сравниваются значения системы, а не решения аналитика. Польза правил на ошибках
  проверяется также на синтетических договорах с внесёнными ошибками каждого вида.
- **FR-011.** Новое правило должно добавляться без изменения существующих; у набора
  правил есть версия, которая записывается в результаты проверок и в отчёт.
- **FR-012.** Пределы дат и ставка НДС по умолчанию задаются в настройках.
- **FR-013.** Терминальный вывод команд фичи содержит только числа, идентификаторы,
  названия полей, правил и статусов; значения договоров, цитаты и текст — только
  в файлах в папке данных (конституция, принцип I).
- **FR-014.** Проверки договора устаревают, когда меняется его извлечение, и при
  следующем запуске выполняются заново; без изменений повторный запуск их не
  пересчитывает, если не задан явный пересчёт.

### Key Entities

- **Правило.** Название, версия набора правил, поля, к которым применяется, исход при
  нарушении (сейчас всегда «требует просмотра»).
- **Результат проверки.** Договор, поле, правило, исход («пройдено», «нарушено», «не
  применялось»), пояснение; относится к конкретному извлечению.
- **Статус поля.** Договор, поле, статус, причины (нарушенные правила или причина
  извлечения), пометки (договор «требует просмотра», «значение системы изменилось»,
  «подтверждено человеком», «исправлено человеком»).
- **Решение аналитика.** Договор, поле, вид решения (подтвердить, исправить, «в
  договоре нет»), исправленное значение и его приведённая форма, значение системы, по
  которому принималось решение, дата. Хранится отдельно от эталона фичи 02.
- **Отчёт о пользе правил.** Запись таблицы результатов фичи 02: по правилу — число
  срабатываний и неверных по эталону; по полю и в целом — доля неверных в очереди
  и доля верных в очереди; случаи.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001.** 100% из шести полей каждого извлечённого договора имеют ровно один
  статус.
- **SC-002.** На синтетических договорах с внесёнными ошибками каждое правило ловит
  100% внесённых для него ошибок и не срабатывает на договоре без дефектов.
- **SC-003.** Не более 20% значений, верных по эталону фичи 02, попадают в очередь
  просмотра (ориентир; записывается, не подгоняется). Долю неверных по эталону
  значений в очереди отчёт записывает; ориентира для неё на рабочем наборе нет, пока
  извлечение даёт 234 верных из 234 на эталоне (ловлю ошибок мерит SC-002).
- **SC-004.** Проверки 56 договоров рабочего набора выполняются меньше чем за минуту.
- **SC-005.** Повторный запуск на тех же данных даёт те же статусы и перечни проверок.
- **SC-006.** Решения аналитика сохраняются после повторного извлечения в 100%
  случаев; каждое изменившееся значение системы помечено.
- **SC-007.** Очередь рабочего набора аналитик проходит на странице без открытия PDF
  там, где правило назвало причину, а цитата и изображение страницы показаны (ориентир;
  время записывает аналитик).

## Вне рамок

- Правила для полей, которых фича 05 пока не извлекает (ИНН, КПП, ОГРН, счета, валюта,
  даты подписания и начала, проценты, неустойки, парные поля, суммы по годам) —
  «Следующая итерация».
- Проверка значений по внешним справочникам (реестр юридических лиц и подобные).
- Проверки с помощью языковой модели.
- Общий веб-экран (фича 12); здесь — только локальная страница очереди, как в фиче 02.
- Юридическая оценка условий.
- Действующее значение для фич 07 и 10 (решение аналитика, если есть, иначе значение
  системы со статусом «принято»): определяется здесь, а используется в этих фичах —
  их доработка вне объёма.

## Следующая итерация

- Правила каталога для полей очереди 1 по мере их извлечения: контрольные разряды ИНН
  и ОГРН, длина КПП, ИНН сторон различаются, валюта из списка, порядок дат (подписание ≤
  конец работ ≤ конец действия), даты доверенностей и основания, проценты 0–100 и их
  пропись, сумма НДС, суммы по годам, неустойка не выше предела, парные поля.
- Номер в заголовке совпадает с номером в колонтитулах и на листе электронной подписи
  (каталог полей; опрос: номер вне заголовка есть только в 2 из 56, на листе подписи он,
  по-видимому, строкой ниже «Номер договора» — сначала научиться его читать).
- Решения аналитика на веб-экране (фича 12).
- Каталог полей изменён: проверки для удалённых полей не выполняются, новые поля получают
  общие проверки по виду (нужно, когда полей станет больше шести).
- Использование действующего значения в индексах (фича 07) и ответах по таблице
  (фича 10).

## Assumptions

- Суммы прописью записаны по-русски, в скобках при сумме цифрами (опрос: у всех 112 сумм).
- Суммы в рублях; ставка НДС, если не написана в тексте, — 20% (настройка).
- У договора две стороны, «Заказчик» и «Подрядчик».
- Страница очереди, файлы ответов и отчётов — в папке данных; агенту не отправляются.
- Сравнение наименований и приведение значений — общие правила фичи 02 (правило
  сравнения наименований, приведение по виду поля).
