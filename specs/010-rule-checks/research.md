# Research: Проверки правилами и статусы полей

Решения плана фичи 06 (минимальная версия, шесть полей прототипа). Числа рабочего набора —
опрос `scripts/survey_rule_checks.py` v1 (2026-11-27, 56 договоров).

## R-1. Команды

**Decision.** Группа `docreader check …` (contracts/cli.md): `check [ID…] [--all]
[--again]` — проверки и статусы; `check summary [--json]` — счёт статусов; `check queue
[ID…] [--out ПАПКА]` — страница очереди; `check load ФАЙЛ` — ответы страницы; `check
report [--label]` — польза правил по эталону фичи 02. Без `ID` и `--all` `check` берёт
договоры с извлечением, у которых проверок нет или они устарели (R-7); `--again`
пересчитывает и неустаревшие.

**Rationale.** Как `eval …` фичи 02: одна группа, вывод только числами.

**Alternatives.** Проверки внутри `extract` — отвергнуто: этапы независимы (принцип VI),
и правила меняются чаще извлечения.

## R-2. Реестр правил

**Decision.** `checks.py`: `Rule(code, fields, fn)`; `RULES` — кортеж в порядке
применения; `CHECKS_VERSION = "06.1"` меняется при любой правке правила или таблицы
статусов. Функция правила получает `DocFields` (шесть строк `field_value` договора и его
текст) и возвращает по исходу на каждое своё поле: `passed`, `violated`, `not_applied`
с кодом причины. Коды и названия по-русски — в `render.py`, значения в них не входят.
Правила минимальной версии:

| Код правила | Поля | Нарушение | Не применялось |
|---|---|---|---|
| `amount_positive` | обе суммы | значение ≤ 0 | значения нет |
| `amount_words` | обе суммы | пропись в скобках не равна рублям (`words_differ`) или не читается (`words_unreadable`) | прописи нет (`no_words`) |
| `vat_consistent` | обе суммы | с НДС ≠ без НДС × (1 + ставка), округление до копейки (`vat_mismatch`) | одной из сумм нет (`one_amount`); «не облагается» в тексте (`exempt`) |
| `end_date_range` | дата окончания | вне `[checks] end_date_min … end_date_max` (`date_out_of_range`) | значения нет |
| `parties_differ` | оба наименования | `values.same_value` — одно и то же (`same_parties`) | одного из двух нет |
| `required` | номер, оба наименования, обе суммы | результат извлечения `not_found` (`required_missing`) | — |
| `kind_valid` | все шесть | приведённое значение не проходит `values.normalize_field` своего вида (`kind_invalid`) | значения нет |

**Rationale.** FR-011: правило добавляется строкой в кортеж; таблица — один источник
для документации и тестов.

**Alternatives.** Правила в настройках или DSL — отвергнуто (принцип VIII).

## R-3. Сумма прописью

**Decision.** `numwords.words_to_int(text) -> int | None`: единицы, десятки, сотни,
«тысяч*», «миллион*», «миллиард*», «одна/две»; чтение останавливается на «руб*» или
«коп*» (дальше — копейки); незнакомое слово → `None`. Пропись поля — первая скобка
в `value_text` без цифр, иначе скобка, начинающаяся в первых трёх знаках после значения
в тексте (поиск `value_text` в цитате, как в опросе). Сравниваются целые рубли.

**Rationale.** Опрос: у всех 112 сумм пропись в скобках, равна рублям, копейки прописью
не пишутся; каталог — «только рубли для сумм». Функция и её тесты переносятся из опроса
в пакет; опрос импортирует её из пакета.

**Alternatives.** `num2words` (обратное направление), `text2num` (нет русского) —
отвергнуто.

## R-4. Ставка НДС

**Decision.** Ставка — первое «НДС … N%» в цитатах двух сумм
(`НДС\W{0,3}(\d{1,2}([.,]\d+)?)\s*%`); нет — `[checks] vat_rate` (по умолчанию 20).
Ожидаемая сумма с НДС — `Decimal` без НДС × (1 + ставка/100), `quantize(0.01,
ROUND_HALF_UP)`; равенство без допуска. «Не облагается» в тексте договора — правило
не применялось у обеих сумм.

**Rationale.** Опрос: ставка 20% написана во всех 56, совпадение точно до копейки
во всех 56; каталог: «с округлением до копейки».

## R-5. Пределы даты окончания

**Decision.** `[checks] end_date_min = "2015-01-01"`, `end_date_max = "2040-12-31"`;
дата в прошлом — не нарушение.

**Rationale.** Уточнение 2026-11-27 по опросу (все 56 в 2025–2026, все в прошлом).

## R-6. Статус поля

**Decision.** Одна функция `field_status(extraction, outcomes, decision) -> Status` по
таблице (сверху вниз, первая подходящая строка):

| # | Условие | Статус | Причины / пометки |
|---|---|---|---|
| 1 | есть решение, значение системы с момента решения не менялось | «подтвердить»/«исправить» → «принято», «в договоре нет» → «не найдено» | `human_confirmed` / `human_corrected` / `human_absent` |
| 2 | есть решение, значение системы изменилось | «требует просмотра» | `system_changed`; решение хранится и показывается на карточке |
| 3 | извлечение `rejected` | «отклонено» | причина извлечения; правила не применялись |
| 4 | извлечение `failed` | «требует просмотра» | причина извлечения |
| 5 | хотя бы одно правило `violated` | «требует просмотра» | все нарушенные правила |
| 6 | извлечение `not_found` | «не найдено» (дата окончания) | — (обязательные поля попадают в строку 5 через `required`) |
| 7 | иначе | «принято» | — |

Пометка `document_needs_review` ставится, когда `stage_status` чтения или разбора
договора — `needs_review`; на статус не влияет. «Значение системы» для решения —
пара `(result, value_normalized)` строки `field_value`.

**Rationale.** Уточнения 2026-11-27 и особые случаи файла фичи; «отклонено» не
переписывается правилами (принцип III); решение аналитика сильнее правил, но не
переживает изменения значения системы молча (FR-009).

## R-7. Устаревание

**Decision.** `field_status.extraction_run_id` = `field_value.run_id`, по которому
вычислен статус, и `checks_version`. Проверки договора устарели, если хоть у одного поля
запуск извлечения или версия правил другие, либо статуса нет. `check` без `--again`
берёт только такие договоры; `stage_status` этапа `checks` — `done` или `needs_review`
(есть статус «требует просмотра» или «отклонено»), причина — число таких полей.
Устаревший договор `summary` и `queue` считают как «проверки устарели» и его статусы
не показывают.

**Rationale.** Извлечение не сбрасывает следующие этапы; сравнение запуска не требует
правок фичи 05 (отступление 4 плана).

## R-8. Хранение и действующее значение

**Decision.** Миграция `0008_checks.sql` (data-model.md): `field_check` (исход каждого
правила), `field_status` (статус, причины, пометки, запуск извлечения, версия правил,
запуск проверок), `field_decision` (решение аналитика со значением системы на момент
решения; одна строка на «документ, поле», новая загрузка заменяет).
`checks.effective_value(conn, doc, field)` — значение решения «исправить» или значение
системы при решении «подтвердить», если статус по строке 1 R-6; иначе значение системы
при статусе «принято»; иначе нет значения.

**Rationale.** Отступление 1 плана; решения отдельно от эталона (уточнение 2026-11-27).

## R-9. Страница очереди и ответы

**Decision.** `check queue` пишет `checks/queue-<сборка>/` в папке данных: `cards.json`
(формат `docreader-check-cards/1`), `index.html` (код `review_page.render_html` с форматом
ответов параметром `docreader-check-review/1`), картинки страниц (`pageimage`, как
в фиче 02). Карточка — договор, поле, статус, коды причин, значение системы, цитата,
пункт, картинка, пометки, прежнее решение. Ответы — `agree` (подтвердить), `typed`
(исправить: значение, необязательный пункт), `absent`, `skip`; файл скачивается
страницей и загружается `check load`: значение приводится по виду поля, ошибка вида —
карточка не принимается (называются договор и поле). Порядок карточек: пять обязательных
полей, затем дата окончания; внутри поля — по договору; карточки с `system_changed`
первыми в своём поле.

**Rationale.** Уточнение 2026-11-27 («страница как в 02»); переиспользуется готовый код.

## R-10. Сводка и отчёт о пользе правил

**Decision.** `check summary` — счёт статусов по полям и в целом, плюс число договоров
с устаревшими проверками. `check report [--label]` — по договорам с эталоном фичи 02
и неустаревшими проверками: значение системы «верно / неверно» по
`outcomes.field_outcome` (верно — `correct`; неверно — `wrong`, `missed`, `invented`;
`not_labeled` — вне отчёта); «в очереди» — статус «требует просмотра» или «отклонено»
**без учёта решений** (FR-010), то есть по строкам 3–7 таблицы R-6. Метрики: по правилу —
`fired`, `fired_on_wrong`; по полю и в целом — `wrong_in_queue / wrong`, `right_in_queue /
right` (SC-003). Запись `eval_result` этапа `checks` с `provenance` (версия правил,
запуски извлечения и проверок, настройки `[checks]`), версией эталона и случаями
`eval_case` (документ/поле, исход `queued_wrong`, `queued_right`, `accepted_wrong`,
`accepted_right`, сработавшие правила во флагах). `eval show`, `compare`, `export`
фичи 02 работают с ней без изменений.

**Rationale.** FR-010; таблица результатов — одна на проект.

## R-11. Синтетика с внесёнными ошибками

**Decision.** `make_check_contracts(directory)` в `tests/synthetic/make_pdfs.py`: договор
без дефектов и по договору на каждую ошибку — пропись ≠ цифры, суммы не согласуются
со ставкой, ставка 10% написана и соблюдена (не нарушение), «не облагается» с одной
суммой, дата окончания вне пределов, одинаковые стороны, пустая сумма (обязательное
поле). Ответы модели — `ScriptedModel` с фиксированными ответами на каждый договор
(уровень 1). SC-002 — каждое правило ловит все свои случаи и молчит на договоре без
дефектов; синтетический эталон для `check report` — загрузка шаблона фичи 02 в тесте.

**Rationale.** Уточнение 2026-11-27 («оба замера»): на рабочем наборе извлечение даёт
234/234, правила там меряют только ложные срабатывания.
