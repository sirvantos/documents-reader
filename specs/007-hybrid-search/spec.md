## Суть и назначение

По запросу аналитика система возвращает упорядоченный список отрывков договоров
(фича 07). Поиск идёт двумя способами одновременно: по словам (с учётом русских
словоформ) и по смыслу (вектор запроса рядом с векторами отрывков). Два списка
кандидатов сливаются в один по местам в каждом списке. Затем реранкер — небольшая
локальная модель, которая читает запрос и каждого кандидата вместе, — ставит каждому
оценку соответствия и пересортировывает список. Поиск можно ограничить одним
договором по его идентификатору.

**Зачем.** Ответ по тексту (фича 09) не может быть лучше найденных отрывков: если
нужный пункт не найден, модель откажется отвечать или ответит по неподходящему
тексту. Поиск по словам точно находит номера и термины, поиск по смыслу — то же
условие другими словами; по отдельности каждый пропускает своё. Реранкер исправляет
порядок среди похожих кандидатов. Поиск в одном договоре нужен, потому что вопрос
обычно задаётся про конкретный договор, а типовые пункты однотипных договоров иначе
заполняют весь список (запрос аналитика 2026-11-24 по индексу по смыслу: 9 из 10
результатов — один и тот же пункт разных договоров).

**Пользователь.** Один аналитик. Он ищет из командной строки и запускает замер
на ноутбуке. Этой же функцией поиска пользуется фича 09.

**Решение аналитика 2026-11-24.** Реранкер входит в минимальную версию и включён
по умолчанию; оставить ли его включённым, решает замер этой фичи (время поиска
и место правильного пункта с реранкером и без него).

## Clarifications

### Session 2026-11-24

- Q: На каких вопросах замерять реранкер, пока нет эталонного набора (фича 02)? → A: 15–20 вопросов аналитика, каждый про один договор: у вопроса обязательны идентификатор договора и правильный пункт (`D-0015/2.2.1`), поиск в замере идёт внутри этого договора, как в прототипе. Набор хранится в папке данных вне репозитория и потом может войти в эталон фичи 02. Решено аналитиком.
- Q: Нужно ли в минимальной версии ограничивать число результатов от одного договора при поиске по всем договорам сразу? → A: Нет, отложить в «Следующую итерацию» и оставить об этом пометку в документации: при поиске без ограничения договором копии типового пункта из разных договоров могут занять весь список (запрос аналитика 2026-11-24: 9 из 10); в прототипе это снимает поиск в одном договоре. Решено аналитиком.
- Q: По какому правилу решать после замера, остаётся ли реранкер включённым по умолчанию? → A: Реранкер остаётся включённым, если с ним доля вопросов с правильным пунктом в первых пяти выше, чем без него; при равных долях — если выше доля «на первом месте»; и в обоих случаях медиана времени поиска с реранкером не больше 10 секунд. Иначе он выключается по умолчанию (и остаётся доступным настройкой). Решено аналитиком; согласуется с конституцией, принцип V.
- Q: Что должно быть в выводе замера, кроме мест и времени? → A: Чем получен результат: модель поиска по смыслу, модель реранкера и настройки поиска (числа кандидатов и результатов). Решено по: конституция, принцип VI («вместе с каждым результатом сохраняется, чем он получен»).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Найти отрывки по запросу (Priority: P1)

Аналитик вводит запрос на русском языке. Система ищет кандидатов по словам и по
смыслу, сливает два списка и возвращает первые результаты: договор, идентификатор
пункта, заголовок раздела, текст отрывка, страницы и места кандидата в каждом
способе поиска.

**Why this priority**: Это и есть поиск: без него фича 09 не получит отрывков
и прототип не ответит на вопрос.

**Independent Test**: Построить индексы синтетических договоров с поддельной моделью
векторов, выполнить поиск с выключенным реранкером и проверить состав и порядок
результатов по известным правилам слияния.

**Acceptance Scenarios**:

1. **Given** индексы построены, **When** аналитик вводит запрос, **Then** он получает
   упорядоченный список отрывков: договор, идентификатор пункта (`D-0001/5.2`),
   заголовок раздела, текст, первая и последняя страница.
2. **Given** запрос содержит точный номер договора или пункта («ДП-17/2026»),
   **When** выполняется поиск, **Then** отрывки с этим номером находятся среди
   первых результатов за счёт поиска по словам.
3. **Given** запрос сформулирован другими словами, чем пункт договора, **When**
   выполняется поиск, **Then** пункт находится за счёт поиска по смыслу.
4. **Given** слово запроса стоит в другой форме, чем в договоре («неустойки»
   и «неустойка»), **When** выполняется поиск по словам, **Then** пункт находится.
5. **Given** отрывок найден обоими способами, **When** списки сливаются, **Then** он
   стоит выше отрывка, найденного на тех же местах только одним способом, и в выводе
   видны его места в поиске по словам, в поиске по смыслу и после слияния.
6. **Given** те же индексы, настройки и запрос, **When** поиск выполняется повторно,
   **Then** список и порядок результатов те же.

---

### User Story 2 - Искать в одном договоре (Priority: P1)

Аналитик указывает идентификатор договора вместе с запросом. Поиск обоими способами,
слияние и реранкер работают только с отрывками этого договора.

**Why this priority**: Вопрос в прототипе задаётся про конкретный договор; без
ограничения однотипные договоры вытесняют нужный пункт из первых результатов.

**Independent Test**: На трёх синтетических договорах с одинаковым типовым пунктом
выполнить один запрос без ограничения и с ограничением одним договором и сравнить
списки.

**Acceptance Scenarios**:

1. **Given** запрос с идентификатором договора, **When** выполняется поиск, **Then**
   все результаты принадлежат этому договору.
2. **Given** идентификатор договора, которого нет в реестре, **When** выполняется
   поиск, **Then** система сообщает, что такого договора нет, и не ищет по всем
   договорам.
3. **Given** договор есть в реестре, но его отрывков нет в индексах (нарезка не
   выполнена или завершилась ошибкой), **When** выполняется поиск в нём, **Then**
   система сообщает об этом с подсказкой «выполните docreader index D-…»
   и не снимает ограничение сама.

### User Story 3 - Пересортировать кандидатов реранкером (Priority: P1)

После слияния реранкер оценивает каждого кандидата вместе с запросом
и пересортировывает список; в результат попадают первые по его оценке. Реранкер
включён по умолчанию и выключается настройкой запуска.

**Why this priority**: Решение аналитика 2026-11-24: реранкер входит в прототип
и включён по умолчанию; нужен замер, чтобы решить, оставить ли его.

**Independent Test**: С поддельным реранкером, который ставит заранее известные
оценки, выполнить один запрос с реранкером и без и сравнить порядок.

**Acceptance Scenarios**:

1. **Given** реранкер включён, **When** выполняется поиск, **Then** кандидаты
   пересортированы по его оценке, а у каждого результата видны оценка реранкера,
   место до пересортировки (после слияния) и место после.
2. **Given** реранкер выключен настройкой запуска, **When** выполняется поиск,
   **Then** порядок — порядок слияния, к модели реранкера система не обращается
   и её запуск не нужен.
3. **Given** реранкер включён, а его модель не запущена, не отвечает или запрещена
   на этой машине, **When** выполняется поиск, **Then** поиск останавливается
   с сообщением об окружении и подсказкой (запустить модель или выключить реранкер)
   и не выдаёт результат без пересортировки.
4. **Given** реранкер ответил ошибкой или не по форме (число оценок не равно числу
   кандидатов), **When** выполняется поиск, **Then** поиск останавливается
   с причиной и не выдаёт частично пересортированный список.

### User Story 4 - Замерить реранкер на вопросах аналитика (Priority: P2)

Аналитик готовит на ноутбуке набор из 15–20 вопросов, каждый про один договор
и с известным правильным пунктом, и запускает замер: каждый вопрос ищется в своём
договоре дважды, с реранкером и без него (уточнение 2026-11-24).
Замер печатает только числа — место правильного пункта в каждом варианте и время
поиска — и итог по набору с выводом по заранее заданному правилу: оставить
реранкер включённым по умолчанию или выключить. Решение записывается
в docs/tech-context.md.

**Why this priority**: Нужен для решения о реранкере, но поиск работает и без него.

**Independent Test**: На синтетических договорах с поддельными моделями и тестовым
набором из трёх вопросов замер печатает ожидаемые места и итог, без текста
вопросов и договоров.

**Acceptance Scenarios**:

1. **Given** набор вопросов, у каждого — идентификатор договора и идентификатор
   правильного пункта этого договора, **When** аналитик запускает замер, **Then**
   для каждого вопроса выводятся его порядковый номер, место правильного пункта без
   реранкера и с реранкером (или «не найден в первых N») и время поиска в каждом
   варианте.
2. **Given** замер выполнен, **When** аналитик смотрит итог, **Then** он видит для
   каждого варианта долю вопросов с правильным пунктом на первом месте и в первых
   пяти, медиану и наибольшее время поиска, модели и настройки поиска, которыми
   получен результат, и вывод по правилу: реранкер остаётся включённым, если с ним
   доля «в первых пяти» выше, а при равных долях — если выше доля «на первом месте»,
   и медиана времени с реранкером не больше 10 секунд; иначе выключается
   по умолчанию.
3. **Given** вопрос набора без идентификатора договора или со ссылкой на пункт,
   которого нет в индексах, **When** запускается
   замер, **Then** вопрос помечается как ошибочный в наборе и не учитывается в итоге,
   остальные вопросы обрабатываются.
4. **Given** вывод замера, **When** аналитик пересылает его агенту, **Then** в нём
   нет текста вопросов и договоров: только номера вопросов, идентификаторы пунктов,
   места, время и доли.

### Edge Cases

- **Запрос из одного слова или одного номера.** Поиск выполняется как обычно.
- **Запрос только из служебных слов** («и в на по»): поиск по словам не даёт
  кандидатов; поиск по смыслу выполняется, список строится по нему, а в выводе
  видно, что поиск по словам ничего не нашёл.
- **Пустой запрос** (пустая строка или только пробелы): отказ с понятной причиной
  до обращения к моделям.
- **Очень длинный запрос** (абзац текста): если запрос длиннее предела модели поиска
  по смыслу или реранкера, вектор и оценки строятся по части, которая помещается,
  и вывод предупреждает об обрезке.
- **Опечатка в запросе.** Поиск по словам может не найти пункт, поиск по смыслу —
  найти; места по каждому способу видны в выводе.
- **Латинские буквы, похожие на русские, в номерах** («C», «O»): запрос
  обрабатывается тем же способом, что текст при построении индекса по словам;
  приведение двойников к одному виду в индексе и запросе — «Следующая итерация».
- **Кандидатов меньше, чем просят результатов**: возвращаются все найденные
  кандидаты.
- **Ничего не найдено** ни одним способом: пустой результат с пояснением.
- **Типовой пункт в десятках договоров** при поиске без ограничения договором:
  результаты — разные отрывки, различимые по договору и метке, и копии пункта могут
  занять весь список (запрос аналитика 2026-11-24: 9 из 10). В прототипе это снимает
  поиск в одном договоре; ограничение числа результатов от одного договора —
  «Следующая итерация» (уточнение 2026-11-24).
- **Индексы устарели.** Если у части договоров отрывки получены по прежнему разбору
  или этап нарезки не в состоянии «готово» или «требует просмотра», поиск выполняется
  по тому, что есть, и предупреждает: сколько договоров не проиндексировано или
  устарело, с подсказкой команды.
- **Индекс по смыслу построен другой моделью**, чем выбрана для запроса (нет векторов
  выбранной модели): отказ с понятной причиной, без поиска.
- **Индексы пусты** (ни одного отрывка): отказ с подсказкой «выполните docreader index».
- **Модель поиска по смыслу недоступна или запрещена на этой машине**: поиск
  останавливается с сообщением об окружении (поиск без смысловой части в минимальной
  версии не выполняется).
- **Одинаковые оценки** у нескольких кандидатов: порядок между ними задаётся
  постоянным правилом (договор, затем порядок пункта в договоре), чтобы повторный
  поиск давал тот же список.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001.** Система должна выполнять поиск по словам по индексу фичи 07: запрос
  приводится к словарным формам тем же способом, что текст отрывков при построении
  индекса; слова с цифрами (номера договоров и пунктов) не приводятся.
- **FR-002.** Система должна выполнять поиск по смыслу: вектор запроса строится той же
  локальной моделью, которой построен индекс по смыслу, и сравнивается с векторами
  отрывков; векторы другой модели не используются.
- **FR-003.** Система должна сливать списки кандидатов двух способов в один по местам
  кандидата в каждом списке; число кандидатов от каждого способа — настройка.
- **FR-004.** Система должна по умолчанию пересортировывать слитый список реранкером
  и выключать реранкер настройкой запуска. С выключенным реранкером система к нему
  не обращается.
- **FR-005.** Если реранкер включён, а его модель недоступна, запрещена на этой машине,
  отвечает ошибкой или не по форме, поиск должен остановиться с причиной и не выдавать
  результат без пересортировки или частично пересортированный.
- **FR-006.** Система должна ограничивать поиск одним договором по его идентификатору;
  ограничение применяется до отбора кандидатов в обоих способах и никогда не снимается
  самостоятельно.
- **FR-007.** Система должна возвращать для каждого результата договор, идентификатор
  пункта, заголовок раздела, текст отрывка, первую и последнюю страницу, место
  в поиске по словам, место в поиске по смыслу (или «не найден этим способом»), место
  после слияния и, если реранкер включён, его оценку и место после пересортировки.
  Число результатов — настройка.
- **FR-008.** Поиск должен выполняться локально: к модели поиска по смыслу
  и к реранкеру система обращается только по адресам на этой машине; при одинаковых
  индексах, настройках и запросе результат тот же.
- **FR-009.** Если модель поиска по смыслу или включённый реранкер недоступны или
  модели запрещены на этой машине, поиск должен остановиться с сообщением об окружении
  до выдачи результата; доступность обеих моделей проверяется до начала поиска.
- **FR-010.** Система должна предупреждать, если часть договоров не проиндексирована
  или их отрывки получены по прежнему разбору, и называть число таких договоров
  и команду для исправления; при поиске в одном договоре без отрывков — отказывать
  (история 2, сценарий 3).
- **FR-011.** Поиск должен быть доступен из командной строки и как функция для фичи 09
  с теми же настройками и тем же результатом.
- **FR-012.** Система должна давать замер реранкера (история 4): набор вопросов
  аналитика, у каждого — идентификатор договора и идентификатор правильного пункта;
  поиск идёт внутри договора вопроса; для каждого вопроса — место правильного пункта
  и время поиска с реранкером и без него; итог — доли «на первом месте» и «в первых
  пяти», медиана и наибольшее время по каждому варианту, модели и настройки поиска
  и вывод по правилу FR-014. Вывод замера не содержит текста вопросов и договоров.
- **FR-013.** Вывод поиска показывает текст договоров; на реальных договорах его
  не присылают агенту (принцип I). Сообщения об ошибках и предупреждения поиска
  не содержат текста договоров.
- **FR-014.** Правило решения о реранкере (уточнение 2026-11-24): он остаётся
  включённым по умолчанию, если в замере доля вопросов с правильным пунктом в первых
  пяти с ним выше, чем без него, а при равных долях — если выше доля «на первом
  месте»; в обоих случаях медиана времени поиска с реранкером не больше 10 секунд.
  Иначе реранкер выключается по умолчанию и остаётся доступным настройкой запуска.

### Key Entities *(include if feature involves data)*

- **Запрос.** Текст, необязательный идентификатор договора, настройка поиска.
- **Настройка поиска.** Число кандидатов от каждого способа, число результатов,
  включён ли реранкер, модель поиска по смыслу.
- **Кандидат.** Отрывок и его места в поиске по словам, в поиске по смыслу и после
  слияния.
- **Результат.** Кандидат в итоговом порядке с оценкой реранкера и местом после
  пересортировки (если реранкер включён).
- **Вопрос замера.** Порядковый номер, текст вопроса, идентификатор договора,
  идентификатор правильного пункта этого договора. Набор (15–20 вопросов) хранится
  у аналитика в папке данных вне репозитория.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001.** На синтетических договорах из тестового набора (с поддельными моделями
  векторов и реранкера) 100% подготовленных случаев дают ожидаемые результаты:
  точный номер находится по словам, перефразированный пункт — по смыслу, словоформы
  совпадают, порядок слияния и пересортировки совпадает с расчётным.
- **SC-002.** 100% результатов поиска с ограничением договором принадлежат этому
  договору (автотесты и замер на ноутбуке).
- **SC-003.** Поиск по набору из 56 договоров на ноутбуке аналитика отвечает
  не более чем за 3 секунды без реранкера и не более чем за 10 секунд с реранкером
  (медиана по вопросам замера). Целевой ориентир из файла фичи.
- **SC-004.** Повторный поиск с теми же индексами, настройками и запросом даёт тот же
  список в том же порядке (100% вопросов замера и автотестов).
- **SC-005.** Замер реранкера выполнен на ноутбуке на всех вопросах набора аналитика
  в обоих вариантах; доли «на первом месте» и «в первых пяти» и время записаны
  в docs/tech-context.md вместе с решением по правилу FR-014, оставить ли реранкер
  включённым.
  Ориентир файла фичи — правильный пункт в первых пяти для не менее 85% вопросов —
  проверяется на эталонном наборе фичи 02; на вопросах аналитика он только
  записывается.

## Следующая итерация

Вне рамок этой спецификации; отдельная спецификация после того, как сквозной
прототип ответит на вопрос (CLAUDE.md, «Delivery»):

- Фильтры по полям договора: сторона, период дат и другие поля из перечня
  полей-фильтров; «по фильтру ничего нет», неизвестное поле (сценарий 3, критерии 2–4;
  FR-005 и SC-004 файла фичи).
- Прогон эталонных вопросов фичи 02 с заданной настройкой и меткой и запись
  в таблицу результатов; четыре варианта — по словам, по смыслу, слияние, слияние
  с реранкером (сценарий 2; FR-006, FR-008, SC-001, SC-002 файла фичи).
- Включение и выключение каждого способа поиска отдельно (только по словам, только
  по смыслу) — для сравнения вариантов на эталоне.
- Пояснение результата и расширенный контекст: весь раздел найденного отрывка
  (сценарий 5, FR-009 файла фичи).
- Ограничение числа результатов от одного договора при поиске без ограничения
  договором (FR-010 файла фичи) и, возможно, склейка одинаковых типовых пунктов
  разных договоров: до этого копии пункта могут занять весь список (уточнение
  2026-11-24).
- Приведение латинских букв-двойников в номерах к одному виду в индексе и в запросе.
- Поиск по куску номера (уточнение фичи 07, U1) — если замер покажет, что он нужен.
- Приставка запроса `search_query:` для FRIDA и выбор модели поиска по смыслу
  при запросе.

## Вне рамок

- Извлечение ограничений и фильтров из текста вопроса (фича 11).
- Формулировка ответа (фича 09).
- Переписывание запроса языковой моделью и поиск в несколько шагов.
- Вопросы на подсчёт и суммирование (фича 10).
- Быстрый приближённый поиск по векторам: при 7 тыс. отрывков достаточно точного
  перебора (принцип VIII).

## Assumptions

- Вход поиска — отрывки и оба индекса фичи 07 (Б4 2026-11-24: 56 договоров,
  7029 отрывков, по 7029 записей в каждом индексе, модель `bge-m3`).
- Модель поиска по смыслу — BGE-M3 (как в фиче 07), реранкер — BGE Reranker v2-m3
  (docs/tech-context.md); обе работают локально только на ноутбуке аналитика.
  Все три модели проекта помещаются в память одновременно (замер 2026-11-24,
  docs/tech-context.md, «Что проверить в первый день», п. 3).
- Числа по умолчанию — из технических заметок файла фичи: по 30 кандидатов от каждого
  способа, реранкер пересортировывает слитый список и оставляет 8 результатов;
  это настройки, подбираются замером.
- Автотесты — только на синтетических договорах из `tests/synthetic/` с поддельной
  моделью векторов (`HashEmbedder`, фича 07) и поддельным реранкером с заранее
  известными оценками (docs/tech-context.md, «Модели в автотестах»). На сервере
  разработки модели запрещены; поиск с реальными моделями, замер и проверка скорости
  (SC-003, SC-005) — на ноутбуке аналитика.
- Способ замера до эталонного набора фичи 02 (уточнение 2026-11-24): аналитик
  составляет 15–20 вопросов и для каждого записывает идентификатор договора
  и правильный пункт вида `D-0015/2.2.1`; набор хранится в папке данных вне
  репозитория; замер печатает только номера вопросов, идентификаторы пунктов, места,
  время, доли, модели и настройки. Набор потом может войти в эталон фичи 02.
  На 15–20 вопросах разница в один вопрос — 5–7 процентных пунктов: вывод замера
  ориентировочный и перепроверяется на эталоне фичи 02.
- Обзор реальных договоров (`scripts/survey_*.py`) до clarify не нужен: правила
  минимальной версии не зависят от вёрстки договоров — поиск работает по уже
  нарезанным отрывкам.
- Запросы на русском языке; набор — несколько тысяч отрывков, скорость не требует
  особых мер.
