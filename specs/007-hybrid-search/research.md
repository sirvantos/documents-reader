# Research: гибридный поиск с реранкером (фича 08, минимальная версия)

Решения плана. Источники: [spec.md](spec.md) с уточнениями 2026-11-24, часть B
`docs/features/08-hybrid-search.md` (где расходится со спецификацией, верна
спецификация), `docs/tech-context.md`, код и исследование фичи 07
(`specs/006-passages-and-indexes/research.md`: R-5 оставил выбор ранжирования
по словам этой фиче).

## R-1. Ранжирование по словам: BM25 по `lemmas` в Python

**Decision.** Поиск по словам считает BM25 (k1 = 1,2, b = 0,75) по столбцу
`passage.lemmas` в коде, а не `ts_rank` по `tsv`:

- слова запроса — `wordforms.query_terms(query)`: те же словарные формы, что
  `lemmatize` при построении индекса (номера и слова с цифрами — как есть), всё
  в нижнем регистре, без служебных слов (R-2), без повторов;
- слова отрывка — `lemmas`, разбитые по пробелу, в нижнем регистре;
- статистика (число отрывков, средняя длина, в скольких отрывках есть слово) — по
  области поиска: весь набор актуальных отрывков или отрывки одного договора;
- кандидаты — отрывки, где есть хотя бы одно слово запроса, по убыванию оценки, первые
  `[search] candidates` (30); равные оценки — по договору, затем по `ordinal`.

**Rationale.** Вопрос — фраза («какой срок оплаты по договору»), а не набор
обязательных слов: `plainto_tsquery` требует все слова сразу и почти всегда ничего
не находит, а запрос «любое из слов» с `ts_rank` не знает, насколько слово редкое —
«договор» встречается почти в каждом отрывке и перевешивает «оплату». BM25 учитывает
редкость слова и длину отрывка. Своё разбиение `lemmas` по пробелу обходит разбор
PostgreSQL, который режет номер `ДП-17/2026` на куски (уточнение фичи 07, U1):
номер целиком совпадает как одно слово. Объём — 7 тыс. отрывков, около 3 МБ `lemmas`
на весь набор: чтение и подсчёт — доли секунды (SC-003 ≤ 3 с). Формула — несколько
десятков строк, новой библиотеки нет (принцип VIII).

**Alternatives considered.** `ts_rank`/`ts_rank_cd` по `tsv` с `|`-запросом — без
редкости слова (см. выше); с `&`-запросом — пустые результаты на фразах.
Библиотека `rank-bm25` — лишняя зависимость ради 30 строк. Статистика по всему набору
при поиске в одном договоре — устойчивее, но требует читать весь набор на каждый
запрос; в минимальной версии — по области поиска, сравнение — следующая итерация
по замеру. Индекс GIN по `tsv` в минимальной версии не используется; он остаётся
для фильтров и фраз следующей итерации.

## R-2. Служебные слова запроса

**Decision.** `query_terms` отбрасывает слова, которые `pymorphy3` относит
к предлогам, союзам, частицам и междометиям (части речи `PREP`, `CONJ`, `PRCL`,
`INTJ`). Слова с цифрами не отбрасываются. Запрос, от которого не осталось слов
(«и в на по»), даёт пустой список кандидатов по словам; поиск по смыслу выполняется
(спецификация, особые случаи).

**Rationale.** Простое правило на уже используемом анализаторе, без своего списка
стоп-слов. Местоимения («какой», «который») не отбрасываются: их вес снижает BM25.

**Alternatives considered.** Список стоп-слов в файле — ещё одна вещь, которую надо
вести; отбрасывать по частоте в наборе — то же, что уже делает BM25.

## R-3. Поиск по смыслу: точный перебор в PostgreSQL

**Decision.** Вектор запроса — `Embedder.embed([query])` той же модели, что
`[embedding] model` (фича 07), без метки и без приставки (BGE-M3 приставок не
требует). Запрос длиннее `[embedding] max_chars` обрезается, вывод предупреждает
(особые случаи). Кандидаты — один запрос SQL:

```sql
ORDER BY v.embedding <=> %(q)s::vector, p.document_id, p.ordinal LIMIT %(n)s
```

по `passage_vector` с `model = [embedding] model`, только актуальные отрывки (R-6)
и, если задан, один договор (R-5). Векторы нормированы (фича 07), поэтому косинусное
расстояние даёт тот же порядок, что скалярное произведение.

**Rationale.** 7 тыс. векторов перебираются за миллисекунды; индекс HNSW — вне рамок
(спецификация, принцип VIII). Модель в `WHERE` — FR-002: векторы другой модели
не сравниваются. Нет ни одного вектора выбранной модели при наличии отрывков —
`EnvironmentProblem` «индекс по смыслу построен другой моделью — выполните docreader
index --all или укажите [embedding] model».

## R-4. Слияние: по местам (reciprocal rank fusion)

**Decision.** Оценка кандидата — сумма `1 / (k + место)` по каждому способу, где он
найден (место с 1, `k` = `[search] rrf_k` = 60, часть B). Порядок — по убыванию
оценки; равные — по договору, затем `ordinal`. После слияния остаются первые
`[search] rerank_candidates` (30): их пересортировывает реранкер; без реранкера
результат — первые `[search] results` (8) слитого списка.

**Rationale.** Оценки BM25 и косинуса несравнимы; слияние по местам не требует
приводить их к одной шкале. Отрывок, найденный обоими способами на тех же местах,
получает две доли и стоит выше (история 1, сценарий 5).

## R-5. Поиск в одном договоре

**Decision.** `--document D-0015` (функция: `document_id`) добавляет условие
`p.document_id = …` в оба отбора кандидатов до `LIMIT`; статистика BM25 — по отрывкам
этого договора (R-1). Неизвестный идентификатор — `UserError` «нет документа D-…»
(как `registry._not_found`); договор без актуальных отрывков — `UserError` «отрывков
нет: выполните docreader index D-…» или «отрывки устарели: …» (как `passage`, фича 07).
Ограничение никогда не снимается (FR-006).

## R-6. Какие отрывки ищутся и предупреждение об устаревании

**Decision.** Ищутся только актуальные отрывки: отпечаток текста и запуск разбора
совпадают с текущими (правило `indexing.passages_current` фичи 07, в виде условия
запроса на весь набор). Договор из реестра без актуальных отрывков (не
проиндексирован, этап `indexing` в `pending` или `failed`, отрывки устарели) не
ищется; вывод предупреждает одной строкой: «не проиндексированы или устарели N
договоров — выполните docreader index». Нет ни одного актуального отрывка —
`UserError` «индексы пусты — выполните docreader index».

**Rationale.** Спецификация говорит «поиск выполняется по тому, что есть»; устаревший
отрывок указывает место в прежнем тексте, и показать по нему текст нельзя (принцип II).
Поэтому «то, что есть» — актуальные отрывки, а остальные названы числом.

## R-7. Реранкер: `llama-server --reranking`, `/v1/rerank`

**Decision.** `docreader/reranker.py` — единственный модуль, который говорит
с реранкером (функция «вопрос, отрывки → оценки», tech-context «Модели в автотестах»).
Запрос — `POST {base_url}/rerank` клиентом `httpx2` (тот же HTTP-клиент, что под
`openai`; у `openai` нет метода для `rerank`):

```json
{"model": "bge-reranker-v2-m3", "query": "…", "documents": ["…", "…"]}
```

Ответ — `{"results": [{"index": 0, "relevance_score": 1.7}, …]}`; оценки
сортируются по `index`, их должно быть ровно столько, сколько отрывков, иначе
`RerankRequestError`. Документ для реранкера — метка и текст отрывка через перевод
строки, как вход модели поиска (фича 07, R-6), обрезанные так, чтобы вместе с запросом
уложиться в `[reranker] max_chars`. Все кандидаты — одним запросом. Оценка — как
отдала модель (без приведения к 0–1), используется только для порядка; равные —
по месту после слияния.

Защиты — как у `embedding.py`: `DOCREADER_FORBID_MODELS` без подменённого транспорта →
`EnvironmentProblem`; адрес только петлевой (`config.is_local_model_url`); без
повторов; обрыв и тайм-аут → `ModelUnavailable` (код 2); 4xx/5xx и ответ не по форме →
`RerankRequestError` — поиск останавливается (FR-005), код 2, без текста в сообщении.
`check()` — пробная пара «проверка»/«проверка» до начала поиска (FR-009).

Запуск на ноутбуке — команда quickstart Б3 фичи 07:
`llama-server -m ~/models/bge-reranker-v2-m3-Q8_0.gguf --reranking -c 8192 -b 8192
-ub 8192 -np 1 --host 127.0.0.1 --port 8082`. Путь `/v1/rerank`, форма ответа
и масштаб оценок **[проверить]** уровнем 3 (`tests/real_model/test_reranker_server.py`,
quickstart Б1).

**Rationale.** Тот же способ запуска, что у модели поиска (llama.cpp уже стоит);
код знает только адрес. Новой библиотеки нет: `httpx2` уже в зависимостях.

**Alternatives considered.** `sentence-transformers` CrossEncoder в процессе — PyTorch
и скачивание весов (принципы VIII, I). Языковая модель как реранкер — в десятки раз
медленнее и без числовой оценки (обсуждение с аналитиком 2026-11-24).

## R-8. Подделки моделей в автотестах

**Decision.** Уровень 1 (tech-context): подменённые HTTP-транспорты `httpx2.MockTransport`,
без сокетов.

- `tests/fakes/embedding.py` + `TopicEmbedder(topics)`: вектор — сумма осей тем,
  чьи слова-признаки (подстроки в нижнем регистре) есть в тексте, плюс малая добавка
  от хэша текста (различает отрывки без тем). Перефразированный пункт и запрос с общей
  темой («оплата» / «перечислить денежные средства») оказываются рядом без общих
  слов — это и проверяет история 1, сценарий 3. `HashEmbedder` фичи 07 остаётся для
  тестов, где смысл не важен.
- `tests/fakes/reranker.py`: `TableReranker(scores)` — оценка документа — значение
  первой подстроки из таблицы, найденной в документе, иначе `default`; хранит
  принятые запросы (`.requests`) для проверок «к реранкеру не обращались»;
  `FailingReranker(kind)` — `http_500`, `wrong_count`, `bad_index`, `not_json`,
  `timeout`, `connect`; `DownReranker()`.
- Фикстура `use_reranker` в `tests/conftest.py`, как `use_embedder`.

Записей ответов (уровень 2) нет: качество проверяет замер (история 4). Уровень 3 —
`tests/real_model/test_reranker_server.py` (только Mac): `check()`, форма ответа,
порядок на очевидной паре («срок оплаты»: «оплата в течение 30 дней» выше «гарантийный
срок»), недоступный адрес → `ModelUnavailable`.

## R-9. Настройки

**Decision.** Два новых раздела `settings.toml`, проверка как у `[embedding]`:

```toml
[search]
candidates = 30          # кандидатов от каждого способа
rrf_k = 60
rerank_candidates = 30   # сколько первых после слияния читает реранкер
results = 8

[reranker]
enabled = true           # уточнение 2026-11-24: включён по умолчанию
base_url = "http://127.0.0.1:8082/v1"
model = "bge-reranker-v2-m3"
timeout_s = 60
max_chars = 16000        # запрос + метка + текст на одну пару
```

Флаг `--no-rerank` выключает реранкер на один запуск. Решение FR-014 «выключить по
умолчанию» — это `enabled = false` в коде по умолчанию (правка после замера).

## R-10. Команда и функция

**Decision.** `docreader search "ЗАПРОС" [--document ID] [--no-rerank] [--results N]
[--json]` ([contracts/cli.md](contracts/cli.md)) и функция
`search.search(conn, settings, query, *, document_id=None, rerank=None, results=None,
embedder=None, reranker=None) -> SearchResult` для фичи 09 и замера (FR-011): CLI
только вызывает её и печатает. Порядок проверок до поиска: пустой запрос → область
(договор, актуальные отрывки, векторы модели) → модель поиска `check()` → реранкер
`check()` (если включён) → поиск. Поиск ничего не пишет в базу: запуска `run`
и миграции нет.

**Rationale.** Поиск — чтение сохранённых индексов, его результат не хранится
(хранить его будут прогоны эталона фичи 02). Модели и настройки, которыми получен
результат, показываются в выводе замера (уточнение 2026-11-24, принцип VI).

## R-11. Замер реранкера

**Decision.** `scripts/quickstart_search.py --questions ФАЙЛ [--json]` на ноутбуке.
Файл вопросов — TOML в папке данных (`$DOCREADER_DATA_DIR/questions/`):

```toml
[[question]]
text = "Какой срок оплаты?"
answer = "D-0015/2.2.1"   # договор вопроса — из идентификатора
```

Скрипт загружает модели один раз и для каждого вопроса выполняет `search.search`
дважды — `rerank=False` и `rerank=True` — в договоре из `answer`, с `results =
rerank_candidates` (30), чтобы место было видно до 30. Печатает номер вопроса,
`answer`, место без реранкера и с ним («—» — не найден в первых 30) и время каждого
поиска; итог — по каждому варианту доля «на первом месте», «в первых пяти», медиана
и наибольшее время, модели (`served_model` обеих) и настройки, и вывод по правилу
FR-014 (`decide(...)`, чистая функция). Вопрос без `answer`, с неверным
идентификатором или ответом, которого нет среди актуальных отрывков, — строка
«ошибка в наборе» без текста, в итог не входит. Текст вопросов не печатается
и не пишется (FR-012). Сводка, как у `quickstart_passages.py`, сохраняется рядом
с файлом вопросов, и её можно прислать агенту.

**Rationale.** Вопросы и правильные пункты — данные аналитика о реальных договорах:
они живут в папке данных (принцип I), в репозитории — только тестовый набор на
синтетике. Отдельная команда CLI не нужна до фичи 02 (`search eval` — следующая
итерация).

## R-12. Скорость и память

**Decision.** SC-003 (медиана ≤ 3 с без реранкера, ≤ 10 с с ним) — по времени
замера (Б3) **[проверить]**. Ожидание: BM25 по одному договору и SQL по векторам —
десятки миллисекунд; вектор запроса — доли секунды; реранкер — 30 пар до нескольких
тысяч знаков, единицы секунд на M3 Pro. Память трёх моделей вместе проверена
(tech-context, «Что проверить в первый день», п. 3).
