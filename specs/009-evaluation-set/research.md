# Research: эталонный набор и таблица результатов (фича 02)

Решения плана. Источники: [spec.md](spec.md) с уточнениями 2026-11-26; часть B
`docs/features/02-evaluation-set-and-results.md` (где расходится со спецификацией,
верна спецификация); `docs/tech-context.md`; `docs/field-catalog.md`; готовый код:
значения и их приведение (`values.py`), проверка поля (`verify.check_field`), поиск
цитаты (`textnorm.locate`), поиск фичи 08 (`search.search`, `ranking.py`), страница
ручной проверки фичи 05 (`scripts/review_extraction.py`), отбор договоров Б5 фичи 05
(`scripts/quickstart_extraction.py`, `pick_review`), шаблоны вопросов
(`scripts/make_search_questions.py`), замер ответов (`scripts/quickstart_answers.py`),
генератор договоров извлечения (`tests/synthetic/make_pdfs.py`,
`make_extraction_contracts`).

Числа рабочего набора, на которые опирается план (tech-context, замер фичи 05):
из 336 полей прототипа найдено 332, «не найдено» 0, отклонено 4. Значит, на странице
проверки почти все карточки — «совпало» или «разошлось»; карточек без значения — единицы.

## R-1. Команды и модули

**Decision.** Одна группа подкоманд `docreader eval …` (contracts/cli.md):

| Команда | Что делает | Модели |
|---|---|---|
| `eval template` | пустой шаблон эталона полей | нет |
| `eval review` | страница проверки шести полей прототипа | нет |
| `eval load ФАЙЛ` | загрузка ответов страницы или шаблона в эталон | нет |
| `eval blind pick` / `eval blind load ФАЙЛ` / `eval blind report` | слепой контроль | нет |
| `eval fields` | сравнение полей фичи 05 (или правил, или файла) с эталоном | нет |
| `eval questions load ФАЙЛ…` / `generate` / `clauses` | эталонные вопросы | нет |
| `eval search` | замер поиска на эталонных вопросах | поиск фичи 08 |
| `eval results` / `eval show` / `eval compare` / `eval export` | таблица результатов | нет |

Модули пакета:

- `docreader/catalog.py` — каталог полей в коде: все 68 основных полей, вид, очередь,
  группа, варианты выбора (R-3).
- `docreader/values.py` — приведение и проверка вида для новых видов (R-4).
- `docreader/gold.py` — разбор файлов эталона, правило замены, версия эталона,
  загрузка в базу (R-5, R-6).
- `docreader/outcomes.py` — чистые функции: исход пары, итоги, исход вопроса поиска,
  сопоставление записей, «лучше/хуже» (R-7, R-12, R-13). Без базы.
- `docreader/rules.py` — извлечение шести полей правилами (R-8).
- `docreader/review.py` — карточки и страница проверки (R-9); картинки страниц и
  прямоугольники строк — общий код, вынесенный из `scripts/review_extraction.py`
  в `docreader/pageimage.py`.
- `docreader/blind.py` — отбор договоров и итог слепого контроля (R-10).
- `docreader/questions.py` — вопросы: разбор файлов, генерация, подбор пунктов (R-11).
- `docreader/evaluation.py` — сравнения, замер поиска, записи таблицы результатов,
  файлы разбора и выгрузка (R-12, R-13).
- `render.py`, `cli.py` — вывод и подкоманды.

**Rationale.** Деление прежних фич: правила решения — чистые функции, проверяемые без
базы (исходы, сопоставление, правила извлечения, замена эталона); сборка и SQL — отдельно.
Команды, а не скрипты: эталон и таблица результатов — постоянная часть системы
(принцип V требует замера при каждом изменении этапа), а не разовый quickstart.

**Alternatives considered.** Скрипты в `scripts/`, как замеры фич 08 и 09, — их пришлось
бы запускать с путями и `--env-file`, и они не делят код; отвергнуто. Отдельная
команда верхнего уровня на каждое действие — засоряет `--help`; отвергнуто.

## R-2. Форматы файлов

**Decision.**

- **Шаблон и выгрузки для табличного редактора** (шаблон эталона, файл разбора,
  выгрузка таблицы результатов) — CSV в UTF-8 с BOM, разделитель `;`, все поля
  в кавычках. Загрузка принимает разделители `;` и `,` (по строке заголовка), с BOM
  и без: Numbers на Mac сохраняет CSV с запятой и без BOM, Excel с русскими
  настройками — с точкой с запятой.
- **Строки подсказки** в шаблоне: вторая и третья строки начинаются с `#вид` и
  `#подсказка` (вид поля, образец записи, отметка «отсутствует», разделитель
  вариантов); загрузка пропускает строки, у которых первая ячейка начинается с `#`.
- **Несколько вариантов значения** в одной ячейке — через ` || ` (две вертикальные
  черты с пробелами): в значениях полей каталога этот знак не встречается.
- **Файлы вопросов** — TOML, тот же вид `[[question]]`, что у наборов фич 08 и 09,
  с новыми необязательными ключами (contracts/files.md). Читается `tomllib`.
- **Ответы страницы проверки** — JSON, который страница отдаёт загрузкой, как страница
  фичи 05.
- **Результаты из файла** (FR-023) — JSON: для полей — значения по документам
  и полям, для поиска — найденные пункты по вопросам (contracts/files.md).

**Rationale.** Только стандартная библиотека (`csv`, `json`, `tomllib`), принцип VIII.
BOM — то, что Excel на Mac требует, чтобы открыть UTF-8 без потери кириллицы; Numbers
читает файл и с ним. Риск «редактор испортил кириллицу» проверяется в quickstart Б1
на первом же шаблоне (часть B файла фичи); если CSV не подойдёт — переход на XLSX
отдельной задачей с записью в tech-context.

**Alternatives considered.** XLSX через `openpyxl` — новая зависимость ради файла,
который CSV открывает; отвергнуто до проверки Б1. TOML для эталона полей — не
открывается в табличном редакторе; отвергнуто.

## R-3. Каталог полей в коде

**Decision.** `docreader/catalog.py`: кортеж `CATALOG` из 68 записей `CatalogField`
(имя, подпись по-русски, вид, очередь, группа, варианты выбора). Поля `*_` раскрыты
на `customer_…` и `contractor_…`. Виды: `identifier`, `requisite` (ИНН, КПП, ОГРН, БИК,
счёт — с длиной), `date`, `amount`, `percent`, `number`, `name`, `choice`, `records`,
`free_text`, `list`. Вручную оцениваются `free_text` и `list` (11 полей, каталог,
«Итог»); `records` (`price_by_year`, очередь 2) до своей итерации тоже не сравнивается
автоматически (см. «Отступления» плана). Наборы: `PROTOTYPE` (6), `QUEUE1` (35),
`ALL` (68). Тест сверяет `CATALOG` с таблицами `docs/field-catalog.md` (имя, вид,
очередь, число полей по видам и итог), так что расхождение каталога и кода — ошибка
теста. `fields.PROTOTYPE_FIELDS` остаётся как есть и проверяется на совпадение
с `catalog.PROTOTYPE`.

**Rationale.** Каталог обязателен для всех фич с полями; фича 06 возьмёт тот же модуль.
Разбор markdown в рабочем коде — хрупко; таблица в коде с тестом на совпадение даёт
один источник истины (документ) и одну проверку.

**Alternatives considered.** Читать `docs/field-catalog.md` при запуске — документ
попадает в рабочий путь программы и ломает её при правке текста; отвергнуто.

## R-4. Приведение и проверка вида для новых видов

**Decision.** `values.py` расширяется функциями для видов каталога, которых нет
у фичи 05; приведение существующих четырёх видов не меняется (они общие с извлечением,
FR-011):

| Вид | Приведённая форма | Ошибка вида |
|---|---|---|
| `requisite` | только цифры; длина по подвиду (ИНН юрлица 10, КПП 9, ОГРН 13, БИК 9, счёт 20) | не цифры или не та длина |
| `percent` | число с точкой без лишних нулей: «0,1%» → `0.1`, «20» → `20` | не число |
| `number` | целое: «60 (шестьдесят)» → `60` | не целое |
| `choice` | вариант каталога, сравнение без учёта регистра и «ё» | не из вариантов (в сообщении — список вариантов) |
| `free_text`, `list`, `records` | текст как есть | нет |

Контрольный разряд ИНН и ОГРН при загрузке эталона не проверяется: это правило
фичи 06, а эталон должен совпадать с тем, что напечатано в договоре, даже если там
опечатка. Сравнение наименований — по приведённой форме без учёта регистра
(каталог, «наименование»).

**Rationale.** Одни правила приведения для этапов, эталона, страницы проверки и
слепого контроля (FR-011); проверка вида при загрузке (FR-008) — та же функция,
что приведение: неприводимое значение — ошибка вида.

**Alternatives considered.** Отдельные правила приведения в модуле эталона — два
приведения разошлись бы, и «неверно» появлялось бы из-за оформления; отвергнуто.

## R-5. Хранение эталона и его версия

**Decision.** Миграция `0007_evaluation.sql` (data-model.md): `gold_load` (каждая
загрузка), `gold_field` (одна строка на размеченную пару; неразмеченная пара — нет
строки), `blind_pick` и `gold_blind` (слепой контроль), `gold_question`, `eval_result`
и `eval_case` (таблица результатов). Версия эталона полей — SHA-256 по отсортированным
строкам `gold_field` (документ, поле, состояние, приведённые варианты), пересчитывается
при каждой загрузке и хранится в `gold_load.gold_sha256`; версия вопросов — так же
по `gold_question`. Запись результата хранит версию, по которой посчитана; «посчитано
по прежней версии» — сравнение с текущей.

**Rationale.** Версия от содержимого, а не от файла: два разных файла с одинаковым
эталоном дают одну версию, а повторная загрузка того же файла версию не меняет.
Неразмеченная пара без строки — три состояния без особого значения NULL.

**Alternatives considered.** Отпечаток загруженного файла (часть B) — меняется
от пересохранения редактором без изменения значений; отвергнуто. Хранить историю
значений эталона — не требуется спецификацией, записи результатов хранят исходы
своих случаев; отвергнуто (принцип VIII).

## R-6. Правило замены эталона при загрузке

**Decision.** Файл (ответы страницы или шаблон) задаёт **охват** — множество пар
«документ, поле», которые он содержит: для шаблона — строки документов × столбцы
полей; для ответов страницы — пары её карточек. Загрузка:

1. разбирает файл; документ не из реестра — строка не загружается, причина;
   столбец не из каталога или нет столбца документа — файл не загружается целиком;
2. проверяет вид каждой непустой ячейки (R-4); ошибка — ячейка «не размечено»,
   причина со строкой и столбцом (или ключом карточки), без значения;
3. считает разницу с текущим эталоном **в пределах охвата**: добавлено, изменено,
   убрано (было значение — стало «не размечено»), без изменений;
4. если убирается хотя бы одно значение и нет `--yes`, печатает числа и останавливается
   с кодом 1 без изменений; иначе в одной транзакции заменяет строки охвата, пишет
   `gold_load` с новой версией и печатает итог.

Пары вне охвата не меняются. Пара, которая уже пришла из файла другого вида, после
загрузки берётся из последнего файла, и итог называет число таких пар.

**Rationale.** Уточнение спецификации (clarify: «файл заменяет эталон в пределах своих
документов и полей»). Подтверждение флагом `--yes`, а не вопросом в терминале: команду
можно запускать из скрипта, а повтор с `--yes` после просмотра чисел — тот же шаг.

**Alternatives considered.** Вопрос «да/нет» в терминале — ломает запуск без
терминала и тесты; отвергнуто.

## R-7. Исход пары «документ, поле»

**Decision.** Чистая функция `field_outcome(field, gold, system) -> CaseOutcome`
(исход и пометки) по таблице
(сверху вниз, первая подходящая строка):

| Эталон | Система | Исход |
|---|---|---|
| поле вида `free_text`, `list`, `records` | любое | `manual` (оценивается вручную) |
| не размечено | любое | `unlabeled` |
| размечено | нет строки `field_value`, `failed`, результат устарел (`source_text_sha256` не совпадает с текущим текстом) или поле не извлекается этапом | `no_result` (причина) |
| значение | `found`, приведённое совпало с любым вариантом | `correct` |
| значение | `found`, не совпало | `wrong` |
| значение | `not_found` или `rejected` | `missed` (у `rejected` — пометка) |
| отсутствует | `found` | `invented` |
| отсутствует | `not_found` или `rejected` | `correct` (у `rejected` — пометка) |

Итоги: число каждого исхода по полю и в целом (сумма = число пар, SC-002, проверяется
перед записью); доли — от размеченных пар с результатом (`correct + wrong + missed +
invented`); `no_result`, `unlabeled`, `manual` — числами отдельно; поля сортируются по
доле `correct` по возрастанию, при равенстве — по `invented` по убыванию; поля, которые
этап не извлекает, — отдельным блоком (спецификация, «Edge Cases»). Сравнение
наименований — без учёта регистра.

**Rationale.** Уточнения спецификации (отклонённое — невыданное; придуманное отдельно,
принцип IV). Устаревший результат — «нет результата», как и у читателей прежних фич
(tech-context, «Договорённости между этапами»: смещения при другом отпечатке
не используются).

**Alternatives considered.** Считать `rejected` отдельным исходом — спецификация
требует ровно шесть исходов; пометка сохраняет видимость; отвергнуто.

## R-8. Извлечение правилами

**Decision.** `docreader/rules.py`, `RULES_VERSION = "02.1"`. Для каждого из шести полей
прототипа — небольшой набор образцов над записями разбора (фича 04), без модели:

| Поле | Где ищется | Образец |
|---|---|---|
| `contract_number` | начало текста до преамбулы и сама преамбула | «ДОГОВОР № …» до конца строки или до «от», «г.» |
| `customer_name_short`, `contractor_name_short` | преамбула | сокращённое наименование в скобках или форма «ООО «…»» перед «(далее — «Заказчик»)» / «именуемое в дальнейшем «Подрядчик»» |
| `amount_without_vat`, `amount_with_vat` | пункты раздела с заголовком «Цена …» | сумма рядом со словами «без учёта НДС», «без НДС» / «с учётом НДС», «включая НДС» |
| `contract_end_date` | пункты со словами «срок действия» | дата после «действует до», «по», «до … включительно» |

Каждое найденное значение становится ответом того же вида, что ответ модели (найдено,
значение, цитата — строка или предложение вокруг, пункт), и проходит `verify.check_field`
— ту же проверку цитаты и значения, что у фичи 05 (принцип III). Несколько разных
значений поля — все сохраняются, карточка «разошлось» (спецификация). Правила работают
на лету: при построении страницы и при `eval fields --source rules`, ничего не пишут
в базу этапов; «чем получено» — `RULES_VERSION` и версия кода в записи результата.
Образцы пишутся и проверяются на синтетических договорах (`make_extraction_contracts`
и новые варианты) и строках-ловушках каталога; на рабочем наборе их доля «совпало»
измеряется в quickstart Б3 (SC-009).

**Rationale.** Независимый от модели второй способ делает «совпало» сильным доводом,
а «разошлось» — указателем на ошибку (решение аналитика). Шесть полей прототипа
стоят в предсказуемых местах (каталог, «Подсказки»). Через `check_field` правила
не могут предложить значение без цитаты.

**Alternatives considered.** Второй запрос к той же языковой модели — ошибки моделей
коррелируют, «совпало» значило бы меньше, и это 4 часа на ноутбуке; отвергнуто.
Хранить значения правил таблицей этапа — правила работают за доли секунды на набор,
таблица и её устаревание не нужны; отвергнуто (принцип VIII).

## R-9. Страница проверки

**Decision.** `docreader eval review [ID…]` строит папку
`$DOCREADER_DATA_DIR/eval/review-<время>/` с `index.html` и картинками страниц (общий
код с `scripts/review_extraction.py`, вынесенный в `docreader/pageimage.py`: отрисовка
`pypdfium2` при 110 dpi, прямоугольники строк цитаты из `text_span` и `page_text`).

- **Карточка** — пара «документ, поле» шести полей прототипа: значение фичи 05
  (`found`; `rejected` — с причиной и предложенным значением; `not_found`), значения
  правил, цитаты с отмеченными строками, пункт, страница, пометка согласия:
  `agree` («совпало»: приведённые значения равны), `disagree`, `model_only`,
  `rules_only`, `none`, `changed` («значение системы изменилось после проверки»:
  у пары есть эталон с путём из страницы, и текущее приведённое значение фичи 05
  отличается от `gold_field.system_normalized` — значения, показанного на карточке,
  когда аналитик отвечал; так исправленная или вписанная пара не помечается, пока
  система выдаёт то же, что видел аналитик). Порядок: `changed`, `disagree`, `rules_only`, `none`, `model_only`,
  `agree`; внутри — по документу и полю каталога.
- **Места для `none` и `rejected`** — три лучших отрывка документа по поиску по словам
  (BM25 фичи 08, `ranking.py`) на образец вопроса поля (R-11), с картинкой первой
  страницы отрывка. Только поиск по словам, без моделей, всегда (см. «Отступления»).
- **Ответы**: клавиши `1` — «верно» (при одном значении), `1`/`2` — какое из двух
  (при расхождении), `3` — «другое значение» (поле ввода), `4` — «отсутствует»,
  `0` — «пропустить», стрелки — по карточкам. Страница хранит ответы в
  `localStorage` под идентификатором сборки, показывает число оставшихся и отдаёт
  файл `gold-review-<сборка>.json` кнопкой. Вписанное значение страница проверяет
  только на пустоту и простой вид (цифры для суммы, дата одной из форм); окончательная
  проверка вида — при загрузке (R-4), ошибка называет ключ карточки.
- **Перенос ответов**: при новом построении карточки с эталоном показываются с
  выбранным ответом из эталона (кроме `changed`), так что работа продолжается с того
  же места после загрузки ответов.
- **Слепой контроль**: договоры из `blind_pick` без строк `gold_blind` в страницу
  не входят; вывод называет их.
- Вывод команды — путь к странице и числа карточек по пометкам; страница, картинки и
  файл ответов — только в папке данных, без внешних ссылок, шрифтов и скриптов (FR-006).

**Rationale.** Подтверждение готового значения с цитатой и страницей — то, что
сокращает работу (спецификация, SC-008); страница фичи 05 уже проверена у аналитика,
её устройство (отдельный HTML, ответы в браузере, файл ответов) переносится.

**Alternatives considered.** Веб-экран фичи 12 — фичи ещё нет; отвергнуто.
Табличный файл с предзаполненными значениями — без цитаты и страницы проверка
медленнее, а ошибку легче пропустить; отвергнуто.

## R-10. Слепой контроль

**Decision.** `eval blind pick` выбирает 5 договоров с результатами фичи 05 тем же
правилом, что отбор quickstart Б5 фичи 05 (`pick_review` в
`scripts/quickstart_extraction.py`, переносится в `blind.py`, скрипт импортирует):
хотя бы один с текстовым слоем (если есть), остальные — сканы по порядку
идентификаторов через равный шаг. Выбор хранится в `blind_pick` и не меняется
повторным `pick` без `--again`. Итог контроля считается только по парам, проверенным
**после** слепой разметки (`gold_field.load_id` позже `gold_blind.load_id`).
Шаблон слепой разметки — шесть полей прототипа на эти договоры, тот же вид, что
`eval template`. `eval blind load ФАЙЛ` — проверка вида как у шаблона, строки
в `gold_blind`. `eval blind report [--label]` — по каждой паре слепое значение против
проверенного (приведённые, без учёта регистра для наименований): совпало / разошлось /
нет одного из двух; число расхождений всего и среди пар с путём `agree`, `confirmed`
или `chosen` (значение системы подтверждено); запись `eval_result` этапа
`gold_blind`; файл разбора с обоими значениями — для аналитика.

**Rationale.** Карточки слепых договоров скрыты до слепой разметки (спецификация),
иначе слепая разметка не слепая. Отбор по правилу фичи 05 — проверенный у аналитика
способ задеть обе формы договоров.

**Alternatives considered.** Случайный отбор — может не задеть договоры с текстовым
слоем (3 из 56); отвергнуто.

## R-11. Вопросы

**Decision.**

- **Хранение**: `gold_question` — текст, документ, вид (`text`, `table`, `both`),
  есть ли ответ, ложная посылка, правильный ответ (варианты), правильные пункты
  (ключи записей разбора), откуда (`own`, `set08`, `set09`, `generated`), путь
  файла относительно папки данных. Ключ вопроса — `Q-` и 10 знаков SHA-256 от
  документа и текста в форме сравнения `textnorm`; он стабилен между загрузками
  и служит ключом случая в таблице результатов.
- **Загрузка** (`eval questions load ФАЙЛ…`): TOML; ключи наборов фич 08 и 09
  (`text`, `answer`, `document`, `expected = "none" | "answer"`, `contains`) и новые
  (`answers` — список пунктов, `kind`, `false_premise`). `answer` → вопрос вида `text`
  с ответом в пункте, документ — из пункта; `expected = "none"` → без ответа;
  `document` + `expected = "answer"` без пункта → «ответ есть, пункт не указан»: вне
  метрик поиска, в составе — отдельным числом с подсказкой `eval questions clauses`
  (решение аналитика, находка analyze U1). Откуда вопрос (`origin`): ключ `origin`
  в начале файла (`generate` пишет `generated`, `clauses` — откуда исходный файл),
  иначе `--origin own|set08|set09`, иначе `own` (находка analyze U2). Файл заменяет
  вопросы, ранее загруженные из него (по пути относительно папки данных); тот же
  ключ из другого файла — одна строка, признаки из последнего, расхождение называется
  номером. Неверный пункт, неизвестный документ, пункта нет в текущем разборе —
  вопрос не загружается, номер и причина. Итог — состав и предупреждения FR-021.
- **Генерация** (`eval questions generate`): из `gold_field` в
  `$DOCREADER_DATA_DIR/questions/generated-<время>.toml` (никогда поверх файла):
  - с ответом — для каждого значения с известным пунктом (`gold_field.clause_key`:
    пункт цитаты принятого значения системы или правил, или места, выбранного
    на карточке `none`), образец вопроса поля, правильный ответ — значение;
  - без ответа — для каждой пары с отметкой «отсутствует»;
  - с ложной посылкой — для полей видов `amount` и `date`: значение того же поля
    ближайшего следующего по идентификатору договора с другим приведённым значением;
    образец «Почему {подпись} по договору — {значение}?»; правильный ответ и пункт —
    из эталона; не больше `--false-premise N` (по умолчанию 10), по порядку
    идентификаторов через равный шаг.
  Образцы: шесть полей прототипа — те же, что `TEMPLATES` в
  `scripts/make_search_questions.py` (переносятся в `questions.py`, скрипт импортирует
  их); остальные поля очереди 1 — общий образец по подписи каталога. Вывод — путь
  и числа по видам.
- **Подбор пунктов** (`eval questions clauses --answers ФАЙЛ.json --questions
  ФАЙЛ.toml`): для вопросов «пункт не указан» предлагает пункты подтверждённых
  утверждений из машиночитаемого файла ответов замера фичи 09 и пишет **весь
  исходный набор** в новый TOML: у этих вопросов — `answers` с пометкой-комментарием
  «пункт из ответа — проверить», остальные как были; файл заменяет исходный при
  загрузке.
  Вопросы двух файлов сопоставляются по документу и тексту (ключ вопроса), не по
  номеру: повторный замер идёт только по вопросам без пункта.
  Машиночитаемый файл `answers-b4-<время>.json` (номер вопроса, итог, подтверждённые
  утверждения с пунктами) начинает писать `scripts/quickstart_answers.py`; для
  прошлого прогона аналитик повторяет замер на вопросах без пункта (quickstart Б5).

**Rationale.** Ключ от текста и документа — требование «вопрос определяется текстом
и документом» и стабильный случай для сопоставления записей. Генерация закрывает
вопросы без ответа и с ложной посылкой, которых в наборах нет. Разбор текстового файла
ответов (`answers-b4-*.txt`) — хрупкий; JSON рядом с ним дешевле.

**Alternatives considered.** Генерировать вопросы без ответа из полей других
договоров («какой аванс» там, где аванса нет, по чужому договору) — без отметки
«отсутствует» в эталоне нельзя утверждать, что ответа нет; отвергнуто.

## R-12. Замер поиска и исход вопроса

**Decision.** `eval search [--label] [--from ФАЙЛ.json]`. Для каждого эталонного вопроса
с ответом вида `text`/`both` — `search.search(conn, settings, text, document_id=doc,
rerank=False|True, results=rerank_candidates)` (30, как в замере фичи 08); место —
номер первого результата, чей ключ пункта входит в правильные пункты (точное
совпадение, уточнение спецификации), или «не найден». Два варианта — две записи
`eval_result` с одной меткой: этапы `search_plain` и `search_rerank`. Метрики варианта:
доля на первом месте и в первых пяти (знаменатель — участвующие вопросы, «не найден»
входит), медиана места по найденным, число «не найден», число неучаствующих (без
ответа, вид `table`, пункт не указан). С `--from` места берутся из файла (FR-023), модели не нужны.
До первого вопроса — проверка доступности моделей; `DOCREADER_FORBID_MODELS` — код 2.

**Rationale.** Те же вызовы, что в `scripts/quickstart_search.py`, — SC-007 (те же места).
Две записи вместо одной с двумя вариантами — сопоставление работает внутри этапа
(«с реранкером» прошлый и нынешний).

**Alternatives considered.** Медиана по всем, «не найден» как 31 — искажает при
изменении `rerank_candidates`; отвергнуто.

## R-13. Таблица результатов, раскрытие, сопоставление, выгрузка

**Decision.**

- **Запись** (`eval_result`): время, метка, этап (`fields`, `rules`, `search_plain`,
  `search_rerank`, `gold_blind`), «чем получено» (`provenance` JSON: версия кода; для
  `fields` — различные `run` строк `field_value` с моделью, подсказкой и настройками;
  для `rules` — `RULES_VERSION`; для поиска — модели, настройки `[search]`,
  `[reranker]`), версии эталона полей и вопросов, доля эталона из проверки (доля
  строк `gold_field` с путём из страницы), итог последнего слепого контроля (числа),
  метрики (JSON), путь файла разбора. Случаи — `eval_case` (ключ случая, документ,
  поле или ключ вопроса, исход или место, пометки, отпечаток эталона случая). Сумма
  исходов проверяется перед записью (SC-002); запись и её случаи — одна транзакция.
- **Раскрытие** (`eval show ЗАПИСЬ [--field F] [--outcome O]`): метрики записи и
  список случаев по фильтру — идентификаторы документов, поля, вопросы, исходы
  (SC-004).
- **Сопоставление** (`eval compare A B`): только записи одного этапа (иначе код 1).
  Разница метрик; случаи с изменившимся исходом по ключу случая. Для полей — ранг
  `correct` 0, `missed` 1, `wrong` 2, `invented` 3 (принцип IV: придуманное тяжелее
  пропущенного); меньший ранг — «стало лучше», больший — «стало хуже»; переходы
  в `no_result`, `unlabeled`, `manual` и из них — отдельной группой «вне сравнения».
  Для поиска — место меньше — лучше, «не найден» хуже любого места. Если версии
  эталона разные — предупреждение, и случаи, у которых изменилось эталонное значение
  (по отпечатку эталона случая), — отдельной группой «из-за эталона» (SC-005).
- **Выгрузка** (`eval export`): CSV (R-2) со строкой на запись и столбцами метрик;
  путь печатается.
- **Файл разбора** (FR-027) — при каждом `eval fields`, `eval search`, `eval blind
  report`: CSV в `$DOCREADER_DATA_DIR/eval/` со значениями эталона и системы, пунктом
  и цитатой (для поиска — текст вопроса, правильные пункты, места, первые пять
  найденных пунктов); команда печатает только путь.

**Rationale.** Ключ случая стабилен (документ и поле; ключ вопроса), поэтому
сопоставление — разность двух множеств строк. Отпечаток эталона у случая показывает
«из-за эталона» без хранения истории эталона.

**Alternatives considered.** Хранить метрики только JSON без случаев — нельзя
раскрыть цифру (SC-004); отвергнуто.

## R-14. Тесты и синтетика

**Decision.** Модульные тесты — каталог против `docs/field-catalog.md`; приведение
новых видов; разбор CSV (`;`/`,`, BOM, строки `#`, ` || `); правило замены (R-6)
на словарях; исход пары (каждая строка таблицы R-7) и итоги; исход поиска и метрики;
сопоставление (каждая группа); правила извлечения на тексте синтетических договоров
и на строках-ловушках каталога («Ловушки для эталона»: номера других документов,
много сумм, даты других документов) — без значений образца; генерация вопросов;
вывод команд без значений и текста (проверка, что в выводе нет ни одного значения
эталона и текста вопроса). Интеграционные — CLI на временной базе:
`make_extraction_contracts` → приём → чтение → разбор → `extract` с `ScriptedModel`
→ `eval review` → ответы (файл, собранный тестом) → `eval load` → `eval fields` →
`eval compare`; `eval search --from` и `eval search` с `TopicEmbedder`/`TableReranker`
на генераторе поиска фичи 08. Синтетический эталон и файлы вопросов — в
`tests/synthetic/` (вымышленные договоры генераторов). Реальных моделей нет; уровня 3
нет (модели нужны только поиску, его уровень 3 есть у фичи 08).

**Rationale.** Уровни tech-context: вся логика фичи — уровень 1, модели не участвуют.

## R-15. Производительность

**Decision.** Сравнение полей — один запрос `gold_field` и один `field_value` (56 × 68
= 3808 пар), исходы в памяти: доли секунды (SC-001 ≤ 60 с). Страница проверки —
около 340 картинок страниц при 110 dpi; картинка страницы, общая для нескольких
карточек, рисуется один раз; ожидаемо минуты, не часы (проверяется в Б3).

**Rationale.** Объём набора мал (конституция: 50 договоров).
