**Feature Branch**: `005-field-extraction`

**Created**: 2026-11-22

**Status**: Draft

**Input**: User description: "Фича 05. Извлечение полей с цитатой. Источник — часть A файла docs/features/05-field-extraction.md, поля — раздел «Поля для сквозного прототипа» в docs/field-catalog.md. Объём — только «Минимальная версия для сквозного прототипа» (CLAUDE.md, «Delivery»): одна группа из шести полей прототипа (contract_number, customer_name_short, contractor_name_short, amount_without_vat, amount_with_vat, contract_end_date); модель получает весь очищенный текст договора; для каждого поля — значение как в тексте, приведённое значение, дословная цитата и пункт договора (идентификатор записи фичи 04, например D-0001/5.2) или «не найдено»; программная проверка цитаты из сценария 2; результаты «значение», «не найдено», «отклонено», «ошибка»; просмотр полей договора из командной строки. Остальное из файла фичи — в раздел «Следующая итерация». Ограничения: значение без подтверждённой цитаты в таблицу не попадает (принцип III); «не найдено» — допустимый результат (принцип IV); языковая модель работает только локально и только на ноутбуке аналитика, автотесты — на синтетических договорах с поддельной моделью; замер качества — на ноутбуке аналитика."

## Суть и назначение

Для каждого разобранного договора система заполняет шесть полей сквозного прототипа:
номер договора, краткие наименования заказчика и подрядчика, цену без НДС и с НДС,
дату окончания действия договора. Значение предлагает языковая модель, прочитав текст
договора без приложений; к каждому значению она приводит дословную цитату. Обычная программа, а не
модель, проверяет, что цитата есть в тексте договора и что значение действительно
в ней записано, и привязывает цитату к пункту договора (запись разбора фичи 04)
и странице. Значение без подтверждённой цитаты не принимается. Если сведений
в договоре нет, поле получает результат «не найдено».

**Зачем.** Таблица полей отвечает на вопросы, на которые поиск по тексту ответить
не может: сколько договоров, на какую сумму, какие истекают в этом году (фичи 08–10).
Модель иногда выдаёт правдоподобное, но неверное значение; обязательная цитата и её
программная проверка превращают незаметную ошибку в заметную и дают аналитику место
в договоре, по которому значение проверяется за секунды. Минимальная версия даёт
ровно шесть полей, нужных сквозному прототипу; остальное откладывается до его
готовности.

**Пользователь.** Один аналитик. Он запускает извлечение из командной строки
на своём ноутбуке и просматривает поля договора там же.

## Clarifications

### Session 2026-11-22

- Q: Какую часть договора показывать модели при извлечении шести полей? → A: Преамбулу, основной текст и раздел реквизитов — без приложений (хвост показывается до первой строки, начинающейся словом «Приложение»). Решение аналитика. Основание — обзор реальных договоров (`scripts/survey_fields.py`, версия 2, 56 договоров, 2026-11-22): весь текст — 65–356 тыс. знаков, без приложений — 56–102 тыс. у всех 56; номер и роли сторон в преамбуле — 56 из 56, раздел о цене — 56 из 56, дата окончания словами в основном тексте — 56 из 56; приложения — 9–282 тыс. знаков. Отступление от «Минимальной версии» файла фичи (там — весь текст). Цитата принимается только из показанной части.
- Q: Когда извлечение помечает договор «требует просмотра» из-за сомнительного текста? → A: Только в двух случаях: (а) цитата найденного значения стоит на странице с флагом «низкое качество распознавания»; (б) в показанной модели части есть непрочитанная страница (сведения могли пропасть). В причине — поле и страница. Состояния «требует просмотра» у чтения и разбора сами по себе на извлечение не переносятся. Решение аналитика: у большинства договоров набора чтение «требует просмотра» из-за страниц приложений, и общая пометка ничего бы не значила.
- Q: Переводит ли поле с результатом «не найдено» договор в состояние «требует просмотра»? → A: Нет. «Не найдено» состояние не меняет (принцип IV); итог команды извлечения показывает по каждому договору число полей «найдено», «не найдено», «отклонено» и названия ненайденных полей, чтобы пропуски были видны без пометки. Решение аналитика.
- Q: Где в договоре стоит номер и подтверждается ли он цитатой? → A: В начале преамбулы, со знаком «№»; заголовок обычно разбит на две строки («ДОГОВОР …» и на следующей строке «№ …»), и цитата может идти через этот перенос — проверка цитаты приводит переносы строк к пробелам. Решено по: обзор `scripts/survey_fields.py`, версия 2 (56 договоров, 2026-11-22) — номер со знаком «№» и цифрами в начале преамбулы у 56 из 56, искажений знака распознаванием нет; на следующей строке после «Договор» — 53, в той же строке — 3; в колонтитулах — у 2, в реквизитах и приложениях — 0.
- Q: Что считать кратким наименованием стороны, если скобок с сокращением нет? → A: Сокращённую форму «организационно-правовая форма + название в кавычках» («ООО «…»»), которой сторона названа в преамбуле; если есть скобки «(ООО «…»)» — это та же форма. Решено по: обзор версии 2 — такая форма вне скобок есть в преамбуле 56 из 56 договоров, скобки — только у 29; определение каталога «из скобок» подходит половине набора (формулировку каталога уточнить в плане).
- Q: На каких договорах аналитик вручную проверяет качество извлечения, пока эталонного набора нет? → A: На 10 договорах: все три договора с текстовым слоем (другая форма договора) и 7 договоров-сканов, взятых по порядку идентификаторов через равный шаг; среди сканов — хотя бы один с состоянием извлечения «требует просмотра», если такие есть. Решение аналитика: 53 договора набора — похожие сканы, и случайная выборка могла бы не задеть вторую форму.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Заполнить поля договора (Priority: P1)

Аналитик запускает извлечение для разобранных договоров. Для каждого из шести полей
система сохраняет один результат: «найдено» со значением как в тексте, приведённым
значением, цитатой, пунктом и страницей; «не найдено»; «отклонено» с причиной;
«ошибка» с причиной.

**Why this priority**: Без полей нет таблицы для вопросов о количестве, суммах
и сроках — части сквозного прототипа.

**Independent Test**: Извлечь поля из синтетического договора с поддельной моделью,
которая возвращает заранее записанный ответ, и сравнить сохранённые результаты
с ожидаемыми.

**Acceptance Scenarios**:

1. **Given** договор разобран на пункты, **When** аналитик запускает извлечение,
   **Then** для каждого из шести полей сохранён ровно один результат: «найдено»,
   «не найдено», «отклонено» или «ошибка».
2. **Given** значение найдено, **When** аналитик смотрит поля договора, **Then** он
   видит значение как в договоре, приведённое значение, цитату, идентификатор пункта
   (`D-0001/2.1`) и страницу.
3. **Given** в договоре дата записана как «25 марта 2026 г.», **When** выполняется
   извлечение, **Then** сохранены и запись из договора, и приведённая дата
   `2026-03-25`.
4. **Given** цена записана как «64 270 348 (…) рублей 83 копейки», **When**
   выполняется извлечение, **Then** приведённое значение — `64270348.83`.
5. **Given** договор уже обработан, **When** аналитик запускает извлечение для него
   снова, **Then** прежний результат договора заменён новым.

### User Story 2 - Проверка цитаты (Priority: P1)

Каждое значение, предложенное моделью, проходит программную проверку: цитата
должна быть в тексте договора, а значение — в цитате. Проверка не обращается
к модели.

**Why this priority**: Это главная защита от придуманных значений (принцип III);
без неё таблице нельзя доверять.

**Independent Test**: Подать на проверку подготовленные ответы с верными и неверными
цитатами без модели и сравнить результаты с ожидаемыми.

**Acceptance Scenarios**:

1. **Given** цитата дословно есть в тексте договора, **When** выполняется проверка,
   **Then** значение принято, цитате сопоставлены место в тексте, пункт и страница.
2. **Given** цитаты нет в тексте договора, **When** выполняется проверка, **Then**
   поле получает «отклонено» с причиной «цитата не найдена»; предложенное значение
   сохраняется для просмотра, но не считается найденным.
3. **Given** цитата есть, но значения в ней нет (номер, дата или сумма другие),
   **When** выполняется проверка, **Then** поле получает «отклонено» с причиной
   «значение не подтверждено цитатой».
4. **Given** цитата отличается от текста только пробелами, переносами строк, видом
   дефиса или кавычек, буквой «ё», **When** выполняется проверка, **Then** цитата
   считается найденной.
5. **Given** цитата встречается в тексте несколько раз, **When** выполняется
   проверка, **Then** выбирается место в пункте, который назвала модель, если цитата
   там есть, иначе первое место в тексте.

### User Story 3 - «Не найдено» (Priority: P1)

Если в договоре нет сведений для поля, поле получает «не найдено», а не значение
по умолчанию и не значение, вычисленное из других сведений.

**Why this priority**: Придуманное значение хуже пропущенного (принцип IV); система
не обязана заполнить каждое поле.

**Independent Test**: Извлечь поля из синтетического договора без цены с НДС
и без даты окончания и проверить результаты.

**Acceptance Scenarios**:

1. **Given** в договоре нет цены с НДС, **When** выполняется извлечение, **Then**
   поле цены с НДС имеет результат «не найдено», даже если цена без НДС и ставка
   НДС известны.
2. **Given** срок действия записан формулой («до полного исполнения обязательств»),
   **When** выполняется извлечение, **Then** дата окончания имеет результат
   «не найдено».
3. **Given** модель вернула для поля пустое значение или признак «не найдено»,
   **When** результат сохраняется, **Then** поле — «не найдено» без цитаты.

---

### User Story 4 - Посмотреть поля договора (Priority: P2)

Аналитик выводит поля одного договора, чтобы сверить их с исходным файлом.

**Why this priority**: Без просмотра аналитик не может проверить результат
на договорах (SC-002) и найти причину ошибки.

**Independent Test**: Вывести поля синтетического договора после извлечения
с поддельной моделью и сравнить с ожидаемым видом.

**Acceptance Scenarios**:

1. **Given** извлечение выполнено, **When** аналитик запрашивает поля договора,
   **Then** он видит по каждому из шести полей результат, значение как в тексте,
   приведённое значение, пункт, страницу и цитату, а для «отклонено» и «ошибка» —
   причину и предложенное моделью значение.
2. **Given** договор ещё не обработан или неизвестен, **When** аналитик запрашивает
   поля, **Then** он видит понятное сообщение на русском с подсказкой, что сделать.

### Минимальная версия для сквозного прототипа

Эта спецификация целиком и есть минимальная версия: истории 1–4. Всё, что в файле
фичи сверх неё, — в разделе «Следующая итерация».

### Edge Cases

- **Что показывается модели.** Преамбула, основной текст и раздел реквизитов: хвост
  показывается до первой строки, начинающейся словом «Приложение»; приложения модели
  не показываются. Если раздел реквизитов не найден (хвоста нет), показывается весь текст.
- **Текст не помещается в один запрос к модели.** Если показываемая часть длиннее
  предела одного запроса (настройка), все шесть полей получают «ошибка» с причиной
  «текст слишком длинный», договор — состояние «ошибка». По обзору таких договоров
  в наборе нет (наибольшая показываемая часть — 102 тыс. знаков).
- **Цитата из приложения.** Цитата, которой нет в показанной части, но которая есть
  в приложении, отклоняется как «цитата не найдена»: модель приложений не видела.
- **Много сумм в договоре.** Цены этапов, штрафы, обеспечение: в поля цены идёт
  только общая цена договора. Если модель приводит цитату с другой суммой и эта
  цитата есть в тексте, проверка цитаты её не отличит — такую ошибку покажет замер
  (SC-002), а правила фичи 06 потом сверят цену с НДС с ценой без НДС.
- **Номера других документов.** Номера доверенностей, протоколов, актов не являются
  номером договора; номер берётся из заголовка договора в начале преамбулы.
- **Заголовок разбит на строки.** «ДОГОВОР …» стоит на одной строке, «№ …» — на следующей:
  цитата с номером может идти через перенос строки и считается найденной.
- **Цитата в хвосте.** Цитата из раздела реквизитов (наименования сторон) привязывается
  к записи хвоста `D-0001/реквизиты`.
- **Цитата на границе пунктов.** Цитата, начинающаяся в одном пункте и кончающаяся
  в другом, привязывается к пункту, где она начинается.
- **Ответ модели не по форме.** Ответ, который не удаётся прочитать как значения
  шести полей, запрашивается повторно ограниченное число раз; после этого все шесть
  полей получают «ошибка» с причиной, а договор — состояние «ошибка».
- **Лишние поля в ответе.** Значения полей, которых нет среди шести, отбрасываются.
- **Указания в тексте договора.** Фразы, обращённые к читателю («в ответе укажите…»),
  остаются текстом договора и не меняют работу системы.
- **Сомнительный текст.** Договор получает «требует просмотра», если цитата найденного
  значения стоит на странице с флагом «низкое качество распознавания» (причина
  «цена без НДС: стр. 5 — низкое качество распознавания») или если в показанной модели
  части есть непрочитанная страница (причина «не прочитана страница 3»). Флаги страниц
  приложений и состояния «требует просмотра» у чтения и разбора на извлечение не влияют.
- **Сторон не две или роли не определяются.** Поля наименований сторон получают
  «не найдено» или «отклонено» по общим правилам; отдельного правила о составе сторон
  в минимальной версии нет.
- **Договор не разобран.** Если разбор договора не выполнен или устарел, извлечение
  его не трогает и объясняет причину с подсказкой команды.
- **Текст изменился после извлечения.** Повторное чтение изменило текст: прежние поля
  считаются устаревшими и не используются как актуальные, этап извлечения ожидает
  перезапуска.
- **Модель недоступна.** Если модель не запущена или не отвечает, извлечение
  останавливается с понятным сообщением об окружении и не помечает договоры ошибкой.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001.** Система должна заполнять для каждого договора ровно шесть полей
  прототипа из каталога полей: `contract_number`, `customer_name_short`,
  `contractor_name_short`, `amount_without_vat`, `amount_with_vat`,
  `contract_end_date` — одним обращением к модели на договор (одна группа). Модель
  получает преамбулу, основной текст и раздел реквизитов договора, без приложений.
- **FR-002.** Система должна сохранять для каждого поля ровно один результат:
  «найдено», «не найдено», «отклонено» с причиной или «ошибка» с причиной.
- **FR-003.** Для результата «найдено» система должна сохранять значение как в тексте,
  приведённое значение, дословную цитату, место цитаты в очищенном тексте, пункт
  (идентификатор записи разбора фичи 04) и страницу.
- **FR-004.** Система должна приводить значения по видам каталога полей: номер
  договора — как идентификатор, наименования — как наименование, цены — как сумма
  с двумя знаками после точки, дата — как `ГГГГ-ММ-ДД`. Приведение выполняет программа,
  а не модель.
- **FR-005.** Система должна программно проверять, что цитата есть в показанной модели
  части очищенного текста договора (с приведением пробелов, переносов, дефисов, кавычек и «ё»), и что значение
  есть в цитате: номер, сумма и дата — по приведённому виду, наименование — по словарным
  формам слов (каталог полей, «Виды значений»). Проверка не обращается к модели.
- **FR-006.** Система не должна сохранять как найденное значение без подтверждённой
  цитаты. Предложенное значение и цитата отклонённого поля сохраняются для просмотра
  вместе с причиной.
- **FR-007.** Система должна оставлять поле с результатом «не найдено», когда модель
  не нашла сведений, и не подставлять значение по умолчанию или вычисленное из других
  полей.
- **FR-008.** Система должна сообщать модели, что текст договора — данные, а не указания:
  указания внутри текста не меняют форму ответа и работу системы.
- **FR-009.** Система должна выставлять состояние этапа извлечения для каждого договора:
  «готово» — все шесть полей «найдено» или «не найдено» («не найдено» состояние
  не меняет); «требует просмотра» с причиной —
  есть поле «отклонено», или цитата найденного значения стоит на странице с флагом «низкое
  качество распознавания», или в показанной модели части есть непрочитанная страница;
  «ошибка» с причиной — ответ модели не получен в нужной форме после повторов.
  В причине перечислены поля, виды отклонения и номера страниц; текста договора
  в причине нет.
- **FR-010.** Извлечение должно брать только договоры, у которых разбор выполнен
  (состояние «готово» или «требует просмотра») и не устарел. Без указания договоров —
  договоры, у которых этап извлечения в состоянии «ожидает» или «ошибка»; повторное
  извлечение заменяет прежний результат договора.
- **FR-011.** Результат извлечения, полученный по тексту, который потом изменился,
  не должен использоваться как актуальный (как у разбора, фича 04, FR-011).
- **FR-012.** Система должна сохранять сведения о запуске: модель, версию подсказки
  и настройки, — и показывать для договора, каким запуском получены его поля.
- **FR-013.** Система должна показывать поля одного договора из командной строки
  (история 4).
- **FR-014.** Извлечение должно выполняться локально, без обращения к сети; если модель
  недоступна, команда останавливается с сообщением об окружении.
- **FR-015.** Вывод команды извлечения (итог по договорам) должен показывать по каждому
  договору состояние, число полей «найдено», «не найдено» и «отклонено» и названия
  ненайденных и отклонённых полей и не должен содержать текста договора: только
  идентификаторы, состояния, названия полей, числа и причины, — чтобы его можно было
  присылать агенту. Значения и цитаты выводит только просмотр полей.

### Key Entities *(include if feature involves data)*

- **Значение поля.** Договор, поле, результат, значение как в тексте, приведённое
  значение, цитата, место цитаты в тексте, пункт, страница, причина (для «отклонено»
  и «ошибка»), предложенное моделью значение (для «отклонено»), запуск, отпечаток
  текста, по которому получено.
- **Группа полей.** Шесть полей прототипа, заполняемых одним обращением к модели.
- **Состояние этапа извлечения.** Для каждого договора: «ожидает», «готово», «требует
  просмотра», «ошибка»; у двух последних — причина.
- **Запуск извлечения.** Модель, версия подсказки, настройки, время.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001.** 100% значений с результатом «найдено» имеют цитату, которая есть в тексте
  договора и содержит значение (проверяется программой на всех договорах набора).
- **SC-002.** На 10 реальных договорах, проверенных аналитиком вручную на его ноутбуке
  (три договора с текстовым слоем и 7 сканов, взятых по порядку идентификаторов через
  равный шаг, включая хотя бы один «требует просмотра» по извлечению, если такие есть),
  не менее 90% из 60 полей имеют верный результат: верное значение или верное
  «не найдено». Целевой ориентир; уточняется после первого замера.
- **SC-003.** На тех же 10 договорах ни одно поле с результатом «найдено» не содержит
  значения, которого нет в договоре (придуманное значение).
- **SC-004.** Извлечение шести полей для всех договоров набора (56) занимает не более
  8 часов на ноутбуке аналитика. Целевой ориентир: скорость модели ещё не измерена.
- **SC-005.** На синтетических договорах из тестового набора (с поддельной моделью)
  100% подготовленных случаев дают ожидаемый результат: верная цитата — «найдено»
  с верным пунктом и страницей, цитаты нет — «отклонено», значения нет в цитате —
  «отклонено», нет сведений — «не найдено», ответ не по форме — «ошибка».

## Assumptions

- Вход извлечения — очищенный текст договора (фичи 03 и 13) и записи разбора
  (фича 04); пункт цитаты определяется по записям разбора.
- У договора две стороны: «Заказчик» и «Подрядчик»; краткое наименование стороны —
  сокращённая форма «ООО «…»», которой сторона названа в преамбуле, в скобках или без
  них (уточнение 2026-11-22).
- Номер договора — из заголовка; цена — общая цена договора; дата окончания — дата
  окончания действия договора, а не выполнения работ (каталог полей).
- Одна языковая модель, работающая локально на ноутбуке аналитика, обслуживает
  извлечение; при одинаковых входных данных она настроена давать по возможности
  одинаковый ответ.
- Число повторов при ответе не по форме — настройка со значением по умолчанию 2.
- Автотесты — только на синтетических договорах из `tests/synthetic/` с поддельной
  моделью: заглушками и ответами, записанными с реальной модели на синтетических
  договорах. Прогоны с реальной моделью и проверки на реальных договорах (SC-002–SC-004)
  выполняет аналитик на своём ноутбуке.
- Эталонный набор (фича 02) ещё не собран; качество в минимальной версии проверяется
  ручной сверкой аналитика на 10 договорах (отбор — в SC-002).
- До `/speckit.clarify` аналитик запускает на ноутбуке обзор реальных договоров
  (`scripts/survey_fields.py`): он выводит только числа и доли — длину очищенного
  текста по частям (преамбула, основной текст, хвост), есть ли в преамбуле краткие
  наименования в скобках, сколько сумм «с НДС» и «без НДС» в разделе о цене, в каком
  виде записан срок действия. Ответы на открытые вопросы опираются на эти числа.
