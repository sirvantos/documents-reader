# Quickstart: проверка фичи 01 «Приём документов и реестр»

**Дата**: 2026-11-16 · **План**: [plan.md](plan.md) · **CLI**: [contracts/cli.md](contracts/cli.md) ·
**Модель данных**: [data-model.md](data-model.md)

Две части: (А) проверка на синтетических файлах — можно выполнять с ИИ-агентом;
(Б) проверка на реальных договорах — **только аналитик, в своём терминале, без агента**
(принцип I и раздел «Разработка с ИИ-агентом» конституции: вывод команд по реальным
договорам содержит их имена и не должен попадать к агенту).

## Предварительные условия

Часть А выполняется на сервере разработки (Ubuntu 24.04) или на ноутбуке; часть Б —
только на ноутбуке аналитика.

- `uv`, Python 3.11+ (ставится через `uv`).
- PostgreSQL 17, запущен локально:
  - ноутбук (macOS):
    ```
    brew install postgresql@17 && brew services start postgresql@17
    createdb docreader
    ```
  - сервер разработки (Ubuntu): PostgreSQL 17 из репозитория PGDG
    (`apt.postgresql.org`), затем роль с правом создавать базы для текущего
    пользователя и `createdb docreader`.
- Папка данных вне репозитория, например `~/docreader-data`.

## Установка

```
uv sync                                    # зависимости + dev-зависимости
export DOCREADER_DATA_DIR=~/docreader-data
export DOCREADER_DATABASE_URL=postgresql:///docreader
uv run docreader migrate
```

Ожидается: «Применена миграция 0001_intake». Повторный `migrate` — «Схема актуальна».

## А. Синтетические файлы

### Автотесты

```
export DOCREADER_TEST_DATABASE_URL=postgresql:///postgres
uv run pytest
```

Ожидается: все тесты проходят. Без `DOCREADER_TEST_DATABASE_URL` интеграционные тесты
падают с сообщением, какую переменную задать.

Тесты покрывают сценарии спецификации:

| Сценарий / требование | Что проверяется |
|---|---|
| US1-1, FR-001, FR-006 | папка с вложенной папкой и 5 PDF → 5 документов с ID, именем, числом страниц |
| US1-2, FR-002, R-5 | DOCX, JPEG, PNG, «непонятный» файл, `.DS_Store` → `rejected` с причиной; остальные добавлены |
| US1-3, FR-004, SC-003 | исходный файл удалён → копия на месте, `verify` = в порядке; хэш копии = хэш исходного |
| US2-1/2/3, FR-005, SC-002 | повторный `add` → 0 новых; копия с другим именем → `existing`; то же имя, другое содержимое → `added` + `name_collision` |
| US3-1…4, FR-007 | цифровой → все `text`; из картинок → все `scan`; смешанный → по страницам; картинка + невидимый текст → `scan_with_text`; картинка полосами → `scan`/`scan_with_text`; маленький логотип + текст → `text`; пустая страница → `scan` |
| US4-1/2/3, FR-008, FR-010 | `list`/`show` содержат все поля; новые документы — все этапы «ожидает» |
| US5-1/2/3, FR-011 | `remove --yes` → нет документа, страниц, состояний, копии; `run` остался; запись в `deletion_log`; повторный `add` → новый ID; неподтверждённое удаление ничего не меняет |
| FR-003 | ID `D-0001`… по порядку; после удаления последнего новый документ получает следующий номер |
| FR-009 | число файлов в отчёте = числу входных файлов; у каждого ровно один `status` |
| FR-012 | у каждого `add`/`reclassify` есть `run` с `code_version` и `settings` |
| Крайние случаи | пароль, повреждённый, нулевой размер, 0 страниц → `rejected`; > `large_file_pages` → `large_file`; прерывание между копией и транзакцией → повторный запуск добавляет файл, лишних документов нет |
| FR-013, принцип I | база с нелокальным хостом и папка данных внутри репозитория → код 2 |

### Ручной прогон на синтетике

> С ИИ-агентом — только в одноразовой папке данных и отдельной базе
> (`DOCREADER_DATA_DIR=/tmp/docreader-demo-data`, `docreader_demo`), не в рабочих.

```
uv run python -m tests.synthetic.make_pdfs /tmp/docreader-demo   # генерирует набор файлов
uv run docreader add /tmp/docreader-demo
uv run docreader add /tmp/docreader-demo        # второй раз
uv run docreader list
uv run docreader show D-0001
uv run docreader remove D-0001                  # ввести не тот ID → отмена
uv run docreader remove D-0001 --yes
uv run docreader verify
```

Ожидается:
- первый `add`: добавлены все PDF, отклонены DOCX/JPEG/PNG/пароль/повреждённый/пустой
  с причинами; у смешанного и сканов — предупреждения с номерами страниц;
- второй `add`: «Добавлено: 0», все PDF в группе «Уже есть» с прежними ID;
- `list`: все этапы «ожидает», столбцы видов страниц сходятся с отчётом;
- `show`: путь к копии существует, `shasum -a 256 <путь>` (на Linux — `sha256sum <путь>`) совпадает с выведенным отпечатком;
- после `remove --yes` документа нет в `list`, `verify` проходит для остальных.

## Б. Реальные договоры (только аналитик, без агента)

### SC-001, SC-002, SC-003, SC-005

```
time docreader add /путь/к/50-договорам
docreader add /путь/к/50-договорам
docreader verify
```

- Итог первого запуска: «добавлено + уже есть + не добавлено = всего файлов»; каждый
  не добавленный файл — с причиной (SC-001).
- Второй запуск: «Добавлено: 0» (SC-002).
- `verify`: «Копии в порядке: N», где N — число документов (SC-003).
- Время первого запуска ≤ 5 минут (SC-005).

### SC-004 — вид страниц на 10 договорах

1. Выбрать 10 договоров, по возможности с подписными сканами и фоновыми картинками.
2. Разметить вид каждой их страницы вручную в `$DOCREADER_DATA_DIR/labels/page-kinds.csv`
   (формат — [contracts/cli.md](contracts/cli.md#docreader-page-kinds-check-labelscsv)).
3. `docreader page-kinds-check $DOCREADER_DATA_DIR/labels/page-kinds.csv`
4. Если точность < 95%: посмотреть показатели несовпавших страниц, поправить пороги
   в `$DOCREADER_DATA_DIR/settings.toml`, выполнить `docreader reclassify`, повторить шаг 3.
5. Записать итоговые пороги в `docs/tech-context.md`; цифру точности — в таблицу
   результатов (фича 02), не в репозиторий.

### SC-006

`docreader show D-XXXX` → открыть выведенный путь к копии (`open <путь>`): открывается
тот же договор.

### Сеть (FR-013)

Выполнить `add` при выключенном Wi-Fi — команда работает так же.
