# Feature Specification: Приём документов и реестр договоров

**Feature Branch**: `001-document-intake`

**Created**: 2026-11-15

**Status**: Draft

**Input**: User description: "Часть A файла docs/features/01-document-intake.md: пользователь указывает папку или файл с договорами; система регистрирует каждый договор в реестре, присваивает постоянный идентификатор, сохраняет неизменённую копию файла, определяет вид каждой страницы (готовый текст / скан) и показывает список договоров с состоянием по этапам обработки."

## Суть и назначение

Пользователь указывает папку или файл с договорами. Система регистрирует каждый договор
в реестре: присваивает постоянный идентификатор, сохраняет собственную неизменённую копию
файла и определяет, какие страницы содержат готовый текст, а какие являются сканами.
Пользователь может посмотреть список договоров и состояние каждого по этапам обработки.

**Зачем.** Все последующие этапы (чтение, извлечение, поиск, ответы) ссылаются на документ
по идентификатору и должны уметь вернуться к исходному файлу (принцип II конституции).
Реестр — единственное место, где известно, какие документы есть в системе и что с каждым
уже сделано. Разделение страниц на «готовый текст» и «скан» заранее показывает, какие
страницы можно читать, а какие на первом этапе останутся непрочитанными
(ограничение «только PDF с извлекаемым текстом»).

**Пользователь.** Один аналитик, который ведёт проверку концепции на своём ноутбуке.
Приём документов выполняется из командной строки.

## Clarifications

### Session 2026-11-15

- Q: По каким этапам обработки реестр ведёт состояние документа? → A: Пять этапов по документу: чтение (03), структура (04), извлечение (05), проверки (06), индексация (07); новый этап добавляется в список вместе со своей фичей.
- Q: Каким должен быть идентификатор документа? → A: Сквозной номер с префиксом `D-0001`, `D-0002`, … по порядку добавления; повторно не используется.
- Q: Что делать с записями о запусках обработки при удалении документа? → A: Удаляются документ, копия, страницы, состояния этапов и все результаты по нему; записи о запусках остаются; факт удаления записывается в журнал (какой документ, когда).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Добавить папку договоров (Priority: P1)

Аналитик указывает папку (или отдельный файл) с договорами и получает отчёт: какие файлы
добавлены и с какими идентификаторами, какие пропущены и почему.

**Why this priority**: Без регистрации документов не работает ни один последующий этап;
это минимальная ценность фичи.

**Independent Test**: Достаточно папки с несколькими файлами и просмотра отчёта
о добавлении.

**Acceptance Scenarios**:

1. **Given** папка с пятью PDF-файлами, которых нет в реестре, **When** аналитик
   добавляет папку, **Then** в реестре появляется пять документов, у каждого есть
   идентификатор, исходное имя файла и число страниц.
2. **Given** в папке есть файл неподдерживаемого формата, **When** аналитик добавляет
   папку, **Then** остальные файлы добавлены, а этот указан в отчёте с причиной
   «формат не поддерживается».
3. **Given** документ добавлен, **When** исходный файл в папке пользователя перемещён
   или удалён, **Then** система по-прежнему имеет доступ к своей копии, побайтно
   совпадающей с исходным файлом на момент добавления.

---

### User Story 2 - Повторное добавление не создаёт дубликатов (Priority: P1)

Аналитик повторно добавляет ту же папку, например после того, как положил в неё новые
файлы. Уже известные документы не дублируются.

**Why this priority**: Набор пополняется постепенно; дубликаты исказили бы все замеры
последующих этапов (принцип VI: повторный запуск не создаёт дубликатов).

**Independent Test**: Добавить папку дважды и сравнить число документов в реестре.

**Acceptance Scenarios**:

1. **Given** папка уже добавлена, **When** аналитик добавляет её снова без изменений,
   **Then** число документов в реестре не меняется, а отчёт показывает для каждого
   файла «уже есть» и его идентификатор.
2. **Given** файл с тем же содержимым, но другим именем, **When** аналитик его
   добавляет, **Then** новый документ не создаётся; отчёт указывает на существующий.
3. **Given** файл с тем же именем, но другим содержимым, **When** аналитик его
   добавляет, **Then** создаётся новый документ, а отчёт предупреждает о совпадении
   имён.

---

### User Story 3 - Определение вида страниц (Priority: P1)

При добавлении система определяет для каждой страницы, как её нужно будет читать:
страница с готовым текстом, скан без текста или скан со встроенным текстом сомнительного
качества.

**Why this priority**: На первом этапе сканы не распознаются; аналитик должен заранее
знать, какие страницы не будут прочитаны, а не обнаружить это по пропускам в результатах
(принцип VII: ничто не отбрасывается молча).

**Independent Test**: Добавить один цифровой PDF, один скан и один смешанный файл
и посмотреть результат по страницам.

**Acceptance Scenarios**:

1. **Given** PDF, выгруженный из текстового редактора, **When** он добавлен,
   **Then** все его страницы помечены как «готовый текст».
2. **Given** PDF, полученный со сканера, **When** он добавлен, **Then** все его
   страницы помечены как «скан».
3. **Given** PDF, в котором основная часть выгружена из редактора, а страница
   с подписями отсканирована, **When** он добавлен, **Then** страницы помечены
   по отдельности, и страница с подписями помечена как «скан».
4. **Given** скан, в который сканер встроил распознанный текст, **When** он добавлен,
   **Then** его страницы помечены как «скан со встроенным текстом», а не как
   «готовый текст».

---

### User Story 4 - Посмотреть реестр (Priority: P2)

Аналитик смотрит список документов: идентификатор, имя, число страниц, сколько страниц
каждого вида, состояние по каждому этапу обработки. Может запросить сведения об одном
документе по идентификатору.

**Why this priority**: Нужен для контроля хода работы, но приём документов ценен
и без него (отчёт о добавлении уже содержит основные данные).

**Independent Test**: После добавления документов вывести список и сведения об одном
документе.

**Acceptance Scenarios**:

1. **Given** в реестре есть документы, **When** аналитик запрашивает список,
   **Then** для каждого документа видны идентификатор, исходное имя, число страниц,
   число страниц каждого вида и состояние каждого этапа.
2. **Given** документ только что добавлен, **When** аналитик смотрит список,
   **Then** все этапы обработки для него показаны как «ожидает».
3. **Given** аналитик указывает идентификатор, **When** он запрашивает сведения
   об одном документе, **Then** он видит те же данные и вид каждой страницы.

---

### User Story 5 - Удалить документ (Priority: P3)

Аналитик удаляет документ, добавленный по ошибке, вместе со всем, что система по нему
накопила.

**Why this priority**: Нужен редко; без него можно обойтись на прототипе.

**Independent Test**: Добавить документ, удалить его и убедиться, что его нет в списке.

**Acceptance Scenarios**:

1. **Given** документ есть в реестре, **When** аналитик удаляет его и подтверждает
   действие, **Then** документ, его копия и все связанные с ним результаты исчезают
   из системы, записи о запусках сохраняются, а в журнале появляется запись
   об удалении.
2. **Given** документ удалён, **When** аналитик добавляет тот же файл снова,
   **Then** он добавляется как новый документ с новым идентификатором.
3. **Given** аналитик запросил удаление, **When** он не подтвердил действие,
   **Then** ничего не удаляется.

---

### Минимальная версия для сквозного прототипа

Сценарии 1 и 2 для PDF, вид страницы в упрощённом виде («есть текст» или «нет текста»),
список документов с идентификатором и числом страниц. Удаление и заметки — позже.

### Edge Cases

- Файл защищён паролем или повреждён: не добавляется, причина указана в отчёте.
- Файл без страниц или нулевого размера: не добавляется, причина указана.
- Файл Word или изображение (JPEG, PNG): не добавляется, в отчёте указана причина
  и предложено сохранить документ в PDF.
- В документе есть страницы вида «скан»: документ добавляется, отчёт предупреждает,
  что такие страницы на первом этапе не читаются, и называет их номера.
- В документе есть страницы вида «скан со встроенным текстом»: документ добавляется,
  отчёт предупреждает, что текст получен распознаванием и может содержать ошибки.
- Очень большой файл (более 200 страниц): добавляется, отчёт предупреждает о размере.
- Папка содержит вложенные папки: файлы из них тоже добавляются.
- Страница содержит казахские буквы: на этом этапе не проверяется; проверка относится
  к чтению (фича 03).
- Файл является дополнительным соглашением к другому договору: система этого
  не распознаёт и регистрирует его как самостоятельный документ.
- Добавление прервано на середине папки: уже добавленные документы остаются,
  повторный запуск добавляет оставшиеся; частично добавленных документов не остаётся.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система должна принимать на вход путь к файлу или к папке, включая
  вложенные папки.
- **FR-002**: Система должна поддерживать PDF; файлы других форматов не добавляются
  и попадают в отчёт с причиной.
- **FR-003**: Система должна присваивать каждому документу постоянный идентификатор
  вида `D-0001`: префикс `D-` и сквозной номер по порядку добавления. Идентификатор
  не меняется в течение жизни документа и не используется повторно, в том числе
  после удаления документа.
- **FR-004**: Система должна хранить собственную копию исходного файла, побайтно
  совпадающую с исходным, и никогда её не изменять.
- **FR-005**: Система должна распознавать повторное добавление по содержимому файла,
  независимо от имени, и не создавать второй документ.
- **FR-006**: Система должна сохранять для документа исходное имя файла, число страниц,
  дату добавления и необязательную заметку пользователя.
- **FR-007**: Система должна определять для каждой страницы PDF её вид: «готовый текст»,
  «скан» или «скан со встроенным текстом», и показывать в отчёте число страниц каждого
  вида по каждому документу.
- **FR-008**: Система должна вести для каждого документа состояние по каждому этапу
  обработки документа — чтение, структура, извлечение, проверки, индексация:
  «ожидает», «готово», «требует просмотра», «ошибка»; для двух последних обязательна
  причина. Этапы, работающие с вопросами (ответы), в состояние документа не входят.
  Новый этап добавляется в перечень вместе со своей фичей.
- **FR-009**: Система должна выдавать после каждого добавления отчёт, в котором каждый
  входной файл отнесён ровно к одной группе: добавлен, уже есть, не добавлен
  (с причиной). Предупреждения (сканы, распознанный текст, совпадение имён, размер)
  указываются дополнительно к группе.
- **FR-010**: Система должна показывать список документов и сведения об одном документе
  по идентификатору.
- **FR-011**: Система должна удалять документ только после явного подтверждения.
  Удаляются документ, его копия, страницы, состояния этапов и все результаты по нему.
  Записи о запусках (FR-012) сохраняются. Факт удаления записывается в журнал:
  идентификатор документа, исходное имя файла, время удаления.
- **FR-012**: Система должна фиксировать каждый запуск обработки: когда, какой этап,
  какой версией кода и с какими настройками. Этой записью пользуются все последующие
  фичи.
- **FR-013**: Система должна работать без подключения к сети и не передавать
  содержимое файлов за пределы машины.

### Key Entities *(include if feature involves data)*

- **Документ**: Один договор. Идентификатор, исходное имя файла, отпечаток содержимого,
  число страниц, дата добавления, заметка. Предусмотрена ссылка на родительский
  документ; на первом этапе она всегда пуста.
- **Страница**: Принадлежит документу. Номер, вид страницы.
- **Состояние этапа**: Для пары «документ, этап»: состояние и причина.
- **Запуск**: Одно выполнение этапа обработки: время, этап, версия, настройки, метка.
  Не удаляется при удалении документов.
- **Запись об удалении**: Идентификатор удалённого документа, исходное имя файла,
  время удаления.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Все 50 договоров эталонного набора добавляются одной командой; каждый
  файл либо добавлен, либо указан в отчёте с причиной; ни один файл не пропущен
  без записи.
- **SC-002**: Повторное добавление той же папки создаёт ноль новых документов.
- **SC-003**: Для 100% добавленных документов копия в системе побайтно совпадает
  с исходным файлом.
- **SC-004**: На выборке из 10 договоров, проверенных вручную, вид страницы определён
  верно не менее чем для 95% страниц.
- **SC-005**: Добавление 50 договоров занимает не более 5 минут на ноутбуке
  пользователя.
- **SC-006**: Аналитик может по идентификатору из любого последующего результата
  открыть исходный файл.

## Вне рамок

- Чтение текста и разбор структуры (фичи 03–04).
- Распознавание сканов.
- Связи между документами, в том числе «договор — дополнительное соглашение».
- Определение типа договора и языка документа.
- Права доступа, несколько пользователей.
- Графический интерфейс (список документов на веб-экране — фича 12).
- Автоматическое отслеживание папки и загрузка из почты или других систем.

## Assumptions

- Договоры поступают как файлы PDF с извлекаемым текстом, один файл — один договор.
- Приложения к договору находятся в том же файле, что и сам договор.
- Объём набора — десятки документов; скорость приёма не критична.
- Порог «очень большого файла» для предупреждения — более 200 страниц (в исходном
  описании — «сотни страниц»); значение может быть уточнено в плане.
- Идентификатор удалённого документа повторно не выдаётся, поэтому ссылки в старых
  результатах не могут указать на другой документ.
- Папка данных (копии файлов, реестр) находится вне репозитория (раздел
  «Разработка с ИИ-агентом» конституции).
