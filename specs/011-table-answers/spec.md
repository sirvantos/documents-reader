# Feature Specification: Ответ по таблице через фиксированные фильтры

**Feature Branch**: `011-table-answers`

**Created**: 2026-11-27

**Status**: Draft

**Input**: User description: "Фича 10 «Ответ по таблице через фиксированные фильтры»
(docs/features/10-table-answers.md), в минимальной версии: действия «посчитать»
и «перечислить» с одним условием по шести полям прототипа. Остальная часть файла фичи —
раздел «Следующая итерация» спецификации (вне рамок). Языковая модель переводит вопрос
в запрос из заранее разрешённых частей, программа проверяет его и выполняет по всем
договорам набора; ответ показывает результат, применённое условие простыми словами,
список договоров со ссылкой на пункт и сколько договоров не учтено и почему."

## Суть и назначение

На вопросы «сколько договоров…» и «какие договоры…» система отвечает **по таблице
полей** (фичи 05 и 06), а не по тексту. Языковая модель только переводит вопрос
в **запрос** из заранее разрешённых частей: одно **условие** по одному из шести полей
прототипа (поле, сравнение, значение) и одно **действие** — «посчитать» или
«перечислить». Программа проверяет запрос и выполняет его по всем договорам набора.
Ответ показывает результат, применённое условие простыми словами, список договоров
со ссылкой на пункт, откуда взято значение, и сколько договоров не учтено и почему.

**Зачем.** Ответ по тексту (фичи 08, 09) видит несколько лучших отрывков, а не весь
набор, и на вопрос о количестве даёт уверенный, но неверный ответ. Таблица перебирает
все договоры, и ответ точен настолько, насколько точны поля. Запрос из фиксированных
частей вместо произвольного запроса, написанного моделью, нужен, чтобы ошибку перевода
нельзя было не заметить: аналитик видит условие и проверяет его, а все числа считает
программа (конституция, принцип VII: модель — только для разбора вопроса).

**Пользователь.** Один аналитик на своём ноутбуке, из командной строки — так же, как
он задаёт вопросы по тексту (фича 09). Веб-экран — фича 12.

**Что уже есть.** Для 56 договоров рабочего набора извлечены шесть полей (фича 05),
у каждого значения — приведённый вид, цитата и пункт договора. У каждого поля есть
статус фичи 06 («принято», «требует просмотра», «отклонено», «не найдено») и, если
аналитик решал карточку очереди, его решение; **действующее значение** поля — решение
аналитика, пока оно в силе, иначе значение со статусом «принято», иначе значения нет
(фича 06, research R-8). Замер фичи 06 (2026-11-27): все 336 полей рабочего набора
«принято».

**Поля и сравнения минимальной версии.** Шесть полей прототипа (docs/field-catalog.md):

| Поле | Сравнения |
|---|---|
| номер договора | «равно» |
| краткое наименование заказчика | «равно» (правило сопоставления наименований — FR-005) |
| краткое наименование подрядчика | «равно» (то же правило) |
| цена без НДС | «больше», «не меньше», «меньше», «не больше», «равно» |
| цена с НДС | те же |
| дата окончания действия договора | «до», «после», «в периоде» (обе границы включаются) |

Значение условия приводится к виду поля теми же правилами, что значения фичи 05.

**Процесс перед clarify** (CLAUDE.md, «Delivery»). Как сопоставлять наименование из
вопроса с таблицей, зависит от того, как одни и те же стороны записаны в разных
договорах. Поэтому до `/speckit.clarify` главная сессия пишет
`scripts/survey_table_answers.py` (только числа и доли: сколько разных кратких
наименований у заказчиков и подрядчиков, сколько из них совпадают по правилу сравнения
наименований фичи 02, сколько сторон встречается в нескольких договорах), аналитик
запускает его на ноутбуке и присылает числа.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Посчитать и перечислить договоры по условию (Priority: P1)

Аналитик задаёт вопрос на подсчёт или перечисление: «сколько договоров с подрядчиком
X?», «какие договоры дороже миллиона с НДС?», «какие договоры заканчиваются до
1 июня 2026 года?». Система переводит вопрос в запрос, показывает применённое условие
простыми словами, считает или перечисляет договоры по всему набору и для каждого
договора называет значение и пункт, откуда оно взято.

**Why this priority**: Это и есть фича: точный ответ на вопрос о наборе, который поиск
по тексту дать не может.

**Independent Test**: На синтетических договорах с известными полями задать вопросы
на подсчёт и перечисление по каждому из шести полей (модель заменена записанными
ответами) и сравнить число и список договоров с ожидаемыми.

**Acceptance Scenarios**:

1. **Given** у договоров набора есть действующие значения полей, **When** аналитик
   спрашивает «сколько договоров с подрядчиком X?», **Then** он получает число,
   посчитанное программой по всем договорам набора, и список этих договоров.
2. **Given** вопрос «какие договоры дороже 1 000 000 рублей с НДС?», **When** аналитик
   задаёт его, **Then** он получает список договоров: идентификатор, номер договора,
   стороны, значение поля условия и пункт, откуда оно взято.
3. **Given** ответ получен, **When** аналитик его читает, **Then** он видит применённое
   условие простыми словами: поле, сравнение и значение в приведённом виде; для
   относительных дат («в этом году», «до конца квартала») — точные даты.
4. **Given** по условию с наименованием стороны совпали несколько разных написаний
   из таблицы, **When** аналитик читает ответ, **Then** он видит, какие наименования
   система сочла совпадающими.
5. **Given** условию не соответствует ни один договор, **When** аналитик получает
   ответ, **Then** ответ — «таких договоров нет» с применённым условием.
6. **Given** один и тот же вопрос задан дважды на тех же данных, **When** модель
   перевела его в тот же запрос, **Then** число и список договоров совпадают.

### User Story 2 - Полнота данных (Priority: P1)

Ответ честно говорит, на скольких договорах он построен: какие договоры не учтены,
потому что у них нет действующего значения поля условия, и почему. По умолчанию
учитываются только действующие значения; аналитик может попросить учесть и значения,
ждущие просмотра, — тогда ответ помечается как включающий непроверенные значения.

**Why this priority**: Без сведений о полноте число из таблицы так же обманчиво, как
число из поиска по тексту: «4 договора» при 10 неучтённых — неверный ответ
(конституция, принцип VII: ничто не отбрасывается молча).

**Independent Test**: На синтетических договорах, где у части поле «требует
просмотра», «отклонено», «не найдено», не извлечено или проверки устарели, задать
вопрос и сравнить число неучтённых договоров по причинам с ожидаемым; повторить
с просьбой учесть непроверенные значения.

**Acceptance Scenarios**:

1. **Given** у части договоров поле условия «требует просмотра», «отклонено» или «не
   найдено», **When** аналитик получает ответ, **Then** в ответе указано, сколько
   договоров не учтено, по каждой причине, и доступен их список.
2. **Given** у договора нет извлечённых полей или проверки фичи 06 не выполнены или
   устарели, **When** аналитик получает ответ, **Then** договор не учтён и это названо
   отдельной причиной (как «договоров с устаревшими проверками» в сводке фичи 06).
3. **Given** аналитик просит учесть и значения, ждущие просмотра, **When** ответ
   пересчитан, **Then** в него входят и значения «требует просмотра», ответ помечен
   как включающий непроверенные значения, а такие договоры отмечены в списке.
   Значения «отклонено» (цитата не подтверждена) не учитываются и в этом случае
   (конституция, принцип III).
4. **Given** аналитик исправил значение в очереди фичи 06, **When** он задаёт вопрос,
   **Then** используется исправленное значение и в списке видно, что оно исправлено
   человеком.

### User Story 3 - Вопрос, на который таблица не отвечает (Priority: P2)

Система не подменяет подсчёт догадкой: если нужного сведения нет среди полей, если
вопрос неоднозначен или требует того, чего минимальная версия не умеет, она говорит
это прямо и называет, чего не хватает.

**Why this priority**: Уверенный неверный ответ хуже отказа (конституция, принцип IV);
но основная ценность — в User Story 1 и 2.

**Independent Test**: На синтетических договорах задать вопросы о свойстве вне шести
полей, неоднозначный вопрос, вопрос с действием «сложить» и с двумя условиями,
и подставить ответ модели с полем вне набора; сравнить исходы с ожидаемыми.

**Acceptance Scenarios**:

1. **Given** вопрос требует сведения, которого нет среди шести полей («сколько
   договоров с предоплатой?»), **When** аналитик задаёт его, **Then** система отвечает,
   что точно посчитать не может, называет недостающее сведение и не подменяет подсчёт
   поиском по тексту.
2. **Given** вопрос неоднозначен («крупные договоры», «недавние договоры»), **When**
   аналитик задаёт его, **Then** система не подставляет порог сама, а просит его
   уточнить.
3. **Given** модель составила запрос с полем, сравнением или действием вне
   разрешённого набора или со значением, которое не приводится к виду поля, **When**
   программа его проверяет, **Then** запрос отклоняется и аналитик видит причину.
4. **Given** вопрос требует действия вне минимальной версии («на какую сумму все
   договоры?», «какой самый крупный?», «сколько у каждого подрядчика?») или двух
   условий, **When** аналитик задаёт его, **Then** система отвечает, что такой запрос
   пока не поддерживается, и называет, чего не хватает.
5. **Given** вопрос содержит два разных запроса, **When** аналитик задаёт его,
   **Then** выполняется первый, а о втором сообщается.

---

### Edge Cases

- **Наименование в вопросе неполное или с другой организационной формой**: сопоставление
  по FR-005; в ответе перечислены совпавшие наименования из таблицы.
- **Одна организация записана в разных договорах по-разному**: совпадение по
  наименованию ненадёжно, ИНН среди шести полей нет; видно по списку совпавших
  наименований. Отбор по ИНН — следующая итерация.
- **Наименование в вопросе без указания стороны** («договоры с X»): если сторона
  не следует из вопроса, система просит уточнить, заказчик это или подрядчик.
- **Относительные даты** («в этом году», «за последний квартал»): переводятся в точные
  даты от сегодняшнего дня; точные даты показаны в условии.
- **Номер договора в вопросе записан иначе** (другие пробелы, «№»): приводится теми же
  правилами, что номер фичи 05; совпадение — по приведённому виду.
- **Сумма в вопросе словами или с сокращениями** («миллион», «1,5 млн», «500 тыс.»):
  модель записывает значение числом, программа приводит его к виду суммы; не
  приводится — запрос отклоняется (сценарий 3.3).
- **Сумма равна границе** («не меньше миллиона», цена ровно 1 000 000,00): граница
  включается или нет строго по сравнению; «больше» и «не меньше» различаются.
- **Длинный список**: в терминале показаны первые записи и общее число; полный список —
  в машиночитаемом выводе команды.
- **Модель недоступна или вернула ответ не по формату**: команда останавливается
  с понятной причиной; на сервере разработки — кодом 2 (запрет моделей), как вопросы
  по тексту.
- **Ни у одного договора набора нет извлечённых полей**: ответ «по таблице ответить
  нельзя» с причиной, не «0 договоров».
- **Вопрос не о договорах вообще**: отказ с причиной (как вопрос без нужного поля).

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001.** Система должна переводить вопрос в один из исходов: **запрос** (одно
  условие — поле из шести, сравнение из разрешённых для поля, значение — и одно
  действие: «посчитать» или «перечислить»), **отказ** с названием недостающего
  сведения, **просьба уточнить** с тем, что уточнить, или **не поддерживается**
  с тем, чего не хватает.
- **FR-002.** Система должна выполнять запрос программой по всем договорам набора
  и только по действующим значениям поля условия (FR-008).
- **FR-003.** Система должна отклонять запрос с полем, сравнением или действием вне
  разрешённого набора и со значением, которое не приводится к виду поля, и называть
  причину.
- **FR-004.** Все числа ответа (число договоров, число неучтённых по причинам) должны
  быть получены вычислением программы; языковая модель чисел ответа не пишет.
- **FR-005.** Краткое наименование стороны из вопроса должно сопоставляться
  с наименованиями таблицы правилом сравнения кратких наименований фичи 02
  (без учёта регистра, организационная форма в сокращённом виде, наименование
  в кавычках и его инициалы совпадают); совпавшие наименования показываются в ответе.
  Будет ли сопоставление шире (по части названия), решается в clarify по числам
  опроса.
- **FR-006.** Каждый ответ должен показывать применённое условие простыми словами,
  со значением в приведённом виде и точными датами вместо относительных.
- **FR-007.** Ответ должен содержать список договоров результата: идентификатор, номер
  договора, краткие наименования сторон, значение поля условия и ссылку на пункт,
  откуда оно взято; для «посчитать» список тоже доступен (SC-005).
- **FR-008.** По умолчанию учитываются только действующие значения фичи 06; по просьбе
  аналитика учитываются и значения «требует просмотра», ответ помечается как
  включающий непроверенные значения, такие договоры отмечаются в списке. Значения
  «отклонено» не учитываются никогда.
- **FR-009.** Ответ должен сообщать, сколько договоров набора не учтено, по причинам:
  поле «не найдено», «требует просмотра», «отклонено», поле не извлечено, проверки
  фичи 06 не выполнены или устарели; список неучтённых договоров доступен.
- **FR-010.** Система должна отказывать в подсчёте, когда нужного сведения нет среди
  шести полей или поле — свободный текст, и не подменять подсчёт поиском по тексту.
- **FR-011.** Система должна просить уточнение вместо подстановки собственных порогов
  и допущений (размер «крупного» договора, сторона договора, период «недавно»).
- **FR-012.** Повторный вопрос на тех же данных, переведённый в тот же запрос, должен
  давать то же число и тот же список в том же порядке.
- **FR-013.** Ответ ничего не записывает в базу (как вопросы по тексту, фича 09);
  с ответом показываются его исход, число договоров и время.
- **FR-014.** Конфиденциальность (конституция, принцип I): вывод команды содержит
  значения договоров (наименования, номера, суммы) и на реальных договорах агенту
  не отправляется — как ответы по тексту и поля; первая строка (исход, числа, время)
  может быть отправлена.
- **FR-015.** Для замера SC-001 должен быть способ прогнать файл вопросов аналитика
  с ожидаемыми ответами (в папке данных, как у фич 08 и 09) и получить сводку, где
  программа сама сравнивает число и список договоров с ожидаемыми; сводка — только
  числа и идентификаторы.

### Key Entities

- **Запрос к таблице.** Действие («посчитать» или «перечислить») и одно условие: поле
  из шести, сравнение, значение в приведённом виде (для «в периоде» — две даты).
  Создаётся моделью из вопроса, проверяется программой.
- **Исход перевода.** Запрос, отказ (недостающее сведение), просьба уточнить (что
  уточнить), не поддерживается (чего не хватает) или ошибка (модель недоступна,
  ответ не по формату).
- **Ответ по таблице.** Исход; применённое условие простыми словами; число договоров;
  список договоров со значениями и пунктами; совпавшие наименования; неучтённые
  договоры по причинам; пометка «включает непроверенные значения»; время.
- **Используемые данные (не меняются).** Значения полей фичи 05 (значение, цитата,
  пункт), статусы, решения и действующие значения фичи 06.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001.** Не менее 90% вопросов аналитика вида «ответ из таблицы» получают верный
  ответ (верные число и список договоров либо верный отказ или просьба уточнить)
  при верных полях. Ориентир; уточняется после первого замера.
- **SC-002.** 100% чисел в ответах совпадают с результатом вычисления программы
  по действующим значениям (проверяется автотестами на синтетике).
- **SC-003.** 100% ответов-запросов показывают применённое условие; 100% отказов,
  просьб уточнить и «не поддерживается» называют причину.
- **SC-004.** Ответ формируется не более чем за 20 секунд на ноутбуке аналитика
  (медиана по вопросам замера; ориентир).
- **SC-005.** Для любого ответа-запроса доступен полный список договоров, из которых
  он сложился, и полный список неучтённых договоров.
- **SC-006.** На синтетических договорах, где у части поле условия не действующее
  (каждая причина FR-009), число неучтённых по каждой причине совпадает с ожидаемым
  в 100% случаев.

## Вне рамок

- Произвольные запросы к хранилищу, написанные языковой моделью.
- Пересчёт валют; графики.
- Вопросы по содержанию пунктов (фича 09) и выбор маршрута между таблицей и текстом
  (фича 11).
- Сведения из таблиц приложений.
- Юридические оценки (конституция, «Ограничения первого этапа»).

## Следующая итерация

- Действия «сложить», «наибольшее», «наименьшее», «сгруппировать» (сценарий 2 файла
  фичи), суммы отдельно по валютам (FR-009 файла фичи; поля валюты среди шести нет,
  рабочий набор — в рублях).
- Несколько условий в одном запросе.
- Условия по остальным полям, пригодным для фильтров (docs/field-catalog.md, «Поля,
  пригодные для фильтров»), по мере их извлечения в фиче 05; отбор по ИНН вместо
  наименования; дата заключения в строке списка.
- Сохранение вопроса, запроса, результата и сведений о полноте (FR-012 файла фичи)
  и прогон эталонных вопросов фичи 02 с меткой (сценарий 5 файла фичи).
- Выгрузка полного списка в файл.
- Ответы по таблице на веб-экране (фича 12).

## Assumptions

- Таблица полей заполнена и проверена правилами (фичи 05, 06); точность ответа
  ограничена точностью полей.
- Набор — все договоры реестра; договор без извлечённых полей входит в неучтённые.
- Суммы — в рублях (конституция, «Ограничения первого этапа»).
- Языковая модель — та же, что в фичах 05 и 09, через то же соединение, только
  на ноутбуке аналитика; на сервере разработки команда останавливается (запрет
  моделей). Автотесты — модель, заменённая заданными ответами, и ответы, записанные
  с настоящей модели на синтетических договорах.
- В строке списка показываются идентификатор, номер договора, обе стороны, значение
  поля условия и его пункт; даты заключения среди шести полей нет (файл фичи
  упоминает её в сценарии 1.2 — переносится в следующую итерацию).
- Просьба учесть непроверенные значения — параметр команды, не часть вопроса.
- «Сегодня» для относительных дат — дата на машине в момент вопроса.
- Файл вопросов для замера SC-001 составляет аналитик; он хранится в папке данных и
  в репозиторий не попадает.
