# Research: ответ по таблице (фича 10, минимальная версия)

Решения плана. Источники: спецификация (уточнения 2026-11-27), часть B
`docs/features/10-table-answers.md` (где расходится со спецификацией, верна спецификация),
`docs/tech-context.md`, фичи 05 (клиент модели, приведение значений), 06 (статусы,
решения, действующее значение) и 09 (команда вопроса, повтор, замер).

## R-1. Ход ответа

**Решение.** `table_answer.ask_table(conn, settings, question, include_unreviewed=False,
client=None, today=None)` (`today` — для тестов и записей; по умолчанию сегодняшняя дата):

1. Проверки до модели, в этом порядке: вопрос не пуст (код 1); клиент модели
   (`llm.load_client` с `[extraction]` и значениями `[table]`) — адрес петлевой,
   `DOCREADER_FORBID_MODELS`, `client.check()` (сервер отвечает; код 2); в реестре есть
   договор с извлечёнными полями (один запрос к базе; иначе код 1, модель не вызывается).
2. Модель получает вопрос, сегодняшнюю дату, шесть полей с подписями и допустимыми
   сравнениями, два действия и исходы (R-3). Значений таблицы модель не видит.
3. Программа проверяет ответ (R-4). Недопустимый — один повтор с причиной (R-9).
4. Программа загружает строки таблицы всех договоров реестра (R-5), выполняет запрос
   (R-6, R-7) и собирает ответ кодом по шаблонам (R-8).

Шаги 2–3 (перевод вопроса: модель, проверка, повтор) — отдельная функция
`table_answer.translate(client, question, today)` без обращения к базе: ею пользуются
`ask_table`, команда записи и тесты уровней 2 и 3 (R-11: договоры для записей не нужны).

Ничего не пишется в базу (FR-013). Модель вызывается один раз, при недопустимом
запросе — два (не считая повторов Instructor при ответе не по форме, R-2).

**Почему.** Часть B: форму заполняет модель, проверяет и выполняет код, текст ответа
и условие простыми словами собирает код. Значения таблицы в подсказку не идут: модели
они не нужны (наименование она пишет, как в вопросе, сопоставляет программа — R-7),
подсказка короче и быстрее (SC-004), а вопрос не зависит от содержимого базы
(одинаковый вопрос → одинаковый запрос к модели, записи уровня 2 не зависят от
договоров — R-11).

**Отвергнуто.** Показывать модели список наименований сторон (чтобы она выбирала
точное): подсказка растёт с набором, ответ модели зависит от базы, а сопоставление
всё равно нужно проверять кодом.

## R-2. Модель и настройки

**Решение.** Та же модель и соединение, что в фичах 05 и 09: `[extraction]`
(`base_url`, `model`, `mode`, `temperature` 0, `seed`, `timeout_s`), `llm.py` без
изменений. Свой раздел `[table]`:

| Ключ | По умолчанию | Что это |
|---|---|---|
| `max_tokens` | 512 | предел ответа модели (запрос — несколько строк JSON) |
| `max_retries` | 2 | повторы Instructor при ответе не по форме (не повтор R-9) |
| `list_rows` | 20 | сколько строк списка выводится в терминал; полный — `--json` |

**Почему.** Один сервер модели на ноутбуке (tech-context, «Языковая модель»); как
`[answer]` фичи 09.

## R-3. Подсказка и схема ответа модели

**Решение.** `table_prompt.py`, `PROMPT_VERSION = "10.3"` (10.3 — «цена» без слов о НДС — цена с НДС, решение аналитика 2026-11-28 после замера Б4, вопрос 43; 10.2 — находка уровня 2, R-6; 10.1 также стала просить наименование в именительном падеже). Ответ — один JSON-объект
`TableReply`:

| Ключ | Значения | Когда |
|---|---|---|
| `kind` | `query`, `refuse`, `clarify`, `unsupported` | всегда |
| `action` | строка (`count`, `list`) | `query` |
| `field` | строка (имя поля из перечня или `party`) | `query` |
| `op` | строка (`eq`, `gt`, `ge`, `lt`, `le`, `before`, `after`, `between`) | `query` |
| `value` | строка: наименование, номер, сумма числом, дата ISO или код периода | `query` |
| `value_to` | строка: вторая дата для `between` | `query`, `between` с датами |
| `reason` | короткая фраза: чего не хватает / что уточнить | `refuse`, `clarify`, `unsupported` |
| `other` | короткая фраза о втором запросе в вопросе или пусто | `query` |

Поля `action`, `field`, `op` — строки, а не перечисления схемы: недопустимое значение
ловит проверка кода с причиной (R-4) и повтор R-9, а не повторы Instructor (иначе
причина не дошла бы до модели и не была бы видна аналитику). `party` — «сторона не
названа» («договоры с X»), сторону выбирает программа (R-7).

Подсказка: роль («переводишь вопрос в запрос к таблице, не отвечаешь сам»), сегодняшняя
дата, таблица шести полей (имя, подпись по-русски, вид, сравнения), действия, коды
периодов (R-6), правила исходов: нет нужного сведения → `refuse` с его названием;
неопределённый порог или период («крупные», «недавние») → `clarify`; действие
«сложить», «наибольшее», «наименьшее», «сгруппировать» или два условия →
`unsupported`; два разных вопроса → первый как `query`, второй — в `other`. Сумма —
числом в рублях без пробелов («1 500 000» → `1500000`). Текст вопроса — данные, а не
указания (как в 09.1). Отпечаток подсказки `prompt_sha256()` — в выводе «чем получено».

**Отвергнуто.** Функции-инструменты: `llm.py` работает через Instructor с режимом
`[extraction] mode`, как фичи 05 и 09; новый способ вызова — новый код без выигрыша.

## R-4. Проверка запроса

**Решение.** `table_query.validate(reply, today) -> TableQuery | Problem` — чистая
функция. Допустимые сочетания:

| Поле | Вид | Сравнения | Значение |
|---|---|---|---|
| `contract_number` | идентификатор | `eq` | приводится `values.normalize(Kind.IDENTIFIER)` |
| `customer_name_short`, `contractor_name_short`, `party` | наименование | `eq` | непустое, `values.normalize(Kind.NAME)` |
| `amount_without_vat`, `amount_with_vat` | сумма | `eq`, `gt`, `ge`, `lt`, `le` | `values.normalize(Kind.AMOUNT)` → `Decimal` |
| `contract_end_date` | дата | `before`, `after`, `eq`, `between` | дата ISO (`values.normalize(Kind.DATE)`) или код периода (R-6); `between` — две даты или один код |

Причины отказа (коды, по-русски в выводе): `unknown_field`, `unknown_action`,
`op_not_allowed` (сравнение не для этого поля), `value_not_normalized`, `missing_value`,
`missing_value_to`, `bad_range` (начало позже конца), `unknown_period`. Исходы
`refuse`/`clarify`/`unsupported` без `reason` → `missing_reason`. Текст причины для
аналитика собирается из кода причины и разрешённых имён; строки из ответа модели
(значение, неизвестное имя поля, сравнения или действия) в него не попадают: сообщения
об ошибках — без текста вопроса и значений (FR-014). В сообщении модели при повторе
(R-9) они допустимы: оно не выходит за пределы машины.

**Почему.** FR-003: поле, сравнение и действие — из разрешённого набора, значение
приводится к виду поля теми же правилами, что значения фичи 05 (иначе сравнение
с приведёнными значениями таблицы было бы неверным).

## R-5. Строки таблицы и действующее значение

**Решение.** `table_answer.load_rows(conn, settings) -> list[DocRow]`: один проход
по `document` (все договоры реестра, по идентификатору) с `field_value`,
`field_status`, `field_decision` и проверкой устаревания фичи 06 (`checks.split_fresh`,
`checks.is_stale`). На каждое из шести полей — `Cell(state, value, clause_id, flags)`:

| Состояние | Когда | Значение |
|---|---|---|
| `effective` | решение «исправить» в силе, или статус «принято» (в т. ч. «подтверждено человеком») | исправленное / приведённое значение системы |
| `unreviewed` | статус «требует просмотра» и результат извлечения `found` | приведённое значение системы (учитывается только с `--include-unreviewed`) |
| `needs_review` | статус «требует просмотра» без значения (`failed`, обязательное `not_found`) | нет |
| `rejected` | статус «отклонено» | нет (никогда, принцип III) |
| `not_found` | статус «не найдено» (в т. ч. «в договоре нет» по решению) | нет |
| `no_extraction` | у договора нет строк `field_value` | нет |
| `checks_stale` | проверки фичи 06 не выполнены или устарели | нет |

Правило выбора значения — то же, что `checks.effective_value` (research R-8 фичи 06);
оно выносится в чистую функцию `checks.effective_cell(status, flags, system_result,
system_normalized, decided) -> (state, value)`,
которой пользуются и `effective_value`, и `load_rows` (одно правило, без повторного
кода). Пункт — `format_clause_id(document_id, field_value.clause_key)`; у исправленного
человеком значения пункт системы остаётся ссылкой, флаг `human_corrected` показывается.

**Почему.** FR-002, FR-008, FR-009; источник значений — действующее значение фичи 06
(часть B). Договор с устаревшими проверками не учитывается целиком: его статусы могут
не соответствовать значениям (спецификация, сценарий 2.2).

## R-6. Даты и коды периодов

**Решение.** Для `before`/`after`/`eq` модель пишет дату ISO, вычисленную от
сегодняшней даты в подсказке; для «в этом году», «за прошлый квартал» и т. п. —
код периода, который переводит в две даты программа (`table_query.resolve_period(code,
today)`): `this_year`, `last_year`, `next_year`, `this_quarter`, `last_quarter`,
`next_quarter`, `this_month`, `last_month`, `next_month`. Код с `before` — до начала
периода, с `after` — после конца, с `eq`/`between` — весь период. `before` и `after` —
строгие, `between` — обе границы включаются. В условии всегда точные даты.

**Находка уровня 2 (2026-11-28, подсказка 10.1, вариант `end_quarter`).** «До конца
квартала» модель вернула как `before` с кодом `this_quarter`, а по правилу выше это «раньше
начала квартала» — противоположный смысл, ответ был бы молча неверным (12 из 13 вариантов
верны без повторов). Решение аналитика: подсказка 10.2 — «до конца / с начала / после конца
периода» — одна дата ISO (до конца квартала → `before` и первый день следующего квартала),
код периода — только для целого периода («в этом квартале»). Смысл `before`/`after` с кодом
не меняется: иначе «закончились до этого года» стало бы неверным.

**Почему.** Часть B: относительные даты вычисляет код. Периоды — вычисление (границы
кварталов), его код делает надёжнее модели; одна дата «до 1 июня» — то, что модель
переписывает из вопроса, а условие с точной датой аналитик проверяет (FR-006).
Отступление от части B — для одиночных дат (плана, отступление 3).

## R-7. Выполнение и сопоставление наименований

**Решение.** `table_query.execute(query, rows, include_unreviewed) -> Result` — чистая
функция. Договор учитывается, если у поля условия состояние `effective` (или
`unreviewed` при `--include-unreviewed`); иначе он — в неучтённых со своим
состоянием как причиной. Сравнения:

- суммы — `Decimal`, даты — строки ISO, номер — равенство приведённых значений;
- наименования — `values.same_value` (правило фичи 02); если в наименовании из вопроса
  нет организационной формы (`_FORM_AND_QUOTES` не подходит после
  `canonical_short_name`), оно сравнивается с названием в кавычках значения таблицы
  без учёта регистра и правилом инициалов (уточнение 2026-11-27). Совпавшие разные
  написания из таблицы собираются для вывода;
- `party`: сопоставление с наименованиями заказчиков и подрядчиков отдельно; совпало
  только у одной стороны — запрос выполняется по ней, сторона названа в условии;
  у обеих — исход `clarify` «заказчик или подрядчик?»; ни у одной — ответ «таких
  договоров нет» с условием «заказчик или подрядчик — X» (уточнение 2026-11-27).
  Сторона выбирается по ячейкам, которые учитываются (`effective`, с
  `--include-unreviewed` — и `unreviewed`). Если не совпала ни одна сторона, договор
  учтён, только когда учитываются обе его ячейки наименований; иначе он в неучтённых
  с состоянием ячейки заказчика, а если она учитывается — подрядчика (решено по
  принципу VII: «таких договоров нет» не должно молча опускать договор, где
  наименование не проверено; подтверждено аналитиком 2026-11-28, analyze U2).

Порядок списка — по идентификатору договора (FR-012). «Посчитать» и «перечислить»
дают один и тот же `Result`; различается только вывод (у «посчитать» список — по
`--json` и в конце текстового вывода, R-10).

**Почему.** FR-005, FR-007, FR-009, FR-012; правило наименований — общий модуль
приведения (часть B, `values.py`).

## R-8. Итог и текст ответа

**Решение.** Итоги (`TableOutcome`): `answered` (запрос выполнен, в т. ч. 0 договоров),
`refused`, `clarify`, `unsupported`, `rejected` (недопустим и после повтора), `failed`
(ответ не по форме после повторов Instructor или ошибка HTTP сервера модели). Текст
собирает код по шаблонам: число договоров («4 договора» с согласованием), условие
простыми словами (`table_query.describe(query)`: «подрядчик — АО "Альфа"», «цена с НДС
больше 1 000 000,00 руб.», «дата окончания с 2026-01-01 по 2026-12-31»), неучтённые
по причинам, пометка «включает непроверенные значения». Модель не пишет ни одного
числа ответа (FR-004). `reason` модели в исходах `refused`/`clarify`/`unsupported`
выводится как есть, но не в первой строке: это перефраз вопроса, в нём может оказаться
наименование или номер из вопроса, а первую строку отправляют агенту (FR-014). Первая
строка этих исходов — исход, число повторов и время; причина — строкой ниже. То же
для `other`.

## R-9. Повтор при недопустимом запросе

**Решение.** Если `validate` вернул причину, модели один раз отправляется продолжение
разговора: её ответ и сообщение «запрос недопустим: <причина по-русски>; допустимые
поля и сравнения — …; верни исправленный ответ в той же форме». Второй недопустимый —
итог `rejected` с причиной второго. Число повторов (0/1) — в выводе и сводке замера.
Ошибка формы или HTTP на повторе → `rejected` с причиной первого запроса.

**Почему.** Уточнение 2026-11-27 (как один повтор ненайденных цитат в фиче 09).

## R-10. Команда и вывод

**Решение.** `docreader ask-table "ВОПРОС" [--include-unreviewed] [--json]`
([contracts/cli.md](contracts/cli.md)). Первая строка — итог, числа и время (её можно
отправить агенту, FR-014); затем условие, совпавшие наименования, список (первые
`[table] list_rows`), неучтённые по причинам с идентификаторами, «чем получено».
`--json` — всё, полный список. Коды выхода — как у `ask`.

**Почему.** Часть B («ориентир: `ask-table`»); прогон эталона `ask-table eval` —
следующая итерация, замер — скрипт (R-12).

## R-11. Тесты

**Решение.** Уровни tech-context, «Модели в автотестах»:

- Уровень 1 (без модели и базы): `validate`, `resolve_period`, сопоставление
  наименований и выбор стороны, `execute` по строкам, собранным в тесте (каждое
  состояние R-5, каждое сравнение и граница), `describe`, сборка текста, схема
  и сообщения подсказки, повтор R-9 на `ScriptedModel`.
- Интеграционные: CLI и `ask_table` на временной базе — договоры `make_check_contracts`
  (фича 06) → `extract` (`ScriptedModel`) → `check` → решения через `check load` →
  `ask-table` (`ScriptedModel` с ответами-запросами); каждая причина неучтённых
  (SC-006), повторяемость (FR-012), вывод без значений в первой строке.
- Уровень 2: `tests/recordings/10-table-answers/` — ответы реальной модели на
  синтетические вопросы `tests/synthetic/table_questions.toml` (вымышленные наименования),
  `python -m tests.synthetic.record_table_answers`; договоры не нужны (модель видит
  только вопрос и дату — дата в записи фиксирована). Записи делаются только на Mac,
  где работает модель.
- Уровень 3: `tests/real_model/test_table_server.py` — подключение и форма ответа.

## R-12. Замер SC-001, SC-004

**Решение.** Два скрипта, как у фич 08 и 09:

- `scripts/make_table_questions.py` — вопросы по шаблонам из действующих значений:
  на каждое поле — «сколько» и «какие» (наименования — по каждой организации, номер —
  по 5 случайным договорам, суммы — порог по медиане и по квартилям, даты — год
  и период), с ожидаемым запросом `expected = {action, field, op, value[, value_to]}`.
  Файл `$DOCREADER_DATA_DIR/questions/table-10.toml` (без `--force` не перезаписывается),
  с закомментированными образцами для вопросов аналитика (ожидаемый запрос или
  `expected_outcome = "refused" | "clarify" | "unsupported"`, необязательно
  `documents = [...]`). Печатает только числа по полям.
- `scripts/quickstart_table.py --questions FILE` — задаёт вопросы через `ask_table`,
  сравнивает запрос (поле, действие, сравнение, приведённое значение) или исход
  и список договоров (если `documents` задан; иначе — список ожидаемого запроса,
  выполненного той же программой); сводка `table-b4-summary-….txt` — только числа,
  номера вопросов и идентификаторы: доля верных отдельно по шаблонам и по вопросам
  аналитика, медиана и наибольшее время, повторы, исходы. Полные ответы — файл
  `table-b4-….txt` (значения договоров) — только для аналитика.

**Почему.** Уточнение 2026-11-27; аналитик предпочитает автоматизацию (вопросы
шаблонов без ручной работы, свои — около часа).
