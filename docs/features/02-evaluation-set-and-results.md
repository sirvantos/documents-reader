## Часть A. Описание для /speckit.specify

### Суть

Аналитик один раз вручную записывает правильные ответы: значения полей для каждого
договора, вопросы с правильными ответами и пунктами, контрольные строки для проверки
чтения. Система сравнивает с этим эталоном то, что выдал каждый этап конвейера,
считает метрики и записывает их в таблицу результатов. По таблице видно, улучшило ли
очередное изменение качество.

### Зачем

Без эталона нельзя отличить улучшение от ухудшения: любой ответ языковой модели
выглядит правдоподобно. Таблица результатов — основание для каждого решения
в проекте: оставить ли реранкер, какую модель взять, достаточно ли ноутбука.
Конституция требует замера для каждого изменения этапа; эта фича делает такой замер
одной командой.

### Пользователь

Один аналитик. Он заполняет эталон в табличном редакторе, запускает сравнение
из командной строки и читает таблицу результатов.

### Сценарии

**Сценарий 1. Загрузить эталонные значения полей (приоритет P1)**

Аналитик получает от системы пустой шаблон: строка на каждый договор, столбец
на каждое поле из каталога полей. Заполняет его вручную и загружает.

Проверяется отдельно: получить шаблон, заполнить две строки, загрузить, посмотреть
сводку загруженного.

Критерии приёмки:

1. **Дано** в реестре есть документы и задан каталог полей. **Когда** аналитик
   запрашивает шаблон. **Тогда** он получает таблицу со строкой на каждый документ
   и столбцом на каждое поле.
2. **Дано** заполненный шаблон. **Когда** аналитик загружает его. **Тогда** система
   сообщает, сколько значений загружено, сколько отмечено как «в договоре
   отсутствует» и сколько не размечено.
3. **Дано** в шаблоне есть значение неверного вида, например текст в поле даты.
   **Когда** аналитик загружает шаблон. **Тогда** система указывает строку, столбец
   и причину; остальные значения загружены.
4. **Дано** эталон уже загружен. **Когда** аналитик загружает исправленный шаблон.
   **Тогда** значения обновляются, а прежние результаты сравнений остаются
   в таблице результатов.

**Сценарий 2. Сравнить извлечённые поля с эталоном (приоритет P1)**

Аналитик запускает сравнение и получает для каждого поля один из исходов, а также
итог по каждому полю и общий.

Проверяется отдельно: загрузить эталон и набор заранее подготовленных «результатов
системы», запустить сравнение.

Критерии приёмки:

1. **Дано** эталон и результаты извлечения. **Когда** аналитик запускает сравнение.
   **Тогда** каждая пара «документ, поле» получает ровно один исход: верно, неверно,
   пропущено, придумано, не размечено или нет результата.
2. **Дано** значение в эталоне и значение системы различаются только оформлением,
   например «01.03.2025» и «1 марта 2025 г.». **Когда** выполняется сравнение.
   **Тогда** исход — «верно».
3. **Дано** в эталоне поле отмечено как отсутствующее в договоре, а система выдала
   значение. **Когда** выполняется сравнение. **Тогда** исход — «придумано».
4. **Дано** в эталоне поле отмечено как отсутствующее, и система оставила его
   пустым. **Когда** выполняется сравнение. **Тогда** исход — «верно».
5. **Дано** сравнение выполнено. **Когда** аналитик смотрит итог. **Тогда** он видит
   число и долю каждого исхода по каждому полю и в целом, причём поля с худшими
   показателями стоят первыми.

**Сценарий 3. Таблица результатов (приоритет P1)**

Каждое сравнение записывается с меткой, которую задаёт аналитик («без реранкера»,
«подсказка v3»). Аналитик смотрит историю и сопоставляет два запуска.

Проверяется отдельно: выполнить два сравнения с разными метками и сопоставить их.

Критерии приёмки:

1. **Дано** выполнено сравнение. **Когда** аналитик открывает таблицу результатов.
   **Тогда** в ней есть запись с датой, меткой, этапом, сведениями о том, чем
   получен результат, и значениями метрик.
2. **Дано** две записи одного этапа. **Когда** аналитик сопоставляет их. **Тогда**
   он видит разницу по каждой метрике и список случаев, у которых исход изменился,
   с разделением на «стало лучше» и «стало хуже».
3. **Дано** таблица результатов. **Когда** аналитик выгружает её. **Тогда** он
   получает файл, который открывается в табличном редакторе.

**Сценарий 4. Загрузить эталонные вопросы и измерить поиск (приоритет P2)**

Аналитик загружает вопросы. Для каждого указано: текст вопроса, откуда берётся ответ
(таблица, текст, оба), есть ли ответ в документах, правильный ответ, документ и
номера пунктов, где он находится, содержит ли вопрос ложную посылку. Система
измеряет, находит ли поиск правильный пункт.

Проверяется отдельно: загрузить десять вопросов и набор заранее подготовленных
результатов поиска.

Критерии приёмки:

1. **Дано** файл вопросов. **Когда** аналитик загружает его. **Тогда** система
   показывает состав набора: сколько вопросов каждого вида, сколько без ответа,
   сколько с ложной посылкой, и предупреждает, если вопросов без ответа меньше 10
   или с ложной посылкой меньше 5.
2. **Дано** вопросы и результаты поиска. **Когда** аналитик запускает сравнение.
   **Тогда** он получает долю вопросов, для которых правильный пункт оказался среди
   первых пяти результатов, и положение первого правильного результата.
3. **Дано** у вопроса указано несколько правильных пунктов. **Когда** выполняется
   сравнение. **Тогда** попаданием считается любой из них.
4. **Дано** вопрос без ответа в документах. **Когда** считаются метрики поиска.
   **Тогда** этот вопрос в них не участвует.

**Сценарий 5. Проверить чтение по контрольным строкам (приоритет P2)**

Для каждого договора аналитик записывает несколько строк, которые обязаны появиться
в прочитанном тексте дословно: номер договора, суммы, даты, ИНН. Для нескольких
договоров — ещё и список номеров пунктов. Система проверяет, все ли они нашлись.

Проверяется отдельно: загрузить контрольные строки для двух договоров и заранее
подготовленный текст.

Критерии приёмки:

1. **Дано** контрольные строки и прочитанный текст. **Когда** аналитик запускает
   проверку. **Тогда** он получает долю найденных строк в целом и по каждому
   документу, и список ненайденных.
2. **Дано** контрольная строка отличается от текста одним символом. **Когда**
   выполняется проверка. **Тогда** строка считается ненайденной, а система
   показывает ближайшее место в тексте.
3. **Дано** для договора задан список номеров пунктов. **Когда** выполняется
   проверка. **Тогда** система показывает долю пунктов, найденных с верным номером.

**Сценарий 6. Оценить ответы вручную (приоритет P3)**

Система выгружает ответы на эталонные вопросы в таблицу. Аналитик ставит по каждому
ответу четыре отметки и загружает таблицу обратно. Система считает доли.

Проверяется отдельно: выгрузить заранее подготовленные ответы, поставить отметки,
загрузить.

Критерии приёмки:

1. **Дано** есть ответы на эталонные вопросы. **Когда** аналитик запрашивает
   выгрузку. **Тогда** он получает таблицу: вопрос, ожидаемый ответ, ответ системы,
   приведённые источники и пустые столбцы для отметок.
2. **Дано** таблица с отметками. **Когда** аналитик загружает её. **Тогда** система
   считает долю ответов, которые верны, подтверждены источником, ссылаются
   на правильный источник и правильно отказались отвечать.
3. **Дано** вопрос без ответа в документах. **Когда** считается доля правильных
   отказов. **Тогда** учитываются и случаи, когда система ответила на вопрос без
   ответа, и случаи, когда она отказалась отвечать на вопрос, у которого ответ есть.

**Сценарий 7. Разобрать ошибки по этапам (приоритет P3)**

Для каждого неверного ответа аналитик указывает этап, на котором возникла ошибка:
чтение, извлечение, поиск или ответ. Система показывает распределение.

Проверяется отдельно: пометить несколько неверных ответов и посмотреть сводку.

Критерии приёмки:

1. **Дано** ответы с отметкой «неверно». **Когда** аналитик указывает для них этап.
   **Тогда** сводка показывает число ошибок по каждому этапу.
2. **Дано** неверный ответ без указанного этапа. **Когда** аналитик смотрит сводку.
   **Тогда** такие ответы показаны отдельной строкой «не разобрано».

### Особые случаи

- В эталоне пустая ячейка означает «не размечено», а не «в договоре отсутствует».
  Отсутствие обозначается явной отметкой. Неразмеченные значения не участвуют
  в метриках.
- Для поля допустимо несколько вариантов записи. В эталоне можно указать несколько
  значений; совпадение с любым — «верно».
- Поля со свободным текстом (предмет договора, условия оплаты, условия расторжения)
  и поля-списки (перечень приложений) нельзя надёжно сравнить автоматически. Они
  не участвуют в автоматических метриках и оцениваются вручную так же, как ответы в сценарии 6.
- В эталоне есть документ, которого нет в реестре: строка не загружается, причина
  указана.
- Для документа есть эталон, но этап ещё не выполнялся: такие случаи считаются
  отдельно как «нет результата» и не смешиваются с «пропущено».
- Сравнение запущено повторно с той же меткой: создаётся новая запись, прежняя
  не перезаписывается.
- Эталон изменён после сравнения: старые записи в таблице результатов помечаются
  как посчитанные по прежней версии эталона.
- Правильный пункт для вопроса указан, но разбор структуры присвоил пункту другой
  номер: попадание не засчитывается; случай виден в списке промахов.
- Вопрос относится к виду «ответ из таблицы»: в метриках поиска по тексту
  он не участвует.

### Требования

- **FR-001.** Система должна выдавать пустые шаблоны для эталонных значений полей,
  вопросов и контрольных строк, уже содержащие идентификаторы документов и названия
  полей.
- **FR-002.** Система должна различать три состояния эталонного значения: задано,
  в договоре отсутствует, не размечено.
- **FR-003.** Система должна при загрузке проверять вид значения по каталогу полей
  и сообщать об ошибках с указанием места.
- **FR-004.** Система должна сравнивать значения с учётом вида поля, не считая
  ошибкой различия в оформлении: формат даты, разделители в суммах, регистр,
  кавычки, пробелы, «е» и «ё».
- **FR-005.** Система должна относить каждую пару «документ, поле» ровно к одному
  исходу: верно, неверно, пропущено, придумано, не размечено, нет результата.
- **FR-006.** Система должна считать исходы по каждому полю и в целом; сумма исходов
  должна равняться числу пар.
- **FR-007.** Система должна хранить эталонные вопросы с признаками: вид вопроса,
  есть ли ответ, ложная посылка, правильный ответ, документ и номера пунктов.
- **FR-008.** Система должна считать для поиска долю вопросов с правильным пунктом
  среди первых пяти результатов и положение первого правильного результата.
- **FR-009.** Система должна проверять дословное присутствие контрольных строк
  в прочитанном тексте и присутствие ожидаемых номеров пунктов.
- **FR-010.** Система должна выгружать ответы для ручной оценки и принимать отметки
  обратно.
- **FR-011.** Система должна записывать каждое сравнение в таблицу результатов
  с датой, меткой, этапом, сведениями о запуске, по которому получены результаты,
  и версией эталона.
- **FR-012.** Система должна сопоставлять две записи одного этапа и показывать
  случаи с изменившимся исходом.
- **FR-013.** Система должна выгружать таблицу результатов в файл для табличного
  редактора.
- **FR-014.** Сравнение не должно обращаться к языковой модели; при одинаковых
  входных данных оно всегда даёт одинаковый результат.
- **FR-015.** Эталонные данные и результаты не должны покидать машину и попадать
  в удалённый репозиторий.

### Сущности

- **Каталог полей.** Общий справочник: имя поля, вид значения, группа. Эта фича его
  только читает.
- **Эталонное значение поля.** Документ, поле, состояние (задано, отсутствует,
  не размечено), одно или несколько допустимых значений.
- **Эталонный вопрос.** Текст, вид (таблица, текст, оба), есть ли ответ, ложная
  посылка, правильный ответ, документ и номера пунктов.
- **Контрольная строка.** Документ и строка, которая должна встретиться в тексте
  дословно. Отдельно — список ожидаемых номеров пунктов.
- **Отметка оценки.** Вопрос, запуск, четыре отметки, этап-виновник.
- **Запись результата.** Дата, метка, этап, запуск, версия эталона, метрики, исходы
  по случаям.

### Критерии успеха

- **SC-001.** Сравнение по всем 50 договорам и всем полям каталога выполняется
  менее чем за минуту.
- **SC-002.** В каждом сравнении сумма исходов равна числу пар «документ, поле».
- **SC-003.** Повторное сравнение тех же результатов с тем же эталоном даёт
  те же числа.
- **SC-004.** По любой цифре в таблице результатов можно получить список случаев,
  из которых она сложилась.
- **SC-005.** Сопоставление двух запусков показывает каждый случай, у которого
  изменился исход.
- **SC-006.** Аналитик заполняет эталон полей для одного договора без обращения
  к документации, пользуясь только шаблоном.

### Вне рамок

- Автоматическая оценка ответов языковой моделью.
- Сами этапы конвейера: эта фича только сравнивает их результаты.
- Подбор договоров и составление вопросов: это делает аналитик.
- Графики и графический интерфейс.
- Статистическая значимость различий между запусками.

### Допущения

- Эталонный набор: 50 договоров, только на русском языке, без дополнительных
  соглашений.
- Вопросов 50–100, плюс 10–15 без ответа в документах и 5–10 с ложной посылкой;
  представлены все три вида вопросов.
- Аналитик заполняет эталон в табличном редакторе.
- На 50 договорах цифры годятся, чтобы сравнивать варианты и находить слабые поля,
  но не чтобы заявлять точность с узким доверительным интервалом.

## Часть B. Технические заметки для /speckit.plan

- **Формат эталонных файлов:** CSV в UTF-8. Табличные редакторы на Mac иногда портят
  кириллицу при открытии CSV; проверить на первом же шаблоне и при необходимости
  выдавать шаблон в формате, который редактор открывает без потерь.
- **Где лежит эталон:** в папке данных вне репозитория (принцип I конституции).
  В репозитории — только синтетический пример на вымышленных договорах для тестов.
- **Версия эталона:** отпечаток содержимого загруженных файлов; записывается
  в каждую запись результата.
- **Приведение значений по виду поля:**
  - дата — к виду ГГГГ-ММ-ДД, включая запись месяца словом;
  - сумма — число без разделителей разрядов, с точкой как десятичным знаком;
  - процент, доля и число — число;
  - идентификатор (номер договора, ИНН, КПП, ОГРН, счёт) — без пробелов, регистр и вид дефисов
    и кавычек приведены;
  - наименование — регистр, кавычки, пробелы, «ё» приведены; организационная форма
    (ООО, АО, ОАО) сравнивается как часть наименования;
  - выбор из списка — точное совпадение с одним из вариантов;
  - свободный текст и список — автоматически не сравниваются.
- **Общий модуль.** Те же функции приведения нужны фиче 06 (проверки правилами).
  Вынести их в общий модуль с самого начала.
- **Правильный пункт** задаётся как идентификатор документа и номер пункта в том
  виде, как он напечатан в договоре («5.2»). Сопоставление с пунктами из фичи 04 —
  по номеру.
