## Часть A. Описание для /speckit.specify

### Суть

Каждое извлечённое значение проходит набор проверок, написанных обычным кодом:
формат, диапазон, согласованность с другими полями. По итогам значение получает
статус: «принято», «требует просмотра», «отклонено» или «не найдено». Аналитик
получает список значений, требующих просмотра, начиная с самых важных, и может
подтвердить значение, исправить его или отметить, что в договоре его нет.

### Зачем

Цитата подтверждает, что значение взято из договора, но не что оно взято из нужного
места и прочитано верно. Правила ловят то, что видно без чтения договора: ИНН
с неверным контрольным разрядом, сумма прописью, не совпадающая с суммой цифрами, дата
окончания раньше даты начала. Статусы отделяют значения, которым можно доверять
в подсчётах, от тех, что ждут человека, и сокращают ручную проверку с тысячи
с лишним значений до небольшой очереди.

### Пользователь

Один аналитик. Он запускает проверки из командной строки и работает с очередью
просмотра через выгруженную таблицу, а позже — через веб-экран.

### Сценарии

**Сценарий 1. Проверить значения и присвоить статусы (приоритет P1)**

Проверяется отдельно: запустить проверки на подготовленном наборе значений
с известными дефектами.

Критерии приёмки:

1. **Дано** извлечение выполнено. **Когда** аналитик запускает проверки. **Тогда**
   каждое поле каждого договора получает ровно один статус и перечень пройденных
   и не пройденных проверок.
2. **Дано** ИНН содержит не 10 цифр или неверный контрольный разряд. **Когда** выполняются проверки. **Тогда**
   значение получает статус «требует просмотра» с названием нарушенного правила.
3. **Дано** сумма цифрами и сумма прописью расходятся. **Когда** выполняются
   проверки. **Тогда** оба поля получают статус «требует просмотра».
4. **Дано** дата окончания раньше даты начала. **Когда** выполняются проверки.
   **Тогда** обе даты получают статус «требует просмотра».
5. **Дано** значение прошло все проверки. **Когда** выполняются проверки.
   **Тогда** статус — «принято».
6. **Дано** обязательное поле имеет результат «не найдено». **Когда** выполняются
   проверки. **Тогда** статус — «требует просмотра» с причиной «обязательное поле
   не заполнено».

**Сценарий 2. Очередь просмотра (приоритет P1)**

Проверяется отдельно: после проверок выгрузить очередь.

Критерии приёмки:

1. **Дано** есть значения со статусом «требует просмотра» или «отклонено».
   **Когда** аналитик выгружает очередь. **Тогда** он получает список: договор,
   поле, значение, цитата, пункт, страница, причина.
2. **Дано** очередь. **Когда** аналитик её читает. **Тогда** сначала идут
   обязательные поля, затем поля-фильтры, затем остальные.
3. **Дано** проверки выполнены. **Когда** аналитик смотрит сводку. **Тогда** он
   видит число значений в каждом статусе по каждому полю и в целом.

**Сценарий 3. Решение аналитика (приоритет P2)**

Проверяется отдельно: загрузить таблицу с решениями по нескольким значениям.

Критерии приёмки:

1. **Дано** значение в очереди. **Когда** аналитик подтверждает его. **Тогда**
   статус становится «принято» с отметкой «подтверждено человеком».
2. **Дано** значение в очереди. **Когда** аналитик вводит исправленное значение.
   **Тогда** исправленное значение используется дальше, а значение системы
   сохранено рядом.
3. **Дано** значение в очереди. **Когда** аналитик отмечает, что в договоре его
   нет. **Тогда** статус становится «не найдено» с отметкой «подтверждено
   человеком».
4. **Дано** решение принято. **Когда** извлечение и проверки запускаются заново.
   **Тогда** решение аналитика не теряется; если новое значение системы отличается
   от прежнего, это видно.

**Сценарий 4. Полезность правил (приоритет P2)**

Проверяется отдельно: запустить проверки на договорах, для которых есть эталон.

Критерии приёмки:

1. **Дано** проверки выполнены и есть эталон. **Когда** аналитик запрашивает отчёт
   по правилам. **Тогда** для каждого правила видно, сколько раз оно сработало
   и сколько из этих значений действительно неверны.
2. **Дано** тот же отчёт. **Когда** аналитик смотрит итог. **Тогда** он видит долю
   неверных значений, попавших в очередь, и долю верных значений, попавших в неё
   напрасно.

### Правила первой версии

Полный перечень правил и их проверка на образце — в разделе «Правила проверки»
каталога полей (`docs/field-catalog.md`); при расхождении действует каталог.

| Правило | Поля | Нарушение даёт |
|---|---|---|
| ИНН юрлица — 10 цифр, контрольный разряд верен | ИНН обеих сторон | требует просмотра |
| КПП — 9 знаков | КПП обеих сторон | требует просмотра |
| ОГРН — 13 цифр, контрольный разряд верен | ОГРН обеих сторон | требует просмотра |
| ИНН сторон различаются | ИНН обеих сторон | требует просмотра |
| Сумма цифрами равна сумме прописью | общая сумма | требует просмотра |
| Сумма положительна | общая сумма | требует просмотра |
| Валюта входит в список | валюта | требует просмотра |
| Дата находится в разумных пределах | все даты | требует просмотра |
| Подписание не позже начала, начало не позже окончания | даты | требует просмотра |
| Процент от 0 до 100 | проценты | требует просмотра |
| Ставка неустойки не выше её предела | неустойка | требует просмотра |
| Число из парного поля встречается в тексте парного текстового поля | парные поля | требует просмотра |
| Обязательные поля заполнены | номер, дата подписания, наименования сторон, сумма, валюта | требует просмотра |
| Наименования сторон различаются | наименования | требует просмотра |

### Особые случаи

- Значение уже отклонено при проверке цитаты: правила к нему не применяются,
  статус «отклонено» сохраняется.
- Результат извлечения «противоречие»: статус «требует просмотра», в очереди
  показаны все варианты.
- Правило нельзя применить, потому что нужное парное поле пусто: правило
  пропускается и отмечается как «не применялось».
- Сумма прописью записана с копейками или в сокращённом виде.
- Сумма указана без НДС и с НДС: это два разных числа, не противоречие правилу
  о сумме прописью.
- Нарушено несколько правил: в причине перечислены все.
- Договор получил состояние «требует просмотра» на чтении или разборе: все его
  значения показываются в очереди с этой пометкой.
- Каталог полей изменён: проверки для удалённых полей не выполняются, новые поля
  получают только общие проверки по виду значения.

### Требования

- **FR-001.** Система должна присваивать каждому полю каждого договора ровно один
  статус: «принято», «требует просмотра», «отклонено», «не найдено».
- **FR-002.** Система должна сохранять для каждого значения перечень проверок
  с исходом: пройдена, не пройдена, не применялась.
- **FR-003.** Система должна выполнять правила первой версии из таблицы выше.
- **FR-004.** Проверки не должны обращаться к языковой модели и должны давать
  одинаковый результат при одинаковых данных.
- **FR-005.** Система должна формировать очередь просмотра, упорядоченную
  по важности поля.
- **FR-006.** Система должна принимать решения аналитика: подтвердить, исправить,
  отметить отсутствие, и хранить их отдельно от значения системы.
- **FR-007.** Система должна сохранять решения аналитика при повторном извлечении
  и показывать, если значение системы после этого изменилось.
- **FR-008.** Система должна показывать сводку статусов и отчёт о полезности
  правил по эталону.
- **FR-009.** Новое правило должно добавляться без изменения существующих.
- **FR-010.** При сравнении с эталоном (фича 02) должны учитываться значения
  системы, а не исправления аналитика, чтобы замер отражал качество извлечения.

### Сущности

- **Правило.** Название, поля, к которым применяется, статус при нарушении.
- **Результат проверки.** Значение, правило, исход.
- **Статус поля.** Итог по значению и причины.
- **Решение аналитика.** Вид решения, исправленное значение, дата.

### Критерии успеха

- **SC-001.** 100% полей имеют ровно один статус.
- **SC-002.** Не менее 80% значений, неверных по эталону, имеют статус «требует
  просмотра» или «отклонено». Целевой ориентир; уточняется после первого замера.
- **SC-003.** Не более 20% значений, верных по эталону, попадают в очередь
  просмотра. Целевой ориентир.
- **SC-004.** Проверки для 50 договоров выполняются менее чем за минуту.
- **SC-005.** Повторный запуск даёт те же статусы.

### Вне рамок

- Проверка значений по внешним справочникам (реестр юридических лиц и подобные).
- Проверки с помощью языковой модели.
- Экран для просмотра и исправления (фича 12).
- Юридическая оценка условий.

### Допущения

- Суммы прописью записаны по-русски.
- У договора две стороны, «Заказчик» и «Подрядчик», обе — российские юридические
  лица с ИНН, КПП и ОГРН; суммы в рублях.

### Минимальная версия для сквозного прототипа

В прототип не входит. Первая рабочая версия: правила о ИНН, порядке дат
и обязательных полях; статусы; сводка.

## Часть B. Технические заметки для /speckit.plan

- **Правила как функции.** Каждое правило — отдельная функция в общем реестре:
  на входе значения полей договора, на выходе исход и пояснение. Новое правило
  добавляется регистрацией функции.
- **Приведение значений:** общий модуль из фичи 02.
- **Контрольные разряды ИНН и ОГРН.** Алгоритмы записаны в каталоге полей и проверены
  на образце; тесты — на синтетических значениях.
- **Сумма прописью.** Нужен разбор русских числительных в число, включая «тысяч»,
  «миллионов», «миллиардов» и дробную часть. Выбрать между готовой библиотекой
  и собственной функцией; покрыть тестами.
- **Разумные пределы дат:** задаются в настройках.
- **Хранение.** Результаты проверок и статус — в `field_value`; решения
  аналитика — отдельные столбцы или таблица, никогда не поверх значения системы.
- **Что считается действующим значением:** исправление аналитика, если оно есть;
  иначе значение системы со статусом «принято». Это значение используют фичи 07
  и 10.
- **Команды** (ориентир): `check [идентификатор…]`, `check summary`,
  `review export`, `review import`, `check rules-report`.
- **Тесты.** Каждое правило тестируется на подготовленных значениях без модели.
