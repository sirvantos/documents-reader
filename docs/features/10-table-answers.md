## Часть A. Описание для /speckit.specify

### Суть

На вопросы «сколько», «на какую сумму», «какие договоры», «какой самый крупный»
система отвечает по таблице полей, а не по тексту. Языковая модель переводит вопрос
в запрос из заранее разрешённых частей: условия по полям каталога и одно действие
(перечислить, посчитать, сложить, найти наибольшее или наименьшее, сгруппировать).
Запрос выполняет программа. В ответе показаны результат, применённое условие
простыми словами, список договоров и сведения о том, сколько договоров не учтено
из-за незаполненных полей.

### Зачем

Поиск по тексту возвращает несколько лучших отрывков и не видит весь набор, поэтому
на вопросы о количестве и суммах он даёт уверенный, но неверный ответ. Таблица
перебирает все договоры, и результат точен настолько, насколько точны поля.
Фиксированный набор условий и действий вместо произвольного запроса, написанного
моделью, нужен, чтобы запрос нельзя было составить неправильно незаметно: аналитик
видит применённое условие и может его проверить.

### Пользователь

Один аналитик. Он задаёт вопросы из командной строки, позже — через веб-экран.

### Сценарии

**Сценарий 1. Посчитать и перечислить (приоритет P1)**

Проверяется отдельно: задать вопрос на подсчёт по набору с заполненной таблицей.

Критерии приёмки:

1. **Дано** таблица полей заполнена. **Когда** аналитик спрашивает «в скольких
   договорах предусмотрена предоплата?». **Тогда** он получает число, посчитанное
   по всем договорам, и список этих договоров.
2. **Дано** вопрос «какие договоры заключены с подрядчиком X?». **Когда**
   аналитик задаёт его. **Тогда** он получает список договоров с номером, датой
   и суммой.
3. **Дано** ответ получен. **Когда** аналитик его читает. **Тогда** он видит
   условие, по которому отобраны договоры, записанное простыми словами.

**Сценарий 2. Сложить, найти наибольшее и наименьшее (приоритет P2)**

Проверяется отдельно: задать вопросы на сумму и на самый крупный договор.

Критерии приёмки:

1. **Дано** вопрос об общей сумме договоров. **Когда** аналитик задаёт его.
   **Тогда** суммы складываются отдельно по каждой валюте.
2. **Дано** вопрос о самом крупном договоре. **Когда** аналитик задаёт его.
   **Тогда** он получает договор с наибольшей суммой и ссылку на пункт, откуда
   взята сумма.
3. **Дано** вопрос «сколько договоров у каждого подрядчика?». **Когда**
   аналитик задаёт его. **Тогда** он получает таблицу: подрядчик и число
   договоров.

**Сценарий 3. Полнота данных (приоритет P2)**

Проверяется отдельно: задать вопрос по набору, где у части договоров поле
не заполнено.

Критерии приёмки:

1. **Дано** у части договоров нужное поле не заполнено или ждёт просмотра.
   **Когда** аналитик получает ответ. **Тогда** в ответе указано, сколько
   договоров не учтено и почему, и доступен их список.
2. **Дано** по умолчанию используются только действующие значения. **Когда**
   аналитик просит учесть и значения, ждущие просмотра. **Тогда** ответ
   пересчитывается и помечается как включающий непроверенные значения.

**Сценарий 4. Вопрос, на который таблица не отвечает (приоритет P2)**

Проверяется отдельно: задать вопрос о свойстве, которого нет в каталоге полей.

Критерии приёмки:

1. **Дано** вопрос требует поля, которого нет в каталоге. **Когда** аналитик
   задаёт его. **Тогда** система отвечает, что точно посчитать не может,
   и называет недостающее сведение.
2. **Дано** вопрос требует условия по полю со свободным текстом. **Когда**
   аналитик задаёт его. **Тогда** система отвечает, что по этому полю отбор
   не выполняется, и предлагает поиск по тексту.
3. **Дано** вопрос неоднозначен («крупные договоры»). **Когда** аналитик задаёт
   его. **Тогда** система не подставляет порог сама, а просит его уточнить.

**Сценарий 5. Прогон эталона (приоритет P3)**

Проверяется отдельно: прогнать эталонные вопросы вида «ответ из таблицы».

Критерии приёмки:

1. **Дано** эталонные вопросы загружены. **Когда** аналитик запускает прогон
   с меткой. **Тогда** ответы сохранены вместе с применёнными условиями
   и доступны для оценки через фичу 02.

### Особые случаи

- Название стороны указано в вопросе частично или с другой организационной формой:
  система показывает, какие наименования из таблицы она сочла совпадающими.
- Одна организация записана в разных договорах по-разному: совпадение
  по наименованию ненадёжно; если известен ИНН, отбор идёт по нему.
- Относительные даты («в этом году», «за последний квартал»): в применённом
  условии показаны точные даты.
- Отбору не соответствует ни один договор: ответ «таких договоров нет»
  с применённым условием.
- Результат — длинный список: показаны первые записи и общее число, полный список
  выгружается.
- Договоры в разных валютах: суммы не складываются между валютами
  и не пересчитываются.
- Модель составила запрос с полем или действием вне разрешённого набора: запрос
  отклоняется, аналитик видит причину.
- Вопрос содержит два разных запроса: выполняется первый, о втором сообщается.

### Требования

- **FR-001.** Система должна переводить вопрос в запрос из условий по полям
  каталога и одного действия: перечислить, посчитать, сложить, наибольшее,
  наименьшее, сгруппировать.
- **FR-002.** Система должна выполнять запрос программой по всем договорам набора.
- **FR-003.** Система должна отклонять запрос, в котором есть поле или действие
  вне разрешённого набора.
- **FR-004.** Все числа в ответе должны быть получены вычислением программы,
  а не написаны языковой моделью.
- **FR-005.** Система должна показывать применённое условие простыми словами.
- **FR-006.** Система должна показывать список договоров, вошедших в результат,
  со ссылкой на пункт, откуда взято значение.
- **FR-007.** Система должна сообщать, сколько договоров не учтено из-за
  незаполненных или непроверенных полей.
- **FR-008.** Система должна по умолчанию использовать только действующие значения
  и по запросу включать значения, ждущие просмотра, с пометкой.
- **FR-009.** Система должна складывать суммы раздельно по валютам.
- **FR-010.** Система должна отказывать в подсчёте, когда нужного поля нет
  в каталоге, и не подменять подсчёт поиском по тексту.
- **FR-011.** Система должна просить уточнение вместо подстановки собственных
  порогов и допущений.
- **FR-012.** Система должна сохранять вопрос, запрос, результат и сведения
  о полноте.

### Сущности

- **Запрос к таблице.** Условия (поле, сравнение, значение), действие, поле
  действия, поле группировки.
- **Результат.** Число, сумма или список; перечень договоров; сведения о полноте.

### Критерии успеха

- **SC-001.** Не менее 90% эталонных вопросов вида «ответ из таблицы» получают
  верный ответ при верных полях. Целевой ориентир; уточняется после первого замера.
- **SC-002.** 100% чисел в ответах совпадают с результатом вычисления программы.
- **SC-003.** 100% ответов показывают применённое условие.
- **SC-004.** Ответ формируется не более чем за 20 секунд. Целевой ориентир.
- **SC-005.** Для любого ответа аналитик может получить список договоров,
  из которых он сложился.

### Вне рамок

- Произвольные запросы к хранилищу, написанные языковой моделью.
- Пересчёт валют.
- Графики.
- Вопросы по содержанию пунктов (фича 09) и выбор маршрута (фича 11).
- Сведения из таблиц приложений.

### Допущения

- Таблица полей заполнена и проверена правилами (фичи 05 и 06).
- Точность ответа ограничена точностью полей.

### Минимальная версия для сквозного прототипа

В прототип не входит. Первая рабочая версия: действия «посчитать» и «перечислить»
с одним условием по шести полям прототипа.

## Часть B. Технические заметки для /speckit.plan

- **Форма запроса.** Список условий: поле из перечня полей-фильтров каталога,
  сравнение (равно, не равно, больше, меньше, между, содержит — только для
  наименований, заполнено, не заполнено), значение. Действие и его поле.
  Форму заполняет модель; допустимые поля и действия проверяет код.
- **Выполнение.** Запрос к хранилищу строит код с параметрами. Текст запроса
  от модели в хранилище не попадает.
- **Текст ответа** собирается кодом по шаблону из результата вычисления. Модель
  не пишет чисел.
- **Применённое условие** записывается простыми словами кодом по шаблонам
  («подрядчик — ООО „…“; дата подписания с … по …»).
- **Сопоставление наименований:** общий модуль приведения; показывать совпавшие
  варианты.
- **Относительные даты** вычисляет код от текущей даты.
- **Источник значений:** действующее значение из фичи 06.
- **Команды** (ориентир): `ask-table "<вопрос>" [--include-unreviewed]`,
  `ask-table eval --label <метка>`.
- **Тесты.** Проверка запроса, выполнение и сборка ответа тестируются без модели
  на подготовленных запросах и синтетической таблице.
