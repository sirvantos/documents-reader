## Часть A. Описание для /speckit.specify

### Суть

По запросу система возвращает упорядоченный список отрывков договоров. Поиск идёт
двумя способами одновременно: по словам и по смыслу. Два списка сливаются в один.
По желанию результат пересортировывает реранкер — модель, которая внимательно
сравнивает запрос с каждым кандидатом. Поиск можно ограничить фильтрами по полям
договора. Каждый шаг включается и выключается, чтобы измерить его вклад.

### Зачем

Ответ не может быть лучше найденных отрывков: если нужный пункт не найден, модель
либо откажется отвечать, либо ответит по неподходящему тексту. Поиск по словам
находит точные номера и термины, поиск по смыслу — перефразированные условия;
по отдельности каждый пропускает своё. Переключатели нужны, чтобы оставить только
те шаги, которые улучшают результат на ваших договорах, а не те, что считаются
обязательными.

### Пользователь

Один аналитик. Он ищет из командной строки и запускает замеры на эталонных
вопросах. Этой же функцией пользуются фичи ответов.

### Сценарии

**Сценарий 1. Найти отрывки по запросу (приоритет P1)**

Проверяется отдельно: выполнить поиск по набору с построенными индексами.

Критерии приёмки:

1. **Дано** индексы построены. **Когда** аналитик вводит запрос. **Тогда** он
   получает упорядоченный список отрывков: договор, номер пункта, заголовок
   раздела, текст, страницы.
2. **Дано** запрос содержит точный номер договора. **Когда** выполняется поиск.
   **Тогда** отрывки этого договора находятся среди первых результатов.
3. **Дано** запрос сформулирован другими словами, чем пункт договора. **Когда**
   выполняется поиск. **Тогда** пункт находится за счёт поиска по смыслу.
4. **Дано** слово запроса стоит в другой форме, чем в договоре («неустойки» и
   «неустойка»). **Когда** выполняется поиск по словам. **Тогда** пункт находится.

**Сценарий 2. Сравнить варианты поиска на эталоне (приоритет P1)**

Проверяется отдельно: запустить эталонные вопросы в двух вариантах настройки.

Критерии приёмки:

1. **Дано** эталонные вопросы загружены. **Когда** аналитик запускает прогон
   с заданной настройкой и меткой. **Тогда** результат записан в таблицу
   результатов с этой меткой.
2. **Дано** доступны варианты: только по словам, только по смыслу, слияние,
   слияние с реранкером. **Когда** аналитик запускает каждый. **Тогда** в таблице
   результатов четыре записи, пригодные для сопоставления.
3. **Дано** прогон выполнен. **Когда** аналитик смотрит промахи. **Тогда** для
   каждого вопроса без попадания видно, на каком месте оказался правильный пункт
   в каждом из способов или что он не найден вовсе.

**Сценарий 3. Фильтры (приоритет P2)**

Проверяется отдельно: выполнить один запрос с фильтром и без.

Критерии приёмки:

1. **Дано** запрос с фильтром по номеру договора. **Когда** выполняется поиск.
   **Тогда** все результаты принадлежат этому договору.
2. **Дано** запрос с фильтром по стороне и периоду дат. **Когда** выполняется
   поиск. **Тогда** все результаты принадлежат договорам, удовлетворяющим обоим
   условиям.
3. **Дано** фильтру не соответствует ни один договор. **Когда** выполняется поиск.
   **Тогда** система сообщает, что по фильтру ничего нет, и не снимает фильтр сама.
4. **Дано** фильтр задан по полю, которого нет в перечне полей-фильтров. **Когда**
   выполняется поиск. **Тогда** система отказывает с понятной причиной.

**Сценарий 4. Реранкер (приоритет P2)**

Проверяется отдельно: выполнить запрос с реранкером и без и сравнить порядок.

Критерии приёмки:

1. **Дано** реранкер включён. **Когда** выполняется поиск. **Тогда** кандидаты
   пересортированы, а в результате видны места до и после.
2. **Дано** реранкер выключен. **Когда** выполняется поиск. **Тогда** поиск
   работает без него и без загрузки его модели.
3. **Дано** реранкер включён, а его модель недоступна. **Когда** выполняется
   поиск. **Тогда** поиск останавливается с понятной причиной и не выдаёт
   результат без пересортировки.

**Сценарий 5. Пояснение результата (приоритет P3)**

Проверяется отдельно: запросить пояснение для одного запроса.

Критерии приёмки:

1. **Дано** поиск выполнен. **Когда** аналитик запрашивает пояснение. **Тогда**
   для каждого результата видно его место в поиске по словам, в поиске по смыслу
   и после слияния.
2. **Дано** найден отрывок. **Когда** запрошен расширенный контекст. **Тогда**
   вместе с отрывком возвращается весь его раздел.

### Особые случаи

- Запрос состоит из одного слова или одного номера.
- Запрос очень длинный (абзац текста).
- В запросе опечатка: поиск по смыслу может найти нужное, поиск по словам — нет;
  это видно в пояснении.
- В запросе латинские буквы, похожие на русские («C», «O» в номерах).
- Запрос состоит только из служебных слов: возвращается пустой результат
  с пояснением.
- Один и тот же типовой пункт есть в десятках договоров: результат не должен
  целиком состоять из копий; число результатов от одного договора ограничено,
  если не задан фильтр по договору.
- Индексы устарели относительно текста: поиск выполняется и предупреждает об этом.
- Индекс по смыслу построен другой моделью, чем выбрана для запроса: система
  отказывает с понятной причиной.

### Требования

- **FR-001.** Система должна выполнять поиск по словам с учётом русских словоформ.
- **FR-002.** Система должна выполнять поиск по смыслу.
- **FR-003.** Система должна сливать результаты двух способов в один список.
- **FR-004.** Система должна по настройке пересортировывать кандидатов реранкером.
- **FR-005.** Система должна ограничивать поиск фильтрами по полям из перечня
  полей-фильтров и никогда не ослаблять фильтр самостоятельно.
- **FR-006.** Каждый шаг должен включаться и выключаться настройкой запуска.
- **FR-007.** Система должна возвращать для каждого результата договор, пункт,
  раздел, текст, страницы и сведения о том, каким способом он найден.
- **FR-008.** Система должна прогонять эталонные вопросы с заданной настройкой
  и записывать результат в таблицу результатов через фичу 02.
- **FR-009.** Система должна возвращать по запросу весь раздел найденного отрывка.
- **FR-010.** Система должна ограничивать число результатов от одного договора,
  когда фильтр по договору не задан.
- **FR-011.** Поиск должен выполняться локально; при одинаковых данных
  и настройках он даёт одинаковый результат.

### Сущности

- **Запрос.** Текст, фильтры, настройка.
- **Настройка поиска.** Включённые шаги, число кандидатов, модель поиска
  по смыслу, число результатов.
- **Результат.** Отрывок, итоговое место, места по каждому способу.

### Критерии успеха

- **SC-001.** Для не менее 85% эталонных вопросов с ответом в тексте правильный
  пункт находится среди первых пяти результатов. Целевой ориентир; уточняется
  после первого замера.
- **SC-002.** В таблице результатов есть записи для четырёх вариантов: по словам,
  по смыслу, слияние, слияние с реранкером.
- **SC-003.** Поиск без реранкера отвечает не более чем за 3 секунды, с реранкером
  — не более чем за 10 секунд. Целевой ориентир.
- **SC-004.** 100% результатов поиска с фильтром удовлетворяют фильтру.
- **SC-005.** Повторный запрос даёт тот же список.

### Вне рамок

- Извлечение фильтров из текста вопроса (фича 11).
- Формулировка ответа (фича 09).
- Переписывание запроса языковой моделью и поиск в несколько шагов.
- Вопросы на подсчёт и суммирование (фича 10).

### Допущения

- Запросы на русском языке.
- Набор — несколько тысяч отрывков; скорость не требует особых мер.

### Минимальная версия для сквозного прототипа

Решение аналитика 2026-11-24: реранкер и выбор одного договора входят в прототип.

- Сценарий 1: оба способа и слияние.
- Сценарий 3, только критерий 1: поиск в одном договоре по его идентификатору.
  Фильтры по полям договора (сторона, даты и другие) — позже.
- Сценарий 4 целиком: реранкер включён по умолчанию и отключается настройкой
  запуска; если он включён, а его модель недоступна, поиск останавливается.
  Оставить ли его включённым, решает замер на ноутбуке аналитика: время поиска
  и место правильного пункта с реранкером и без него. Способ замера до появления
  фичи 02 определяется в спецификации.
- Сценарии 2 и 5 — позже; прогон эталонных вопросов — сразу после появления фичи 02.

## Часть B. Технические заметки для /speckit.plan

- **Слияние:** по местам в двух списках (reciprocal rank fusion), постоянная 60.
- **Число кандидатов:** по 30 от каждого способа; реранкер пересортировывает 30
  и оставляет 8. Числа — настройки, подбираются замером.
- **Запрос для поиска по словам** приводится к словарным формам тем же способом,
  что и текст при индексации; номера и коды не приводятся.
- **Латинские буквы-двойники** в номерах приводить к одному виду и в индексе,
  и в запросе.
- **Фильтры** выполняются условием в запросе к хранилищу до ранжирования.
- **Реранкер:** BGE Reranker v2-m3; загружается только при включении. Запуск —
  `llama-server --reranking` (адрес `/v1/rerank`), только `127.0.0.1`, как модель
  поиска в фиче 07.
- **FRIDA:** к запросу добавляется приставка `search_query:`.
- **Память.** Для поиска языковая модель не нужна. Языковая модель, модель поиска
  и реранкер помещаются в память одновременно (замер 2026-11-24, tech-context,
  «Что проверить в первый день», п. 3).
- **Порядок замеров:** по словам → по смыслу → слияние → реранкер → фильтры.
  Шаг остаётся включённым по умолчанию, только если улучшил попадание в первые
  пять.
- **Команды** (ориентир): `search "<запрос>" [--filter поле=значение] [--no-rerank]
  [--explain]`, `search eval --label <метка> [настройки]`.
