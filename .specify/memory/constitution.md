# Конституция проекта: извлечение данных и поиск по договорам (PoC)

## О проекте

Локальная система, которая читает русскоязычные договоры подряда ОАО «РЖД»
(строительно-монтажные и проектно-изыскательские работы), извлекает из них ключевые факты
в таблицу, делает текст договоров доступным для поиска и отвечает на вопросы со ссылкой
на конкретный пункт договора.

Проект — проверка концепции (PoC) на одном ноутбуке. Цель — получить измеренные цифры
качества по каждому этапу и по ним решить, стоит ли строить систему для полного архива.

Конвейер состоит из четырёх этапов:

1. **Чтение** — превращение файла договора в чистый текст с сохранённой структурой:
   текст берётся из текстового слоя PDF, а страницы-сканы распознаются локально.
2. **Извлечение** — заполнение таблицы фактов по каждому договору.
3. **Поиск** — нахождение нужных пунктов по вопросу.
4. **Ответ** — краткий ответ на вопрос с цитатами и ссылками на источник.

## Принципы

### I. Данные не покидают машину (НЕ ОБСУЖДАЕТСЯ)

- Содержимое договоров, извлечённые значения, вопросы и ответы обрабатываются только
  локально. Никаких обращений к внешним сервисам с этими данными.
- Модели скачиваются заранее; во время обработки сеть не требуется.
- Телеметрия библиотек и инструментов отключается.
- Реальные данные договоров, эталонные ответы и результаты прогонов не попадают
  в удалённый репозиторий. В репозитории хранится только код и синтетические примеры.

**Почему:** договоры содержат персональные данные подписантов, банковские реквизиты
и коммерческие условия заказчика. Какие требования к локализации и защите данных
применимы, юридически не подтверждено, как и разрешение на передачу данных вовне.
До такого подтверждения данные обрабатываются только локально.

### II. Исходный файл — источник истины

- Исходный файл договора хранится без изменений. Извлечённый текст — рабочая копия.
- Каждый фрагмент текста, каждое значение и каждая цитата хранят ссылку на документ,
  страницу и место на странице (или в тексте), откуда они взяты.
- Человек должен иметь возможность за один шаг перейти от любого значения к его месту
  в исходном файле.

### III. Нет значения без цитаты (НЕ ОБСУЖДАЕТСЯ)

- Извлечённое значение попадает в таблицу только вместе с дословной цитатой из текста
  договора.
- Каждое утверждение в ответе на вопрос ссылается на пункт договора или строку таблицы.
- Наличие цитаты в тексте проверяет обычная программа, не языковая модель. Значение или
  утверждение без подтверждённой цитаты отклоняется или помечается.

### IV. «Не найдено» — допустимый результат

- Пустое поле и ответ «в документах не найдено» считаются правильным поведением, когда
  данных нет. Система не обязана заполнить каждое поле и ответить на каждый вопрос.
- Придуманное значение считается более тяжёлой ошибкой, чем пропущенное, и учитывается
  в замерах отдельно.

### V. Сначала замер, потом усложнение

- У каждого этапа есть метрика, которая считается на эталонном наборе.
- Любое изменение этапа (новая модель, новый шаг, новая подсказка) сопровождается
  прогоном на эталонном наборе и записью в таблицу результатов.
- Приём остаётся в системе, только если он улучшает цифры. Общепринятость приёма —
  не аргумент.
- Сначала строится самая простая работающая версия этапа, затем она улучшается
  по результатам замеров.

### VI. Этапы независимы и перезапускаемы

- Каждый этап читает сохранённый результат предыдущего и сохраняет свой. Этапы
  не вызывают друг друга напрямую.
- Любой этап можно перезапустить для одного документа или для всех, не трогая остальные.
  Повторный запуск с теми же входными данными и настройками не создаёт дубликатов.
- Вместе с каждым результатом сохраняется, чем он получен: версия кода, модель,
  подсказка, настройки.

### VII. Сомнительное — человеку

- Ничто не отбрасывается молча. Файл, страница, поле или ответ, с которыми что-то
  не так, получают явный статус и причину.
- Проверки (формат, диапазон, совпадение суммы цифрами и прописью, порядок дат)
  пишутся обычным кодом и работают одинаково при каждом запуске.
- Языковая модель используется только там, где без неё нельзя: для распознавания
  текста страниц-сканов, извлечения значений из текста, разбора вопроса и формулировки
  ответа.

### VIII. Простота

- Один пользователь, один ноутбук. Никаких абстракций «на вырост».
- Конвейер и замеры запускаются из командной строки. Для вопросов, просмотра полей
  и проверки по источнику есть локальный веб-экран; он только показывает сохранённые
  результаты и доступен только на этой машине.
- Одна зависимость на одну задачу. Новая библиотека добавляется, только когда без неё
  задачу нельзя решить несколькими десятками строк кода.
- Каждая фича даёт результат, который можно проверить отдельно от остальных.

## Ограничения первого этапа

Эти допущения приняты сознательно. Спецификации не должны их нарушать, а система должна
явно сообщать, когда входные данные им не соответствуют.

| Ограничение | Следствие |
|---|---|
| PDF с текстом и сканы | Страница-скан распознаётся локально на ноутбуке. Распознанный текст помечается как распознанный и хранит место на странице. Страница с низким качеством распознавания помечается и уходит на ручной просмотр. Цитата проверяется по распознанному тексту: ошибка распознавания внутри цитаты даёт неподтверждённую цитату, а не принятое значение |
| Российские договоры на русском языке | Реквизиты сторон — ИНН, КПП, ОГРН; валюта — рубли. Страница с буквами не русского алфавита (например, казахскими: Ә, Ғ, Қ, Ң, Ө, Ұ, Ү, Һ, І) помечается и уходит на ручной просмотр |
| Две стороны договора | «Заказчик» и «Подрядчик»; договор с иным составом сторон помечается |
| Договоры не связаны между собой | Дополнительные соглашения не обрабатываются как изменения; если такой файл попадёт в систему, он будет обработан как самостоятельный договор. Сведения, которые договор переносит в дополнительные соглашения (например, календарный график работ), считаются отсутствующими |
| Один пользователь | Права доступа и учётные записи не реализуются; веб-экран не открывается по сети |
| 50 договоров | Скорость важна только в пределах «прогон набора за разумное время на ноутбуке» |
| Система сообщает, что написано в договоре | Юридические оценки («рискован ли пункт», «законно ли условие») не даются |

## Что считается готовым PoC

- На 50 договорах заполняется таблица по полям первой очереди каталога полей.
- Система отвечает на 50–100 эталонных вопросов с цитатой и ссылкой на пункт.
- По каждому из четырёх этапов есть измеренные цифры в таблице результатов.
- Качество распознавания страниц-сканов измерено и записано в таблицу результатов
  отдельной цифрой.
- Для каждой ошибки можно определить, на каком этапе она возникла.

## Порядок работы

- Одна фича — одна спецификация — одна ветка.
- Фича считается законченной, когда её критерии приёмки выполнены, проходят
  автоматические проверки кода (тесты, линтер, проверка типов) и результат записан
  в таблицу результатов (для фич, влияющих на качество).
- Отступление от принципа допускается только с записью: что нарушено, почему, и что
  должно произойти, чтобы отступление было снято.

## Технический контекст

Общие технические решения проекта записаны в файле `docs/tech-context.md`:
оборудование, стек, набросок модели данных, договорённости между этапами, карта фич.

- При составлении плана любой фичи (`/speckit.plan`) этот файл обязательно читается
  целиком до начала работы.
- Решения из него обязательны для плана. Выбор, оставленный в нём открытым, делается
  в плане фичи и записывается обратно в этот файл.
- Отступление от решения из этого файла допускается только с записью в плане: что
  изменено и почему. После этого файл обновляется.
- Решения с пометкой **[проверить]** нельзя считать подтверждёнными, пока проверка
  не выполнена и её результат не записан в файл.
- Спецификации (`/speckit.specify`) технологий не называют; этот файл в них
  не используется.

Перечень извлекаемых полей, их виды и допустимые значения записаны в файле
`docs/field-catalog.md`. Он обязателен для всех фич, которые работают с полями.
Поле, которого нет в каталоге, не извлекается и не используется как фильтр.

## Разработка с ИИ-агентом

Код пишется с помощью облачного ИИ-агента. Принцип I распространяется и на него:

- Тексты реальных договоров, эталон и результаты прогонов не передаются агенту:
  ни вставкой в запрос, ни чтением файлов из папки данных, ни выводом в терминал
  во время его работы.
- Отладка и тесты ведутся на синтетических договорах, которые лежат в репозитории.
- Папка данных находится вне репозитория и вне рабочей папки агента.

## Изменение конституции

Принципы I и III не меняются в рамках PoC. Остальные принципы и ограничения первого
этапа меняются явным решением владельца проекта с записью даты и причины.

- Конституция имеет приоритет над остальными договорённостями проекта, включая
  `docs/tech-context.md`, спецификации, планы и задачи.
- Версия конституции меняется по правилам семантического версионирования:
  MAJOR — удаление или переопределение принципа или ограничения; MINOR — новый принцип
  или раздел либо существенное расширение правил; PATCH — уточнения формулировок
  без изменения смысла.
- Каждый план фичи (`/speckit.plan`) проверяет соответствие принципам до начала
  проектирования и после него; найденные отступления оформляются по правилу из раздела
  «Порядок работы».
